## H — 설계·일정을 바꿔야 하는 항목

### 1. 1개월 차 ER 파이프라인이 2개월 차 DB 스키마에 의존한다

7장은 1개월에 "엔티티 해석 4단계 파이프라인"을 두고 DB 스키마를 2개월에 둔다. 그런데 4단계의 1단계는 pgvector 후보 검색이고, 2단계는 `person_aliases`와 위계 정보를 쓴다. DB 없이는 1단계·2단계를 만들 수 없다.

**수정 방향**: `persons`, `person_aliases`, `person_embeddings` 3개 테이블과 마이그레이션은 1개월 차로 당긴다. 나머지 테이블(`events`, `schedules`, `person_facts`)은 2개월 차에 두어도 된다.

### 2. 기획서 일정과 하네스의 마일스톤이 다르다

| 시기 | 기획서 7장 | CLAUDE.md / backlog / architect |
|------|-----------|--------------------------------|
| M1 | 데이터셋 150건 + ER 4단계 + 베이스라인 3종 | 스키마 + 툴 골격 + ER v1 + 소규모 조기 점검 |
| M2 | 툴·루프·DB·API·로깅 | 루프 + 3계층 메모리 + 관측성 |
| M3 | 프론트 3화면 + 브리핑 | 평가 150건 + 베이스라인 + 곡선 |
| M4 | 전반 인프라 / 후반 평가·보고서 | 프론트 + 인프라 + 데모 |

둘 다 "ER 먼저, UI 마지막"이라는 원칙은 같지만 평가와 프론트의 위치가 다르다. architect가 backlog를 채울 때 어느 쪽을 따를지 정해야 한다.

**권장안**: 기획서의 "1개월 차 성능 수치"는 유지하되 150건 전체가 아니라 30~50건 파일럿 세트로 낮춘다. 150건 완성과 최종 평가는 M4 후반에 두되, 측정 코드 자체는 M1에 만든다. 프론트는 M3, 인프라는 M4 전반이라는 기획서 순서를 따르고 CLAUDE.md의 마일스톤 표를 그에 맞게 고친다.

### 3. 트레이드오프 설명의 임계치 방향이 반대다

5.2: "확신도 임계치를 낮추면 오병합은 줄지만 질문이 늘어". 자동 병합 임계치를 **낮추면** 더 낮은 확신도에서도 병합하므로 오병합이 **늘고** 질문은 **줄어든다**. 문장은 "임계치를 높이면 오병합↓ 질문↑"이어야 한다. 같은 문장이 `.claude/skills/eval-harness/SKILL.md` 4절에도 있다.

또한 3.2의 高/中/低 분기는 임계치가 **두 개**(병합 상한, 신규 생성 하한)다. 상한을 올리면 오병합이 줄고 질문이 늘며, 하한을 내리면 미검출이 줄고 질문이 는다. 스윕은 상한 하나를 고정하거나 2차원으로 그려야 한다.

**수정 방향**: 5.2 문장 방향을 바꾸고, 곡선의 x축을 "병합 상한 임계치"로 명시한다. 스킬 문서도 함께 고친다.

### 4. "LLM 출력 확률"은 Claude API에서 얻을 수 없다

3.4와 10장 꼬리 질문은 확신도를 "LLM 출력 확률 + 임베딩 유사도 + 규칙 충족"으로 결합한다고 한다. Claude Messages API는 토큰 로그 확률을 반환하지 않는다. 툴 호출 응답에서도 마찬가지다.

**수정 방향**: LLM 신호를 "모델이 구조화 출력으로 직접 산출한 확신도 점수(0~1)"로 정의한다. 자기보고 점수는 보정이 필요하므로, M1 파일럿 세트에서 점수 구간별 실제 정답률을 표로 만들어 보정한다. 이 보정 표 자체가 보고서의 산출물이 된다.

### 5. 임베딩 공급자가 정해지지 않았다

4장은 `vector(1536)`을 고정했지만 어떤 임베딩 모델을 쓰는지 없다. Claude API에는 임베딩 엔드포인트가 없으므로 별도 공급자가 필수다. 차원은 공급자·모델에 따라 다르므로 1536은 모델을 정한 뒤 확정해야 한다.

**수정 방향**: 착수 단계에서 임베딩 공급자와 모델을 결정하고, 스키마의 차원을 그 모델에 맞춘다. 한국어 짧은 호칭("팀장", "그 사람")의 임베딩 품질을 파일럿에서 먼저 확인한다.

## M — 구현 전에 결정해야 하는 항목

### 6. 신규 인물 등록 시 확인 여부

3.2 루프는 "확신도 低 → create_person (신규)"로 자동 등록한다. 8장 데모 1번과 부록 채팅 화면은 "김팀장을 기억해둘까요? [네] [다른 사람이에요]"로 **확인 후** 등록한다. 부록의 "1일차: 확인 칩만 성가심"도 확인형을 전제한다.

**결정 필요**: 신규 등록도 ask_user를 거치는지, 자동 등록 후 취소 가능하게 하는지. 확인형이면 ask_user 발생률 지표에 "신규 확인"과 "동일성 확인"을 분리해 집계해야 한다.

### 7. `ask_user(question, options) → str`의 동기 반환

웹 채팅에서는 사용자 답이 다음 HTTP 요청으로 온다. 툴이 한 요청 안에서 `str`을 받아 돌아올 수 없다. 작업 메모리가 인메모리라서 서버 재시작 시 대기 중인 질문도 사라진다.

**결정 필요**: `ask_user`는 "대기 중 질문"을 저장하고 루프를 중단하는 툴로 정의하고, 답이 오면 그 질문 ID로 루프를 재개한다. 대기 질문은 DB에 저장한다(예: `pending_questions` 테이블 또는 `agent_traces`의 step 상태).

### 8. 시맨틱 메모리 → 원문 링크가 스키마에 없다

3.3은 "원문은 보존해 근거 추적이 가능"이라 하지만 `person_facts`에는 출처 이벤트를 가리키는 컬럼이 없다. 승격된 사실에서 어떤 `events`가 근거였는지 알 수 없다.

**수정 방향**: `person_facts.source_event_ids` (배열) 또는 `fact_sources(fact_id, event_id)` 조인 테이블을 추가한다. 부록 ②의 "타임라인 펼치면 원문"은 `events.raw_utterance`로 이미 가능하다.

### 9. 인물당 임베딩 1개

`person_embeddings(person_id, embedding)`는 인물당 벡터 하나다. "김팀장"으로 만든 벡터로 "부장님"을 찾아야 하는데, 별칭이 쌓일수록 어떤 텍스트를 임베딩할지 모호해진다.

**수정 방향**: 별칭 단위 임베딩(`person_aliases`에 embedding 컬럼 또는 `alias_embeddings`)으로 바꾸고 후보 검색은 별칭 매칭 후 인물로 묶는다. 이렇게 해야 "person_aliases 누적이 검색 정확도를 높인다"는 4장의 주장이 실제로 성립한다.

### 10. 툴 시그니처와 스키마 필드 불일치

| 툴 | 문제 |
|----|------|
| `add_event(person_id, type, content, occurred_at)` | `events.raw_utterance`를 받을 인자가 없다. 원문 보존이 3.3의 핵심인데 툴이 원문을 모른다. 런타임이 자동 주입하든 인자를 추가하든 명시해야 한다. |
| `update_person(person_id, facts)` | 승진 케이스에서 "새 호칭을 `person_aliases`에 누적"해야 하는데 별칭 인자가 없다. `aliases` 인자를 추가하거나 `add_alias`를 facts의 특수 키로 정의한다. |
| `create_person(name, aliases, tags, hierarchy)` | `tags`(복수) vs `persons.relation_tag`(단수). 태그가 하나인지 여럿인지 정한다. |
| `search_person(query: str)` | 2단계 규칙 필터가 위계·소속 제약을 쓰는데 문자열 하나로는 전달할 수 없다. `hints`(위계, 관계 태그) 선택 인자를 둔다. |
| `events.type` | 값 집합이 정의되지 않았다. 추출 F1을 재려면 고정 집합이 필요하다. |

### 11. "반복 패턴 감지"의 메커니즘이 없다

부록 ✅표와 ② 카드의 "공개 석상에서 지적 3회", 8장 브리핑의 "최근 3회 모두 공개 석상 지적 패턴"은 핵심 데모인데, 2장 포함 범위와 3장 아키텍처 어디에도 없다.

**수정 방향**: 3.3 승격 규칙의 산출물로 정의한다. "같은 `events.type`이 N회 이상이면 요약 시 패턴 사실(`person_facts.key = 'pattern:*'`)을 생성"처럼 규칙을 문서화하고 2장 포함 목록에 넣는다.

### 12. 브리핑 트리거와 푸시 구독 저장소가 없다

"만남 직전 브리핑"과 "웹푸시"를 하려면 (a) `schedules.scheduled_at`이 임박한 항목을 찾는 주기 작업, (b) 브라우저 푸시 구독 정보를 저장할 테이블이 필요하다. 둘 다 아키텍처와 스키마에 없다.

**수정 방향**: 백엔드 컨테이너 안의 주기 작업(예: APScheduler)과 `push_subscriptions(user_id, endpoint, keys, created_at)` 테이블을 추가한다. 데모의 "시간 앞당기기"는 이 주기 작업을 수동 트리거하는 엔드포인트로 구현하면 8장의 "발표자 수동 트리거 버튼"과 겸용된다.

### 13. 예상 비용에 LLM·임베딩 API가 빠져 있다

6장 "월 $30~40"은 AWS 항목만이다. 150건 × 베이스라인 4종 × 임계치 스윕 × 개발 중 반복 실행이면 LLM 호출이 수천 건이다. 9장은 소형 모델·캐싱·결과 재사용을 말하지만 금액 추정이 없다.

**수정 방향**: 착수 시 시나리오 1건당 토큰을 실측하고 LLM 예산 항목을 별도로 잡는다. 평가 실행은 배치 API 사용을 검토한다.

### 14. CloudFront → EC2 TLS 방법

ACM 공개 인증서는 EC2에 직접 설치할 수 없다. 선택지는 (a) CloudFront가 EC2 오리진에 HTTP로 접속(구간 평문), (b) EC2에 Let's Encrypt 설치, (c) ALB 추가(월 비용 증가). 6장은 이 중 무엇인지 말하지 않는다.

**수정 방향**: 비용상 (b)를 기본으로 하고 트레이드오프를 문서화한다. CloudFront용 ACM 인증서는 us-east-1에서 발급해야 한다는 점도 기록한다. RDS는 인터넷 아웃바운드가 필요 없으므로 NAT 없이 프라이빗 서브넷에 두는 것이 맞고, "퍼블릭 서브넷"은 EC2에만 해당한다고 명확히 한다.

### 15. 데모 날짜

부록 ① 채팅에서 "다음 주 화요일 3시" → "9/10(화)". 타임라인의 오늘은 9/03이고 2026년 9월 3일은 목요일이다. 다음 주 화요일은 9/08이고, 9/10은 목요일이다. 리허설 스크립트에서 실제 발표일 기준으로 다시 계산해야 한다.

### 16. 예시 수치

부록 "F1 0.87, 오병합률 3%, 베이스라인 대비 +0.19"는 가상의 예시인데 결과처럼 읽힌다. CLAUDE.md 원칙 5(수치 조작 금지)에 비추어 "예시"임을 명시하거나 삭제한다. 같은 이유로 "F1 0.85면 여섯 번에 한 번 틀린다"도 F1은 오류율이 아니므로 표현을 완화한다.

### 17. 제목의 "관계 그래프"

1장 제목은 "개인 관계 그래프 기반"인데 2장은 인물 간(A–B) 관계 저장을 제외한다. 저장되는 것은 사용자–인물 관계뿐이므로 그래프가 아니라 별(star) 구조다. 심사위원이 "그래프가 어디 있느냐"고 물을 수 있다. 제목을 "관계 메모리 기반"으로 바꾸거나, 제외 사유에 "그래프는 향후 확장"을 넣는다.

### 18. 승진 후 표시 이름

8장 5번 브리핑은 승진 반영 후에도 "김팀장 회의"라 부른다. `display_name`을 최신 호칭으로 갱신할지, 최초 호칭을 유지하고 별칭만 누적할지 정책이 없다. 데모에서 눈에 띄는 부분이므로 정한다.

### 19. 브리핑 "제안"과 상담 제외의 경계

8장·부록 ③의 "1:1을 요청해 보세요"는 조언이다. 2장은 고민 상담을 제외한다. "브리핑 제안은 기록된 사실에서 도출되는 한 줄 행동 제안으로 한정하고, 감정·고민에 대한 대화는 하지 않는다"처럼 경계를 문장으로 적어두면 발표에서 방어할 수 있다.

### 20. AWS 크레딧 조건

"신규 계정 크레딧 $200"은 2025년 7월 이후 신규 계정의 크레딧 제도를 가리키는 것으로 보이며, 가입 시 일부와 활동 완료 시 추가분으로 나뉘고 유효기간이 있다. 계정 생성 시점의 실제 조건을 확인하고 기획서에 근거 링크를 남긴다.
