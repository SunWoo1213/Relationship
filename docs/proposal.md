## 1. 프로젝트 개요

### 제목

대화형 관계 메모리 에이전트 — 자연어 대화에서 자동 구축되는 개인 관계 그래프 기반 브리핑 시스템

### 한 줄 정의

사용자가 평소처럼 대화하면 에이전트가 인물·사건·일정을 스스로 추출·해석해 장기 메모리를 구축하고, 만남 직전에 필요한 맥락만 요약해 제공한다.

### 문제 정의

관계가 넓은 사용자는 사람을 기억하지 못해 반복적으로 손실을 겪는다(이름 착오, 지난 대화 반복, 경조사 누락). 기존 해법은 두 갈래이고 둘 다 실패한다.

| 기존 해법 | 한계 |
|-----------|------|
| 수동 기록 도구 (노션, 명함 앱) | 입력 비용이 체감 가치를 초과 → 유지되지 않음 |
| 범용 LLM (ChatGPT) | 세션을 넘어 축적되지 않고, 동일 인물의 호칭 변이를 식별하지 못함 |

→ 입력을 요구하지 않고, 대화에서 스스로 메모리를 구축하는 에이전트가 필요하다.

### 기술적 난제 (본 프로젝트의 핵심 기여)

한국어는 사람을 이름으로 지칭하지 않는다. 동일 인물이 대화 속에서 다음과 같이 등장한다.

```
팀장 → 김팀장 → 우리 팀장님 → 그 사람 → 걔 → 부장님(승진 후) → 김선배
```

이를 하나의 인물로 묶는 **엔티티 해석(Entity Resolution)** 이 시스템 전체의 성능을 좌우한다. 잘못 병합하면 신뢰가 즉시 붕괴하고, 병합하지 못하면 메모리가 파편화된다.

## 3. 에이전트 아키텍처 ★ 핵심

### 3.1 툴 정의 (Function Calling)

파이프라인 하드코딩이 아니라 LLM이 툴을 선택·호출하는 구조로 설계한다.

| 툴 | 시그니처 | 역할 |
|----|----------|------|
| `search_person` | `(query: str) → Person[]` | 언급된 지칭에 대응하는 기존 인물 후보 검색 |
| `create_person` | `(name, aliases, tags, hierarchy)` | 신규 인물 등록 |
| `update_person` | `(person_id, facts)` | 인물 정보 갱신 (호칭 변경, 소속 이동) |
| `add_event` | `(person_id, type, content, occurred_at)` | 상호작용 사건 기록 |
| `add_schedule` | `(person_id, title, scheduled_at)` | 향후 일정 등록 |
| `get_briefing` | `(person_id) → Briefing` | 만남 전 요약 생성 |
| `ask_user` | `(question, options) → str` | 확신도 부족 시 사용자에게 질의 |

`ask_user`를 별도 툴로 정의한 것이 설계상 핵심이다. 에이전트가 "모른다"를 스스로 판단하고 선택하는 행동으로 만들어, 오병합을 구조적으로 차단한다.

### 3.2 에이전트 루프

```
사용자 발화
   │
   ▼
[인식]  발화에서 인물 지칭 표현 추출
   │
   ▼
[해석]  search_person → 후보 검색 → 동일성 판정
   │
   ├─ 확신도 高 ──> 기존 인물로 연결
   ├─ 확신도 中 ──> ask_user (사용자 확인)
   └─ 확신도 低 ──> create_person (신규)
   │
   ▼
[기록]  add_event / add_schedule / update_person
   │
   ▼
[응답]  자연스러운 대화 응답 생성
```

단일 호출이 아니라 다단계 루프라는 점, 그리고 각 단계에서 툴 선택이 일어난다는 점이 에이전트 구조의 근거가 된다.

### 3.3 메모리 3계층 ★ 면접 최대 어필 포인트

| 계층 | 저장소 | 내용 | 수명 |
|------|--------|------|------|
| 작업 메모리 | 인메모리 | 최근 N턴 대화 컨텍스트 | 세션 |
| 에피소드 메모리 | `events` 테이블 | 개별 사건 + 원문 발화 보존 | 영구 |
| 시맨틱 메모리 | `person_facts`, 인물 카드 | 요약된 사실과 반복 패턴 | 영구 |

**압축 승격 규칙**: 동일 인물의 에피소드가 임계치를 넘으면 LLM이 요약해 시맨틱 메모리로 승격한다. 원문은 보존해 근거 추적이 가능하다.

대부분의 지원자가 "벡터 DB에 넣고 유사도 검색"에서 끝나는 지점에서, 계층 분리 + 압축 승격 + 근거 추적을 설계했다고 말할 수 있다.

### 3.4 엔티티 해석 4단계 파이프라인 ★ 기술 기여

| 단계 | 방법 | 목적 |
|------|------|------|
| 1. 후보 검색 | pgvector 임베딩 유사도 | 전체 인물 중 상위 K명 추림 |
| 2. 규칙 필터 | 한국어 호칭 사전 + 소속·위계 제약 | "팀장"과 "이모"를 후보에서 배제 |
| 3. LLM 판정 | 대화 맥락 + 후보 정보 → 동일성 판단 | 최종 판정 및 확신도 산출 |
| 4. 안전장치 | 확신도 임계치 미만 → `ask_user` | 오병합 방지 |

**"왜 LLM 단일 호출로 하지 않았는가"** 에 답할 수 있는 것이 이 설계의 목적이다. 인물이 늘수록 전체를 프롬프트에 넣을 수 없고(1단계 필요), LLM은 위계·소속 제약을 자주 어기며(2단계 필요), 오병합 비용이 미검출 비용보다 훨씬 크다(4단계 필요).

### 3.5 관측성

- 각 스텝의 입력·출력·툴 호출·토큰 사용량 로깅
- 판정 근거(후보 목록, 확신도) 저장 → 오류 사후 분석
- 발표 시 "에이전트가 어떻게 판단했는지"를 보여주는 화면으로 활용

## 4. 데이터 모델

```sql
persons(id, user_id, display_name, relation_tag, hierarchy, created_at)
person_aliases(id, person_id, alias, source)          -- 호칭 누적
person_embeddings(person_id, embedding vector(1536))  -- pgvector
person_facts(id, person_id, key, value, confidence, updated_at)
events(id, person_id, type, content, raw_utterance, occurred_at, created_at)
schedules(id, person_id, title, scheduled_at, briefed_at)
agent_traces(id, session_id, step, tool_name, input, output, tokens, created_at)
```

`person_aliases` 누적이 엔티티 해석의 성능을 시간에 따라 개선시키는 구조다. `agent_traces`가 관측성과 평가 실험의 근거 데이터가 된다.

**관계 태그**: 가족 / 연인 / 친구 / 직장 / 지인 × 위계 상 / 동 / 하
→ 브리핑 내용과 알림 조건을 분기시키는 용도. 사용자가 고르지 않고 대화에서 자동 추론한다.

## 5. 평가 계획 ★ 보고서의 결과 섹션

### 5.1 데이터셋 구축

- 한국어 대화 시나리오 150건 직접 작성
- 호칭 변이 케이스 의도적 포함 (승진에 따른 변경, 지시대명사, 별칭 혼용)
- 정답 라벨: 각 지칭 표현 → 인물 ID 매핑

### 5.2 지표

| 지표 | 의미 |
|------|------|
| Precision / Recall / F1 | 인물 동일성 판별 전반 성능 |
| **오병합률 (False Merge Rate)** | 핵심 지표 — 다른 사람을 같은 사람으로 묶은 비율 |
| 미검출률 | 같은 사람을 다른 사람으로 분리한 비율 |
| 이벤트·일정 추출 F1 | 구조화 추출 정확도 |
| 툴 호출 정확도 | 올바른 툴을 선택한 비율 |
| ask_user 발생률 | 정확도–사용자 마찰의 트레이드오프 지표 |

마지막 지표가 중요하다. 확신도 임계치를 낮추면 오병합은 줄지만 질문이 늘어 UX가 나빠진다. 이 트레이드오프 곡선을 그려 최적점을 제시하는 것이 결과 섹션의 하이라이트가 된다.

### 5.3 베이스라인 비교

| 방식 | 기대 |
|------|------|
| 문자열 완전 일치 | 낮음 |
| 임베딩 유사도 단독 | 중간 |
| LLM 단일 프롬프트 | 중간~높음 |
| 제안 4단계 하이브리드 | 높음 |

이 표가 "그냥 GPT 부른 거 아니냐"에 대한 최종 반박이다.

## 6. 인프라 및 배포

```
사용자
  ├─ CloudFront ──> S3            (React 빌드 · PWA)
  └─ CloudFront ──> EC2 (Docker)  (FastAPI 백엔드)
                        ├──> RDS PostgreSQL + pgvector
                        └──> LLM API (외부)
```

| 항목 | 선택 | 근거 |
|------|------|------|
| 프론트 | S3 + CloudFront + ACM | 정적 파일에 서버 불필요, PWA 필수 요건인 HTTPS를 무료 인증서로 충족 |
| 백엔드 | EC2 t3.small + Docker | 1인 개발 기준 최단 경로 |
| DB | RDS db.t4g.micro + pgvector | 별도 벡터 DB 불필요 — 인물 테이블과 임베딩을 같은 DB에서 조인 |
| 시크릿 | SSM Parameter Store | Standard 타입 무료 |
| IaC | Terraform | VPC·EC2·RDS·S3 정의. DevOps 어필 겸용 |
| CI/CD | GitHub Actions | 무료, 설정 최소 |
| 네트워크 | 퍼블릭 서브넷 + 보안그룹 | NAT Gateway 월 $35~45 회피 (트레이드오프 문서화) |
| 오케스트레이션 | 미도입 | EKS 컨트롤 플레인 월 $73 — 프로젝트 규모에 부적합. K8s는 로컬 k3s로 별도 학습 |

**예상 비용**: 월 $30~40 × 4개월 ≈ $120~160 → AWS 신규 계정 크레딧 $200 내 처리 가능.
**필수 조치**: AWS Budgets 알림($10 / $30 / $50) 첫날 설정.

## 8. 데모 시나리오 (3분)

1. "오늘 김팀장이랑 또 부딪혔어" → 인물 인식, "김팀장을 기억해둘까요?"
2. 몇 턴 대화 → 인물 카드가 실시간으로 채워지는 화면
3. "다음 주 화요일에 그 사람이랑 회의 있어" → 일정 자동 추출
4. ★ "부장님이 또 그러시더라" (승진으로 호칭 변경)
   → "김팀장님 말씀이신가요? 승진하셨다면 반영할게요"
5. 시간 앞당기기 → 브리핑: "내일 15시 김팀장 회의 — 최근 3회 모두 공개 석상 지적 패턴. 1:1 요청을 제안합니다"

4번이 하이라이트다. 기술적 난제를 심사위원이 눈으로 확인하는 지점이며, 시연 리허설의 대부분을 여기에 투자한다.

**푸시 3중 안전장치**: 웹푸시 / 인앱 배너 / 발표자 수동 트리거 버튼. 현장 네트워크 문제로 데모가 죽지 않게 한다.

## 10. 면접 답변 초안 (AI Agent 직군)

> "대화에서 인물·사건·일정을 추출해 장기 메모리를 구축하는 에이전트를 만들었습니다.
>
> 가장 어려웠던 건 한국어 엔티티 해석입니다. 같은 사람이 '팀장', '그 사람', 승진 후엔 '부장님'으로 불리는데, 단일 LLM 프롬프트로는 인물 수가 늘면 컨텍스트에 다 넣을 수 없고 위계 제약도 자주 어겼습니다. 그래서 임베딩 후보 검색 → 규칙 필터 → LLM 판정 → 확신도 미달 시 사용자 확인의 4단계로 나눴습니다.
>
> 특히 ask_user를 별도 툴로 정의해서, 에이전트가 '모른다'를 스스로 판단해 선택하도록 했습니다. 오병합은 사용자 신뢰를 즉시 무너뜨리지만 되묻기는 마찰에 그치기 때문에, 비대칭 비용을 설계에 반영한 겁니다.
>
> 메모리는 작업/에피소드/시맨틱 3계층으로 나누고 압축 승격 규칙을 뒀습니다. 원문을 보존해서 요약의 근거를 추적할 수 있게 했고요.
>
> 평가는 호칭 변이를 포함한 한국어 대화 150건 데이터셋을 직접 만들어서 F1과 오병합률을 측정했고, 베이스라인 3종과 비교했습니다. 확신도 임계치에 따른 정확도–질문빈도 트레이드오프 곡선도 뽑아서 운영 지점을 정했습니다."

### 꼬리 질문 대비

| 예상 질문 | 답변 방향 |
|-----------|-----------|
| 왜 벡터 DB를 따로 안 썼나요? | pgvector로 충분 + 인물 테이블과 조인 필요 + 운영 복잡도·비용 |
| 확신도는 어떻게 산출했나요? | LLM 출력 확률 + 임베딩 유사도 + 규칙 충족 여부 결합 |
| 오병합이 왜 미검출보다 나쁜가요? | 미검출은 카드가 늘 뿐 복구 가능, 오병합은 잘못된 정보가 브리핑에 섞여 신뢰 붕괴 |
| 확장한다면? | 툴 추가로 기능 확장 가능한 구조. 멀티 유저 시 인물 임베딩 인덱스 분리 필요 |

# 부록 A. 완성됐을 때 실제로 손에 쥐는 것 (서비스 최종 형태)

## 화면은 셋입니다

### ① 채팅 — 데이터가 들어가는 곳

```
─────────────────────────────────────
  나: 오늘 김팀장이랑 또 부딪혔어

  🤖 회의 때 또 그런 일이 있었나 보네요.
     어떤 상황이었어요?

     ┌─────────────────────────────┐
     │ 👤 김팀장을 기억해둘까요?    │
     │    [네]  [다른 사람이에요]   │
     └─────────────────────────────┘

  나: 사람들 다 있는데 내 보고서 지적하더라

  🤖 기록해뒀어요. 이런 일이 세 번째네요.

  나: 다음 주 화요일 3시에 그 사람이랑 회의야

     ┌─────────────────────────────┐
     │ 📅 9/10(화) 15:00 김팀장 회의│
     │    [등록]  [아니에요]        │
     └─────────────────────────────┘
─────────────────────────────────────
```

평소처럼 얘기하면 하단에 확인 칩이 뜹니다. 폼도 없고 입력 화면도 없습니다.

### ② 인물 카드 — 쌓인 것이 보이는 곳

```
─────────────────────────────────────
  김팀장                    [직장 · 상급자]
  별칭: 팀장, 우리 팀장님, 부장님
  마지막 접촉: 3일 전

  ▸ 알고 있는 것
    · 딸 대학 입시 중
    · 골프 안 침
    · 3월 승진 누락

  ▸ 반복 패턴  ⚠️
    공개 석상에서 지적 — 3회
    (5/12, 7/28, 9/03)

  ▸ 타임라인
    09/03  회의에서 보고서 공개 지적    ⌄
    08/21  점심 같이 함, 딸 얘기
    07/28  전체회의에서 지적당함        ⌄
    ...

  ▸ 다가오는 일정
    09/10 (화) 15:00  회의
─────────────────────────────────────
```

타임라인 항목을 펼치면 원문 발화가 나옵니다. 요약이 틀렸을 때 근거를 확인하고 고칠 수 있습니다.

### ③ 브리핑 — 앱을 여는 이유

```
─────────────────────────────────────
  📌 내일 15:00 · 김팀장 회의

  · 최근 3회 모두 공개 석상 지적 패턴
  · 지난 만남(8/21)은 분위기 좋았음, 딸 입시 얘기
  · 3월 승진 누락 이후 예민한 시기일 수 있음

  💡 제안
     지적이 반복되니 회의 전 1:1을 요청해
     사전에 공유해두는 방법이 있습니다
─────────────────────────────────────
```

## 시간이 지나면서 이렇게 변합니다

| 시점 | 인물 수 | 체감 |
|------|---------|------|
| 1일차 | 1~2명 | ChatGPT보다 나을 게 없음. 확인 칩만 성가심 |
| 1주차 | 5~8명 | 카드가 채워지기 시작. 첫 브리핑이 유용하게 느껴지는 지점 |
| 1개월 | 15~20명 | 패턴 감지가 작동. "또 그 패턴이네요"가 나옴 |
| 3개월 | 30명+ | 타임라인이 자산이 됨. 이 시점부터 지우기 아까워짐 |

이 곡선 자체가 이 제품의 정체이자 약점입니다. 1일차가 가장 나쁘고 3개월차가 가장 좋습니다. 실사용자를 붙잡으려면 1주차까지 버티게 만들어야 하는데, 졸업 프로젝트 범위에서는 그 문제를 풀지 않습니다.

## 되는 것 / 안 되는 것

| ✅ 된다 | ❌ 안 된다 |
|---------|-----------|
| 대화에서 인물·사건·일정 자동 추출 | 음성 입력 |
| 호칭 변이 인식 (팀장 = 부장님) | 카카오톡·캘린더·연락처 연동 |
| 인물 카드 자동 구축·갱신 | iOS 푸시 알림 (조건부만) |
| 만남 전 브리핑 | 인물 간(A–B) 관계도 |
| 반복 패턴 감지 | 감정 상담 |
| 관계 태그 자동 분류 | 다중 사용자 운영 |
| 웹·안드로이드 설치형(PWA) | 오프라인 사용 |

## 냉정하게 — 이건 무엇인가

완성품은 **"동작하는 시스템"** 이지 **"출시 가능한 서비스"** 가 아닙니다. 이 구분을 명확히 알고 계셔야 발표에서도 면접에서도 흔들리지 않습니다.

### 출시 제품과의 격차

- 사용자 1명 기준으로 설계돼 있습니다. 멀티테넌시는 스키마에 `user_id`가 있을 뿐 실제 검증은 안 됩니다
- 콜드스타트가 그대로 남습니다. 연락처 가져오기가 없어서 빈 상태로 시작합니다
- 엔티티 해석 F1이 0.85쯤 나온다면 여섯 번에 한 번은 틀립니다. 실사용에는 부족한 수치입니다
- 계정·백업·복구·보안 대응이 최소 수준입니다

### 그럼에도 손에 남는 것

| 항목 | 가치 |
|------|------|
| 배포된 URL | 포트폴리오에 링크로 넣을 수 있는 실물 |

| 확장 가능한 기반 | 졸업 후 이어서 개발 가능한 상태 |
