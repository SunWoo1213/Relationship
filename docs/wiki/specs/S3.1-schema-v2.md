# S3.1 · 스키마 v2

원문: `docs/resolution-plan.md` §3.1 · 위: D2 D5 (R8 R12) · 아래: P1-schema · 이웃: S3.2(툴이 이 스키마를 쓴다)

```sql
persons(id, user_id, display_name, relation_tag, hierarchy, created_at, updated_at)
person_aliases(id, person_id, alias, source, embedding vector(1536), confirmed_at)  -- N=1536: D4 확정(text-embedding-3-small, reports/embed_pilot.md)
person_facts(id, person_id, key, value, confidence, updated_at)
fact_sources(fact_id, event_id)                          -- 시맨틱 사실 → 근거 원문
events(id, person_id, type, content, raw_utterance, occurred_at, created_at)
schedules(id, person_id, title, scheduled_at, briefed_at)
pending_questions(id, session_id, kind, question, options, context, answer, created_at, answered_at)
push_subscriptions(id, user_id, endpoint, keys, created_at)
agent_traces(id, session_id, step, tool_name, input, output, tokens_in, tokens_out, created_at)
```

- `person_embeddings` 없음 (D5).
- `events.type` CHECK 제약: `conflict / praise / meal / meeting / personal_share / favor / other`.
- `relation_tag` ∈ {가족, 연인, 친구, 직장, 지인}, `hierarchy` ∈ {상, 동, 하}.
- `person_aliases.source` ∈ {user_said, confirmed, system} (P2-tools 결정 5, 앱 검증·DB CHECK 없음).
- `pending_questions.kind` ∈ {identity, new_person, schedule}.
- `agent_traces.output`(ER 단계): `candidates[]`, `confidence_breakdown{}`, `decision`.
- 인물–인물 관계 테이블 없음 (D8, 원칙7).
- 인물 단위 완전 삭제가 가능해야 함(기획서 9장 개인정보) → FK ON DELETE CASCADE.
- **보충(CR-006 · D18, 2026-11-15 — 리비전 0003)**: 계정과 계정별 격리.
  ```sql
  users(id, username, password_hash, created_at)                     -- id 는 Text(persons.user_id 와 같은 타입), username UNIQUE(소문자 정규화)
  auth_sessions(id, user_id, token_hash, created_at, expires_at)     -- token_hash UNIQUE, 토큰 원문은 저장하지 않는다
  chat_messages(id, user_id, role, content, question_id, created_at) -- role ∈ {user, assistant}, question_id 는 칩이 달린 답(nullable)
  pending_questions(+ user_id)                                       -- NOT NULL, 답변 소유 검사
  ```
  - 새 테이블의 `auth_sessions.user_id`·`chat_messages.user_id` → `users.id` FK ON DELETE CASCADE. 기존 테이블의 `persons.user_id`·`push_subscriptions.user_id`·`pending_questions.user_id` 는 `users.id` 값을 담되 **FK 는 두지 않는다**(P9b 결정 O 권장안 — 기존 테스트 수백 건이 `users` 행 없이 인물을 만든다. 계정 삭제는 범위 밖이라 CASCADE 가 필요 없다. 값의 출처는 로그인 의존성 하나로 강제한다).
  - `agent_traces` 는 바꾸지 않는다 — 대화 trace 의 `session_id` 가 `chat:<user_id>` 라 계정으로 거슬러 갈 수 있다(P9b 결정 N).
  - 0003 은 기존 사용자 데이터(`persons` 와 그 CASCADE 자식, `pending_questions`, `push_subscriptions`, `agent_traces`)를 **비운다**(CR-006 결정 4). downgrade 는 스키마만 되돌리고 데이터는 돌아오지 않는다.
  - 계정 간 인물 관계는 여전히 없다 — `users` 는 사용자이지 인물이 아니다(원칙7).
- **보충(CR-007 · D18 결정 10·11, 2026-11-16 — 리비전 0004)**: 계정 닉네임.
  ```sql
  users(+ nickname)                                                  -- Text NOT NULL, UNIQUE uq_users_nickname(정규화한 값: NFC·앞뒤 공백 제거·영문 소문자)
  ```
  - 최종 `users(id, username, nickname, password_hash, created_at)`. 닉네임은 사용자 자신의 표시 이름이다 — 인물이 아니고 `persons`·`person_aliases` 와 관계가 없다(원칙7).
  - UNIQUE 는 앱이 정규화한 값 그대로에 거는 **보통 UNIQUE 제약 하나**다(함수 인덱스 없음 — `lower()` 는 앱이 저장 전에 한다). 형식(길이·허용 문자)은 앱이 검사하고 DB CHECK 는 두지 않는다(`username` 과 같다).
  - 0004 upgrade 순서: ① `nickname` 을 nullable 로 추가 ② 기존 행을 `nickname = username` 으로 채움(아이디는 이미 UNIQUE·소문자라 닉네임 UNIQUE 를 어기지 않는다) ③ NOT NULL ④ UNIQUE. **데이터를 지우지 않는다**(0003 과 다르다). downgrade 는 제약·컬럼만 지운다 — 계정 행은 남고 닉네임 값만 사라진다.
- **보충(CR-008 · D19, 2026-11-17 — 리비전 0005)**: MCP 개인 접근 토큰.
  ```sql
  mcp_tokens(id, user_id, token_hash, created_at, expires_at, last_used_at)  -- user_id UNIQUE(계정당 1개), token_hash UNIQUE, 토큰 원문은 저장하지 않는다
  ```
  - `id` BIGINT PK · `user_id` Text NOT NULL → `users.id` FK **ON DELETE CASCADE**, UNIQUE `uq_mcp_tokens_user_id` · `token_hash` Text NOT NULL, UNIQUE `uq_mcp_tokens_token_hash`(`hash_token()` = sha256 hex, `auth_sessions.token_hash` 와 같다) · `created_at`·`expires_at` timestamptz NOT NULL · `last_used_at` timestamptz **NULL**(아직 안 씀). 별도 인덱스 없음(두 UNIQUE 가 조회 경로를 덮는다). CHECK 없음.
  - 다시 발급하면 그 계정 행을 덮어쓴다(upsert) — 이전 해시가 사라져 이전 토큰은 즉시 무효. 폐기는 행 삭제.
  - 0005 upgrade 는 테이블 생성뿐 — **기존 데이터를 지우지 않는다**. downgrade 는 `mcp_tokens` 만 지운다(발급한 토큰 전부 무효, 계정·기록 불변).
  - 최종 테이블 13개(원본 9 + 0003 3 + 0005 1). `users` FK 는 `auth_sessions`·`chat_messages`·`mcp_tokens` 세 곳(FK 총 9).
- 보충(FIX-020, 2026-10-06): UNIQUE `person_facts(person_id, key)` · `person_aliases(person_id, alias)` · `push_subscriptions(user_id, endpoint)` — 동시 upsert 로 중복 행이 생기지 않도록 DB 제약으로 강제(0002 리비전).
