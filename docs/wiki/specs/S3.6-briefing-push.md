# S3.6 · 브리핑 트리거와 푸시

원문: `docs/resolution-plan.md` §3.6 · 관련: R12 원칙7(경계) · 적용: P6-briefing, P7-push

- 주기 작업(컨테이너 내, 1분): `scheduled_at - now() ≤ 24h AND briefed_at IS NULL` → `get_briefing` → 웹푸시 → `briefed_at`.
  - 운용(CR-005 · D17 개정 ②, 2026-11-14): 배포도 EC2 컨테이너 안 lifespan 루프(1분) 그대로 — `BRIEFING_SCHEDULER_ENABLED=1` 을 운영 `.env` 에서 켠다. (1차 Vercel 안의 "GitHub Actions 5분 스케줄" 보충은 같은 날 철회됨.)
  - 보충(2026-10-02, P6-briefing 결정 B(i) 사용자 확정): 창은 `now ≤ scheduled_at ≤ now + 24h` — **이미 지난 일정은 제외**한다(만남 "직전" 맥락. 서버가 꺼져 있다 켜져도 지난 약속 브리핑이 한꺼번에 생기지 않는다). `get_briefing` 의 `upcoming_schedules`(`scheduled_at >= now`)와 같은 방향. 기획서 본문에 이 공식이 없어 CR 이 아니라 카드 보충이다(02-plan-verify H-2).
  - 다중 사용자(CR-006 · D18, 2026-11-15): 한 번 돌 때 **사용자마다** 같은 함수를 그 사용자의 `ToolContext(user_id=…)` 로 부르고, 한 사용자의 실패는 로그로 남기고 다음 사용자로 넘어간다. 대상은 창 안에 미브리핑 일정이 있는 사용자.
- 수동 트리거 `POST /briefings/run` = 같은 함수. (CR-006) 로그인 사용자의 일정만 — 남의 `schedule_id` 는 404.
- 보기(CR-006 변경 항목 2, P9c-briefing-calendar): 브리핑 화면에 목록 보기와 함께 **월 달력 보기** — 월 범위 일정과 그 일정의 최신 브리핑 존재 여부를 날짜별로 보인다. 읽기 전용(LLM 0·trace 0), 새 생성 없음. 데모 "시간 앞당기기"와 "발표자 수동 버튼" 겸용.
- 브리핑 내용: 기록된 사실·패턴·최근 사건. **제안은 사실에서 도출되는 한 줄 행동 제안으로 한정**, 감정·고민 대화 금지.
- 보충(CR-009 · D20, 2026-11-22): ① **고지 미동의 계정**은 주기 작업에서 브리핑 생성·푸시를 건너뛰고(LLM 0·푸시 0·`briefed_at` 무변경 — 동의 뒤 창 안이면 그때 만든다), 수동 `POST /briefings/run` 은 403 `notice_required`(사용자 결정 17·21). 건너뛰는 자리·trace 빈도는 P9d 01-plan. ② **민감 항목 제외 자리**: `get_briefing` 툴 안(사실·최근 사건·다가오는 일정 — 상한은 거른 뒤, 민감 대상 일정은 `ScheduleNotFound`) + 브리핑 입력의 사실 재조회와 근거 원문(사건 표시로도 거름) + 일정 선정(기본·수동 모두 민감 일정 건너뜀, 수동은 skip 사유 `sensitive_schedule`). 그래서 브리핑 LLM 프롬프트·저장 브리핑·푸시 제목·본문에 민감 항목이 0. ③ 배포 전에 만든 저장 브리핑은 소급하지 않는다(그대로 `GET /briefings`·MCP 로 나간다). ④ 만료된 민감 질문 원문 정리를 같은 1분 루프의 **사용자 반복 밖 독립 단계**로 얹는다 — 스위치가 꺼진 환경에서는 돌지 않는다.
- 푸시 구독은 `push_subscriptions`. (CR-006) 같은 endpoint 는 마지막으로 구독한 계정 하나에만 묶이고(다른 계정의 같은 endpoint 행은 구독 저장 때 지운다), 로그아웃 시 그 브라우저 endpoint 행을 그 계정에서 지운다 — 남의 일정 알림이 내 브라우저로 오지 않는다. VAPID 키는 SSM/환경변수, 코드·저장소에 두지 않는다.
