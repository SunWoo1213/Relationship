# verification — 가시적 검증 규칙 카드

> "확인했습니다 / 완료했습니다"는 검증이 아니다. **다른 사람이 같은 명령을 쳐서 같은 것을 볼 수 있어야** 검증이다.
> 집행부: `.claude/scripts/verify-plan.sh`(계획), `.claude/scripts/verify-impl.sh`(구현), 템플릿의 증거 열.

## 증거로 인정하는 것 (이 중 하나가 없으면 "보류")

| 종류 | 형태 | 어디에 남기나 |
|------|------|---------------|
| 자동 테스트 출력 | `pytest -q` 전체 출력 파일 | `packages/<id>/evidence/<ts>-pytest.txt` |
| 명령 재현 출력 | 실행한 명령 + 출력 (curl, alembic, psql, docker compose ps …) | `evidence/<ts>-<name>.txt` 또는 04-review 코드 블록 |
| 데이터 확인 | SQL 조회문 + 결과 행 | 같은 방식 |
| trace 확인 | `agent_traces` 행(step, candidates, confidence_breakdown, decision) | 같은 방식 |
| 커밋 해시 | 7자 이상 | 04-review 증거 열 |
| 파일 경로 | 존재하는 파일 (스크린샷 `.png`, 리포트 `.md/.json`) | 증거 열 |
| 카드 인용 | 계획 검증에서: 카드 파일명 + 해당 문장 | 02-plan-verify 근거 열 |

인정하지 않는 것: "정상 동작 확인", "문제 없음", "검토 완료", 출력 없이 붙인 명령, 요약만 있는 테스트 결과.

## 계획 검증 기법 (02-plan-verify)

1. **카드 인용** — 점검표 8행마다 근거 열에 카드 파일명과 인용 문장을 쓴다. 빈 근거 열은 스크립트가 FAIL 처리한다.
2. **기계 검증** — `bash .claude/scripts/verify-plan.sh <id>` 실행 결과를 02-plan-verify "기계 검증 출력" 절에 그대로 붙인다. FAIL 이 있으면 결과는 통과가 될 수 없다.
3. **수용 기준 문자열 일치** — 계획의 수용 기준은 backlog 문장과 글자 그대로 같아야 한다(스크립트 4번). 바꿔 쓰면 목표가 슬쩍 바뀐다.
4. **의존 상태 확인** — 선행 패키지의 04-review `결과: 완료`를 스크립트가 확인한다. P5 이후는 P4 게이트.
5. **중복 확인** — 산출물 경로가 `registry.md`에 다른 패키지로 있으면 경고. 이미 만든 것을 다시 만들지 않는다.

## 구현 검증 기법 (04-review, FIX 결과)

1. **테스트 우선** — 위험 로직(병합·승격·임계치·삭제)은 회귀 테스트가 먼저 있고, 그 출력 파일이 증거다.
2. **재현 명령** — 수용 기준마다 "이 명령을 치면 이것이 보인다"를 적고 출력을 붙인다. `verify-impl.sh`가 증거 열의 파일·해시·경로 실재를 검사한다.
3. **데이터로 확인** — 스키마·마이그레이션은 `\d 테이블` 또는 `information_schema` 조회 결과. ER 판정은 `agent_traces` 행.
4. **부정 케이스** — "되어야 할 것"만이 아니라 "되지 말아야 할 것"(팀장↔이모 배제, T_merge 미만 자동병합 없음, create_person 직접 호출 실패)의 테스트 출력.
5. **태그 역추적** — `git log --grep <태그>` 결과 파일. 03-log 의 Refs 와 커밋이 어긋나면 경고.
6. **registry 등록** — 만든 모듈·엔드포인트·툴·테이블·테스트를 `registry.md`에 올린다. 등록 없으면 FAIL.

## 평가(eval) 산출물의 검증 (원칙8)

- `metrics.json`만으로 `eval.md`가 재생성되는지: 재생성 명령과 diff 결과를 증거로.
- 데이터셋·라벨 변경은 커밋 diff 로만. "조정"은 CR 또는 FIX 로 기록.
- 미달 수치도 그대로 기록. 실패 케이스 분석 파일 경로가 증거다.

## 검증 → 조치 루프 (문제가 나왔을 때 에이전트가 따르는 순서)

```
1. 검증 실행      bash .claude/scripts/verify-plan.sh <id>  또는  verify-impl.sh <id>
                  | tee docs/wiki/packages/<id>/evidence/<ts>-verify-*.txt
2. 소견 생성      python .claude/scripts/findings.py <id> evidence/<ts>-verify-*.txt --source verify-impl
                  → 05-remediation.md 에 FAIL/WARN 마다 F-xxxxxx 블록 (같은 문제 = 같은 ID)
3. 소견 채우기    블록마다: 원인 가설 → 확인 명령 실행·출력 인용 → 해결 단계 표
                  (단계 = 파일·방법 + 완료 판정 명령 + 기대 출력. 명령 없는 단계는 단계가 아니다)
4. 조치 실행      단계 순서대로. 단계마다 완료 판정 명령을 실제로 실행해 상태를 완료로.
                  결정·명세(D/S/원칙)를 바꿔야만 풀리면 → 멈추고 FIX/CR 로 올려 사용자에게.
5. 재검증         1 의 같은 명령을 다시 실행 → findings.py 재실행 → 사라진 소견은 자동 해소.
6. 반복 한도      같은 소견이 3회 재검증 후에도 열려 있으면 재시도하지 않고 사용자에게 보고(원칙8).
7. 커밋           소견 해소도 작업 단위다 → /commit (Refs 에 F-id 포함)
```

- pytest 출력도 2번에 그대로 넣을 수 있다(`FAILED …` 줄을 소견으로 만든다).
- 평가(P4·P10) 미달은 `metrics.json` 수치를 인용해 같은 형식의 블록을 직접 추가한다(출처: eval). 해결 단계가 "S3.3 재설계"면 그것은 CR/D 카드 작업이다.
- 소견은 삭제하지 않는다. 해소된 소견도 남아 "무엇이 왜 실패했고 어떻게 고쳤나"의 기록이 된다.

## 사람이 하는 마지막 판단

기계 검증이 전부 PASS 여도 사용자의 승인(`승인:` 줄)이 있어야 다음 단계다. 기계는 "빠진 것"을 찾고, 사람은 "방향"을 본다.
