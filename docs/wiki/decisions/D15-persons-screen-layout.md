# D15 · 인물 화면 배치 — 카드 그리드 + 이름·별칭 검색, 사이드바는 최근 5명, 상세는 가운데 비례 폭

상태: 유효 (대체하는 D 카드 없음 — P8-frontend 01-plan 의 **결정 N 일부·U6 문장**을 대체한다) | 해결하는 검증: 없음(R1~R20 중 화면 배치 항목 없음) | 출처: CR-003 (제기·승인 2026-10-16 사용자, 문서 이행 2026-10-21) · 변경: `docs/wiki/changes/CR-003.md`

**결정**
1. `#/persons` 인물 화면은 세로 목록이 아니라 **카드 그리드**다. 타일마다 이름·관계 태그·위계·마지막 접촉(·별칭 1~2개)을 보이고, 타일을 누르면 **기존 상세 경로 `#/persons/:id`** 가 열린다(새 화면·새 라우트 없음). 데스크톱 2~3열, 모바일 1열.
2. 인물 화면에 **검색창 1개**를 둔다. 이름(`display_name`)과 별칭(`aliases`)의 **부분 일치**로 그리드를 바로 줄인다. 검색·자르기는 **프론트에서** 한다(새 엔드포인트·새 쿼리 파라미터 없음, CR-003 §3 ③(가)). **보정(2026-10-21, 결정 K (나))**: `GET /persons` 응답에는 별칭이 없었으므로(`PersonListItemOut` 5필드) 응답에 `aliases: list[str]`(읽기 전용, 카드 응답과 같은 값·순서) 1필드를 더한다 — CR-003 §2 가 예고한 "(나) 응답 1필드 추가(읽기 전용, 스키마 아님)" 갈래. 스키마 v2·툴 시그니처 v2 는 그대로.
3. **관계 태그 필터 컨트롤은 두지 않는다.** 기획서 2장 표의 제외 칸 "관계 태그 필터링"은 움직이지 않는다 — 넣고 싶으면 별도 CR.
4. 사이드바 인물 목록은 전원이 아니라 **최근 5명**이다. 기준은 `last_contact_at`(마지막 사건 시각 — `GET /persons` 가 이미 이 순서로 정렬해 준다) 내림차순 앞 5명, 그 아래 "전체 보기 →"(`#/persons`) 링크. 사이드바 구조(결정 N — 모든 폭 왼쪽 사이드바, 모바일 서랍형, 하단 탭바 없음)는 그대로다.
5. 폭·정렬 규칙(**PC 웹 기준**, 창 크기에 비례): **목록/그리드는 본문 폭 전체**(왼쪽부터, 폭 상한 없음). **상세(`#/persons/:id`)는 가운데**, 폭은 고정 px 가 아니라 본문 폭의 **75%**(`md:` 이상), 모바일 100%. **75% 에 px 상한을 두지 않는다** — 01-plan 체크리스트 2항("줄 폭이 너무 넓지 않다")보다 뒤에 나온 상위 결정이며, 넓은 창에서 원문 줄이 길어지는 것은 사용자가 32행 점검에서 자기 화면으로 판정한다(review-u10-closeout R-U10C-4). 채팅(`mx-auto max-w-3xl`, 768px 가운데)·브리핑(상한 없음)은 바꾸지 않는다.
6. 서버 문자열은 프론트가 바꾸지 않는다(결정 L 경계·원칙7). 타일·검색 결과의 문구는 `GET /persons` 값 그대로이고, 검색은 그 값의 부분 일치다.

**이유**
U10 사람 점검(2026-10-16)에서 사용자가 셋을 요구했다 — "인물 카드들을 왼쪽에 나열하지 않고 인물카드란을 만들어서 거기서 검색해서 찾아볼 수 있게", "왼쪽에 나열된건 최근에 수정한 5명 정도만", "인물을 무조건 아래로 내리는게 아니라 진짜 카드처럼 클릭해서 볼 수 있게". 인물이 늘면 사이드바 전원 목록이 메뉴를 밀어내고(U10 관찰 3-1), 세로 목록은 찾기가 느리다. 5명 기준을 `last_contact_at` 으로 둔 것은 "최근에 대화에 나온 사람"이 사용자 의도에 가깝고 **백엔드 변경이 0** 이기 때문이다(`persons.updated_at` 은 응답 필드 추가가 필요해 보류). 검색을 프론트에서 하는 것은 지금 인물 수에서 충분하고 U6 "새 API 없음"을 지키기 위해서다 — 인물이 수백 명이 되면 그때 서버 검색(`GET /persons?q=&limit=`)을 별도 결정으로. 상세를 가운데·비례 폭으로 둔 것은 "상세보기를 했을 때는 왼쪽으로 치우치지 않으면 좋겠어 · 창의 크기에 따라 비율을 맞춰야 해"(사용자, 2026-10-16).

**파급**
- S 카드: 무변경(스키마 v2·툴 시그니처 v2). 조회 API 응답은 `GET /persons` 에 `aliases` 1필드 추가(읽기 전용, 결정 K (나)) — S 카드가 정하는 범위 밖(조회 API 는 P8 에서 생긴 것).
- P 패키지: P8-frontend 01-plan **결정 N**(사이드바 "아래 인물 목록 전원" → 최근 5명)·**U6**("필터 컨트롤 없음, 같은 목록 컴포넌트를 사이드바에도" → 그리드+검색, 사이드바는 5명)·**체크리스트 19·20**(사이드바 인물 = 5명 기준). 상세 가운데·75% 는 U10 수정 1회로 이미 반영(`3bd5025`). 나머지 코드는 **P8b-persons-grid**(P8 04-review 뒤 `/devlog start`).
- CLAUDE.md 원칙: 5(화면 3개)·7(제외 범위) 그대로 — 문장 교체 없음.
- 기획서: 본문 무변경, 상단 "원본 이후 확정된 사항" 한 줄.

**코드에서 지켜야 할 것** (리뷰어가 grep 으로 확인)
- `web/src/api/client.ts` 의 `getPersons` 는 인자가 없다 — `?q=`·`?limit=` 를 붙이지 않는다. 백엔드 변경은 `GET /persons` 응답(`PersonListItemOut`)에 `aliases: list[str]` 를 더하는 것뿐(결정 K (나), 2026-10-21) — `app/api/read.py`·`app/api/schemas.py`·`tests/test_api_read_persons.py` 밖 `app/`·`alembic/` diff 0, 마이그레이션 0.
- 인물 화면에 `relation_tag`·`hierarchy` 로 거르는 `<select>`/토글이 없다. 검색 `<input>` 은 1개이고 `display_name`·`aliases` 부분 일치만 한다.
- 타일은 `#/persons/:id` 로 이동한다(`href="#/persons/`). 라우트는 여전히 3경로(`#/chat`·`#/persons`·`#/briefings`) — 판정 13행.
- 사이드바(`AppShell.tsx`)가 그리는 인물은 `GET /persons` 결과의 **앞 5명**이고 그 아래 `#/persons` 링크가 있다. 서버 정렬을 프론트가 재정렬하지 않는다.
- `[data-screen="persons"]` 목록 모드의 **조상·자신 어디에도** `max-w-*`·`mx-auto` 가 없다(R-U10C-3 — `section` 한 요소만 보는 테스트는 부족, 조상 전부 또는 E2E `boundingBox()` 로 목록 폭 ≈ `main` 폭). 상세 모드는 `data-testid="card-wrap"` 가 `mx-auto w-full md:w-3/4` 이고 `max-w-*` 가 없다.
- `ChatScreen.tsx` 의 `mx-auto max-w-3xl`·`BriefingScreen.tsx` 폭은 이 결정으로 바꾸지 않는다.
- 서버 문자열 변환 0(원칙7) — 타일·검색 하이라이트에서 `reply`·이름·별칭을 가공하지 않는다.

**갱신 이력**
- 2026-10-21 신설(CR-003 문서 이행). 상세 가운데·75% 는 U10 수정 1회 `3bd5025` 에 선반영. 그리드·검색·사이드바 5명은 P8b-persons-grid 에서 구현 — 완료 해시는 그때 적는다.
- 2026-10-21 **보정(결정 K (나), P8b 01-plan)**: 신설 때 "목록 전체를 이미 받음" 이라 적었으나 `GET /persons` 응답에 별칭이 없었다(architect 가 `schemas.py` 312~319행에서 확인). 결정 2 와 코드 규칙 1번째 줄을 "응답에 `aliases` 1필드 추가뿐" 으로 고쳤다. CR-003 §2 가 예고한 갈래라 새 CR 은 내지 않았다. 사용자 확정 — P8b 결정 K·A~J.
