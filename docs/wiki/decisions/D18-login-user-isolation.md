# D18 · 아이디·비밀번호 로그인과 계정별 기억 격리 — 계정마다 채팅방 하나, 세션은 계정에 묶인다

상태: 유효 | 해결하는 검증: (직접 R 없음) F-fbaaae · R-U10D-3 · 관련 R12·R14 | 출처: CR-006 (제기·승인 2026-11-15, 사용자)

**결정**
1. **로그인 방식**: 서비스 안에서 **아이디 + 비밀번호**로 가입·로그인·로그아웃. 비밀번호는 **해시로만** 저장(평문·가역 암호화 0). 소셜 로그인·비밀번호 재설정·이메일 인증 없음.
2. **로그인 유지**: 같은 출처(Caddy 가 `/api/*` 를 같은 호스트로 프록시)이므로 **HttpOnly 쿠키**에 무작위 세션 토큰을 담고, 서버는 토큰의 해시만 `auth_sessions` 에 저장한다(새 비밀 값이 필요 없는 방식 — P9b 결정 D 권장안). 로그아웃은 그 행을 지운다.
3. **격리**: `/health`·`/auth/signup`·`/auth/login` 밖의 모든 API 는 로그인 사용자를 요구한다(없으면 **401**). 모든 조회·쓰기는 로그인 사용자의 `users.id` 를 `user_id` 로 쓴다. 남의 인물·사건·사실 근거·일정·브리핑·대기 질문은 **404**(존재 여부를 드러내지 않는 기존 공통 404 규약). **(CR-007 보충, 2026-11-16)** 가입 전 중복 조회 `GET /auth/availability` 도 로그인 없이 열린 예외다 — 예외는 이 네 경로(+ FastAPI 문서 경로)뿐이다. **(CR-008 보충, 2026-11-17)** `/mcp`(D19, `MCP_ENABLED` 켜진 앱에서만)는 예외가 아니라 **자격이 다른 경로**다 — 세션 쿠키가 아니라 `Authorization: Bearer` 개인 접근 토큰으로 인증하고, 없거나 틀리면 401 이다. 토큰은 로그인한 계정만 `/auth/mcp-token`(로그인 필수)으로 만들 수 있고, 토큰이 가리키는 계정의 `users.id` 가 `user_id` 다. 반대로 기존 API 는 Bearer 토큰을 자격으로 받지 않는다(자격이 섞이지 않는다).
4. **계정마다 채팅방 하나**: 계정의 대화 `session_id` 는 서버가 정한다(`chat:<user_id>`). 클라이언트의 `X-Session-Id` 는 더 이상 쓰지 않는다. 대화 기록은 `chat_messages` 에 저장하고, 로그인하면 최근 기록을 불러와 이어서 보인다. **채팅방 목록은 의도적으로 두지 않는다**(사용자 2026-11-15 "채팅방 목록은 일부러 넣지 않아 우리는 관계를 기억하는 것이 메인이니까" — 기억 단위는 대화방이 아니라 인물이다).
5. **대기 질문 소유**: `pending_questions.user_id` 를 두고, `POST /answers/{question_id}` 는 질문의 `user_id` 가 로그인 사용자와 같을 때만 받는다(F-fbaaae 닫기).
6. **브리핑·푸시**: 주기 작업은 사용자마다 같은 `run_briefings` 를 돈다(사용자 단위 예외 격리). 같은 브라우저 endpoint 는 마지막으로 구독한 계정 하나에만 묶이고, 로그아웃하면 그 브라우저의 구독을 그 계정에서 뗀다.
7. **고정 사용자 제거**: `APP_USER_ID` 설정과 `app_user_id()` 를 제품 코드에서 없앤다. `ToolContext.user_id` 는 기본값이 없다(호출자가 반드시 넘긴다).
8. **기존 데이터**: 리비전 0003 이 사용자 데이터 테이블을 비운다(사용자 결정 — 빈 상태에서 시작). 되돌려도 데이터는 돌아오지 않는다.
9. **화면**: 로그인·가입 화면을 더한다(원칙5 폐지 — CR-006). 채팅·인물 카드·브리핑 핵심 화면은 그대로.
10. **(CR-007, 2026-11-16) 닉네임**: 가입할 때 닉네임을 **필수로** 받는다. 닉네임은 사용자 자신의 **화면 표시 이름**이다 — 가입·로그인·내 정보 응답과 사이드바에만 쓰고, 로그인은 여전히 아이디로 한다. 다른 사용자에게 보이는 곳이 없고, 인물(`persons`·`person_aliases`)이 아니며, 제품 속 에이전트의 답·브리핑·툴 입력에 넣지 않는다(원칙7 경계). 규칙·정규화 값은 P9b 결정 X·Y(01-plan 개정 3). 리비전 0004 는 기존 계정의 닉네임을 그 계정의 아이디 값으로 채우고 **계정을 지우지 않는다**.
11. **(CR-007) 중복검사**: 아이디·닉네임은 각각 UNIQUE(정규화한 값)이다. 가입 제출 때 서버가 409 `username_taken` / `nickname_taken`(둘 다 겹치면 `username_taken`)으로 거부하고, 가입 화면은 제출 전에 **로그인 없이** `GET /auth/availability` 로 중복 여부를 조회한다. 최종 판정은 DB UNIQUE + 가입 시 409 이고 조회는 참고용이다(조회와 가입 사이 경합). 아이디와 닉네임은 서로 다른 이름 공간이다.

**이유**
- 사용자 목적(CR-006 원문): 평가 시연에서 "새 계정을 생성하는 모습" 과 "이미 데이터가 들어가 있으면 어떻게 해 주는지" 를 둘 다 보여야 한다 — 한 사람의 기억을 공유하는 지금 구조로는 두 상태를 동시에 보일 수 없다.
- 쿠키 + 서버 세션 테이블: 같은 출처라 CORS·토큰 보관(localStorage XSS 노출)이 필요 없고, 서버 `.env` 에 새 비밀 값을 넣지 않아도 된다(배포 반영이 `git pull` + `compose up` 으로 끝난다). 로그아웃이 즉시 무효화된다(JWT 와 달리).
- 조회 함수(`app/api/read.py`)·후보 검색(`app/er/candidates.py`)·브리핑 선택(`app/briefing/select.py`)은 이미 `user_id` 조건을 건다 — 바뀌는 것은 값의 출처뿐이라 ER·툴·평가 경로가 그대로다.

**코드에서 지켜야 할 것**
1. 비밀번호는 솔트가 있는 느린 해시(P9b 결정 C)로만 저장한다 — `users` 에 평문·가역 값 컬럼 0. 비교는 상수 시간(`hmac.compare_digest`).
2. 세션 토큰은 `secrets` 로 만든 무작위 값이고, DB 에는 그 **해시만** 저장한다. 쿠키 속성은 `HttpOnly`·`SameSite=Lax`·`Path=/`·`Secure`(설정으로 로컬 http 개발만 끔). 만료가 있다. **(CR-008 보충)** MCP 개인 접근 토큰(D19)도 같은 방식 — `secrets` 무작위 값, `mcp_tokens.token_hash` 에 해시만, 만료 7일, 계정당 1개.
3. 비밀번호·토큰·쿠키 값은 로그·`agent_traces`·응답 본문·예외 메시지에 남기지 않는다. **(CR-008 보충)** MCP 토큰 원문은 `POST /auth/mcp-token` 응답 한 번에만 실린다 — 그 밖의 응답·로그·trace·증거 0.
4. `/health`·`/auth/signup`·`/auth/login` 밖의 모든 라우트가 로그인 의존성을 갖는다 — **라우트 목록을 열거해 미로그인 401 을 단언하는 계약 테스트**가 있다(새 라우트가 빠지면 실패). **(CR-007 보충)** 예외에 `GET /auth/availability` 하나를 더한다 — 계약 테스트(`tests/test_auth_required_routes.py`)의 면제 목록도 이름으로 함께 고친다. **(CR-008 보충)** `/auth/mcp-token` 세 메서드는 로그인 필수 목록(`_MUST_REQUIRE_LOGIN`)에 든다. `/mcp` 는 면제 목록에 넣지 않는다 — 스위치를 켠 앱에서 쿠키만 있고 Bearer 가 없으면 401 이라는 단언을 따로 둔다.
5. 요청 경로에서 `app_user_id()`·`APP_USER_ID` 참조 0, `ToolContext.user_id` 기본값 0(`grep` 판정).
6. 대화 `session_id` 는 서버가 계정에서 만든다 — 요청 헤더로 다른 계정의 세션을 가리킬 수 없다.
7. `POST /answers/{question_id}` 는 남의 질문에 404, 질문 행·`answer` 변화 0.
8. 주기 작업은 사용자마다 별도 `ToolContext(user_id=…)` 로 돌고, 한 사용자의 실패가 다른 사용자의 브리핑을 막지 않는다.
9. 툴 7종 시그니처·ER 4단계·임계치·확신도는 바뀌지 않는다(`tools_check` 7/7).
10. **(CR-007)** 닉네임 검사는 정규화(NFC → 앞뒤 공백 제거) 뒤 허용 문자 정규식 `fullmatch` 로 하고, 형식 위반(NUL·제어문자·짝 없는 서로게이트 포함)은 **DB 에 묻기 전에** 422 `invalid_nickname`(조회 API 는 `"invalid"`) — 500 경로 0. 가입과 조회는 같은 정규화 함수 하나를 쓰고, DB UNIQUE 는 그 함수가 돌려준 값에 건다.
11. **(CR-007)** 중복 조회 API 는 읽기 전용이다(쓰기·`agent_traces`·LLM 호출 0). 로그인 응답(없는 아이디·틀린 비밀번호 같은 401)은 바꾸지 않는다.
