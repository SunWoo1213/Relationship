## 1. 무엇이 바뀌는가

- 기획서(`docs/proposal.md`)에는 외부 AI 클라이언트 연동·MCP 문장이 **없다**. 2장 범위 표의 포함 칸에 새 항목이 하나 생긴다.
  - **새 문장(권장안 기준)**: "사용자는 자신의 관계 메모리를 **MCP 클라이언트(Claude·Claude Code·ChatGPT·Codex·Gemini 계열)** 에서 **읽기 전용으로** 조회할 수 있다 — 인물 목록·이름 찾기·인물 카드·저장된 브리핑. 연결은 **서비스 계정으로 로그인해 동의**하는 방식(OAuth)으로만 하며, 기록(쓰기)·브리핑 생성·원문 조회는 MCP 로 열지 않는다."
  - 제외 칸 변동 없음. 다만 **경계 문장 하나를 더한다**(3장 원칙7): "MCP 로 내보내는 것은 기록된 사실 그 자체다. 외부 클라이언트의 LLM 이 그 사실로 무엇을 말하는지는 이 제품의 범위가 아니며, 제품은 상담·평가·A–B 관계를 만들어 내보내지 않는다."
- **"제품 속 에이전트의 툴 7종"과 "MCP 툴"은 다른 것이다.** MCP 툴은 외부 클라이언트가 부르는 **어댑터**이고, 툴 7종 시그니처(S3.2)·`tools_check` 7/7 은 바뀌지 않는다. MCP 툴이 툴 7종 등록표에 섞여 들어가지 않게 한다(11장 수용 기준).
- **새로 생기는 것은 MCP 어댑터만이 아니다 — 이 서비스가 OAuth "인가 서버"가 된다.** 즉 다른 앱(Claude·ChatGPT 등)에 "이 사람의 기록을 읽어도 된다"는 토큰을 내주는 쪽이 된다. D18 결정 1 의 "소셜 로그인 없음"(우리가 남의 로그인을 빌려 쓰지 않는다)과는 방향이 반대라 충돌하지 않는다 — 로그인 자체는 여전히 우리 아이디·비밀번호다.

### 2.2 권장 근거
1. **A-읽기만이 불변 원칙을 하나도 건드리지 않는다.** 쓰기 0 → 원칙1·2·3·4 의 병합 경로가 없고, 툴 7종(S3.2)·ER·임계치가 그대로다. B 는 툴 7종과 게이트를 고치므로 사실상 기획서 핵심 변경이다.
2. **도구 쪽 새 코드가 가장 적다.** 조회 함수가 이미 있다 — `app/api/read.py` 의 `list_persons`(149행)·`get_person_card`(183행)·`list_briefings`(268행). 어댑터는 이 함수들을 그대로 부르고, 응답 모델에 원문 필드가 없다(`PersonCardOut`·`PersonListItemOut`·`BriefingRecordOut` — `app/api/schemas.py` 39·196·222·329행 주석, 원문을 싣는 모델은 `EventRawOut`·`FactSourceEventOut` 둘뿐). 2차 개정에서 커진 부분은 도구가 아니라 **인증(OAuth)** 이다.
3. **LLM 비용 0.** 위 세 함수와 `get_briefing` 툴(`app/tools/briefing.py:6` "LLM 호출이 없다")은 LLM 을 부르지 않는다. 브리핑 **생성**(`run_briefings`)과 채팅 조회 턴(D16, 답 생성에 LLM)만 비용이 든다 → 둘 다 MCP 로 열지 않는다.
4. A-쓰기는 가치가 크지만(밖에서 "오늘 김 부장이랑 점심" 이라고 말하면 기록됨), **외부 LLM 이 발화를 고쳐 쓰는 문제**와 **`ask_user` 왕복 문제**를 풀어야 한다(2.3). 읽기를 먼저 열어 인증·전송을 검증한 뒤 별도 단계로 판단하는 편이 안전하다.

### 2.3 A-쓰기를 나중에 열 경우의 설계 방향 (이번 CR 에서는 결정하지 않음 — 기록만)
- **같은 파이프라인만 탄다**: `record_utterance(text)` 는 `POST /chat` 과 **같은 함수 경로**(`build_chat_ctx` → `run_turn`, `app/agent/loop.py:1086`)를 부른다. `create_person`·`update_person`·`add_event` 같은 툴 7종을 MCP 툴로 **직접 노출하지 않는다** — 노출하면 외부 LLM 이 4단계(후보검색→규칙필터→LLM판정→ask_user)를 건너뛰고 인물을 만들거나 병합할 수 있다(원칙4 위반).
- **`ask_user` 는 MCP 클라이언트에 "대기 질문"으로 돌려준다**: 루프가 `pending_questions` 에 저장하고 `{question_id, status:"pending"}` 으로 끝나는 지금 모델(S3.4) 그대로, MCP 툴 결과에 `question_id`·질문·선택지(`options`)를 싣는다. 사용자가 답하면 `answer_question(question_id, option)` 툴 → `POST /answers/{id}` 와 같은 함수. **외부 LLM 이 사용자 대신 선택지를 골라 답하는 것을 막을 수 없다** — 그래서 ① 툴 설명에 "사용자에게 그대로 물어 보라" 를 적고 ② 대기 질문은 웹 채팅방(`chat:<user_id>`)에도 같은 질문으로 보이게 해 사용자가 웹에서 답할 수 있게 하는 안을 권장한다. MCP 규격의 "사용자에게 묻기" 기능은 클라이언트 지원이 확인된 뒤에(7장 미확인 목록).
- **쓰기 범위(scope)**: OAuth 범위를 `read` 하나로 시작하므로, 쓰기를 열면 `write` 범위를 따로 두고 동의 화면에 별도로 묻는다. 읽기 토큰으로 쓰기 툴 호출은 403 `insufficient_scope`(규격 [F2]).
- **원 발화 보존**: 외부 LLM 이 요약·재작성한 문장이 `raw_utterance` 로 저장된다. 이 한계는 01-plan 에 고지로 남긴다(원칙8 — 평가 데이터에는 섞지 않는다).
- **비용 상한**: 토큰마다 하루 기록 호출 N회(5장).

## 4. 인증 · 격리 (D18 과의 관계)

### 4.1 왜 쿠키를 못 쓰나
D18 결정 2 의 로그인은 같은 출처 **HttpOnly 쿠키**다. MCP 클라이언트(데스크톱 앱·CLI·Anthropic/OpenAI/Google 클라우드의 원격 커넥터)는 우리 출처의 브라우저가 아니므로 그 쿠키를 갖지 않는다. 그래서 `/mcp` 에는 **다른 자격(Bearer 토큰)** 이 필요하다. 다만 **토큰을 받는 과정(인가 화면)** 은 사용자의 브라우저에서 일어나므로 거기서는 기존 로그인 쿠키를 그대로 쓸 수 있다(4.3).

| 인증 없음 + 네트워크 제한 | 로컬에서만 열고 IP 로 막음 | 공개 서버에서 불가 | 채택하지 않음(계정 격리가 사라짐) |
| 로컬 stdio 프록시 + 쿠키 | 사용자 PC 의 얇은 프록시가 아이디·비밀번호로 로그인 | 웹·앱형 클라이언트에 못 붙음 | 채택하지 않음(비밀번호 평문 저장 — security §1) |

### 4.3 OAuth 설계 초안 (2차 권장안 — **3차: 다음 단계, 이번에 안 함.** 이번 자격은 0-b·D19 의 개인 접근 토큰이다. 아래 (가) 의 Bearer 헤더 전용·쿼리 문자열 거부·쿠키 비자격·401 규칙은 토큰 방식에도 그대로 쓴다. (나) 인가 서버·(다) OAuth 테이블 3개는 만들지 않는다)

**이름·주소 (결정 사항이 아닌 기본값 — 01-plan U0 에서 고정)**
- 보호 리소스(MCP): `https://relmemo.com/mcp` — **사용자가 클라이언트에 넣는 주소와 PRM 의 `resource` 가 글자 그대로 같아야 한다** [A4].
- 인가 서버 `issuer`: `https://relmemo.com` (경로 없음 → 메타데이터가 루트 `/.well-known/oauth-authorization-server` 에 놓인다).
- 인가·토큰·등록 엔드포인트: `https://relmemo.com/api/oauth/authorize` · `/api/oauth/token` · `/api/oauth/register` — 지금 Caddy 의 `/api/*` 규칙으로 백엔드에 그대로 닿게 한다(백엔드 라우트는 `/oauth/*`). 실제 경로는 메타데이터가 알려 주는 값이 권위라 루트에 둘 필요가 없다 [조사 6절 머리말].

**(가) 리소스 서버 쪽 — `/mcp`**
1. **보호 리소스 메타데이터(PRM, RFC 9728)**: `GET /.well-known/oauth-protected-resource/mcp`(그리고 같은 내용을 루트 `/.well-known/oauth-protected-resource` 에도). 필드 `resource: "https://relmemo.com/mcp"`, `authorization_servers: ["https://relmemo.com"]`(Claude 는 첫 항목만 씀 [A4]), `scopes_supported: ["read"]`(`offline_access` 는 넣지 않는다 — SHOULD NOT [F2]). SDK 가 자동으로 만들어 주지만, **하위 앱으로 마운트하면 그 경로가 `/mcp/.well-known/…` 아래로 들어갈 수 있다(미확인)** → 우리 FastAPI 루트 라우트로 직접 서빙하는 안을 기본으로 두고 U0 에서 SDK 동작을 확인한다.
2. **401 응답**: 토큰 없음·무효·만료·폐기 → `401` + `WWW-Authenticate: Bearer resource_metadata="https://relmemo.com/.well-known/oauth-protected-resource/mcp", scope="read"`. Claude 는 **401 일 때만** 로그인을 시작한다 [A4]. 범위 부족은 403 + `error="insufficient_scope"`(이번에는 범위가 `read` 하나라 나올 일이 없다).
3. **토큰 받기**: `Authorization: Bearer` 헤더로만. **쿼리 문자열 토큰은 받지 않는다**(MUST NOT [F2]). 쿠키는 자격으로 받지 않는다(4.4).
4. **토큰 검증**: 불투명(무작위) 토큰을 해시해 DB 에서 찾고 ① 만료 전 ② 폐기 안 됨 ③ **audience = `https://relmemo.com/mcp`**(토큰 행에 저장한 `resource` 와 비교 — 자기를 대상으로 발급된 토큰만, MUST [F2]) ④ 범위에 `read` 포함 을 본다. JWT 를 쓰지 않으므로 서명 키·JWKS 가 필요 없고 서버 비밀 값도 늘지 않는다(조사 6.1 #8 — 클라이언트가 JWKS 를 요구한다는 문서는 없음, 미확인). 다섯 곳이 불투명 토큰에 문제없는지는 **미확인**(ChatGPT 문서의 검증 항목이 JWT 를 전제로 쓰여 있음 [C3]) → 11장 U7 실제 연결 시험이 판정.
5. **SDK 연결**: 공식 SDK v2 의 `TokenVerifier.verify_token(token) -> AccessToken | None` 을 구현해 `MCPServer(token_verifier=…, auth=AuthSettings(issuer_url, resource_server_url, required_scopes, validate_token_resource))` 로 넘기고, 툴 안에서 `get_access_token()` 으로 꺼낸다 [G4]. **`AccessToken` 에 사용자 id 를 실을 칸이 있는지 미확인**(예제는 `client_id` 로 식별) → 없으면 `/mcp` 앞에 우리 ASGI 래퍼를 두어 토큰을 직접 검사하고 요청 범위 변수(contextvar)에 `user_id` 를 싣는다. 어느 쪽이든 **툴 입력에는 `user_id` 인자가 없다**.

**(나) 인가 서버 쪽**
1. **인가 서버 메타데이터(RFC 8414)** `GET /.well-known/oauth-authorization-server`: `issuer`, `authorization_endpoint`, `token_endpoint`, `registration_endpoint`, `response_types_supported: ["code"]`, `grant_types_supported: ["authorization_code","refresh_token"]`, `code_challenge_methods_supported: ["S256"]`(없으면 클라이언트가 중단 — MUST [F3]), `token_endpoint_auth_methods_supported: ["none"]`(공개 클라이언트만), `scopes_supported: ["read"]`, `authorization_response_iss_parameter_supported: true`(ChatGPT 요구 [C3]). CIMD 를 열 때 `client_id_metadata_document_supported: true` 추가(Claude 는 이 값과 `none` 이 **둘 다** 있어야 CIMD 를 씀 [A4]). 응답 10초 이내 [A4].
2. **인가 화면 = 기존 로그인 세션 + 동의 화면** `GET /oauth/authorize`:
   - 받는 값: `response_type=code`, `client_id`, `redirect_uri`, `state`, `code_challenge`, `code_challenge_method=S256`(다른 값·누락은 거부), `scope`, `resource`.
   - **먼저 검사, 그다음 화면**: `client_id` 가 등록돼 있고 `redirect_uri` 가 그 클라이언트의 등록값과 **정확히 일치**하며 허용 목록(아래 4)에 맞아야 한다. 틀리면 **리디렉트하지 않고** 오류 화면(열린 리디렉트 방지 — RFC 규칙상 검증 전에는 그 주소로 보내지 않는다).
   - 브라우저에 기존 로그인 쿠키(`__Host-rel_session`, `SameSite=Lax` — 다른 사이트에서 넘어온 최상위 GET 이동에도 실린다)가 있으면 바로 동의 화면, 없으면 **같은 화면에 아이디·비밀번호 칸**을 보여 기존 비밀번호 검사 함수(`app/auth/passwords.py`)로 확인한다. 로그인에 성공하면 기존과 같은 세션 쿠키도 준다(웹 로그인과 같은 상태가 됨).
   - 동의 화면 내용(결정 N2): 연결하려는 앱 이름(등록 때 받은 `client_name` — **자기 신고 값이라 믿지 않는다고 표시**), **리디렉트 주소의 호스트명**(MUST [F3]), 루프백 주소면 "이 컴퓨터의 프로그램" 경고(SHOULD [F3]), 열어 줄 범위("읽기 전용: 인물 목록·인물 카드·저장된 브리핑. 기록·수정·원문은 열지 않음"), 외부 공급자 전송 고지, 로그인한 **아이디**(닉네임은 D18 결정 10 상 사이드바·`/auth/*` 응답 전용이라 쓰지 않는다 — 쓰려면 D18 보충). 버튼: 허락 / 거절.
   - 동의 제출 `POST /oauth/authorize`: 같은 출처 POST 라 기존 Origin 검사(`app/auth/origin.py`)를 그대로 통과·적용. 추가로 인가 요청마다 만든 일회용 값을 폼에 숨겨 두고 세션과 묶어 확인(위조 제출 방지). 화면은 `frame-ancestors 'none'`(다른 사이트가 iframe 으로 덮어 클릭을 훔치는 것 방지).
   - 허락 → `redirect_uri?code=…&state=…&iss=https://relmemo.com`. 거절·오류도 `error=…&state=…&iss=…` [F2][C3].
3. **인가 코드**: 무작위 값, DB 에는 해시만, **한 번만 사용**, 수명 짧게(기본 5분 — 결정 N3), `client_id`·`redirect_uri`·`code_challenge`·`resource`·`scope`·`user_id` 를 함께 저장. 두 번째 사용 시도는 거부하고 그 코드로 나간 토큰도 폐기(재사용 탐지).
4. **리디렉트 허용 목록(서버 설정, 등록 때·인가 때 모두 대조)** [조사 6.5]:
   - Claude 앱(웹·데스크톱·모바일): `https://claude.ai/api/mcp/auth_callback` [A4]
   - ChatGPT: `https://chatgpt.com/connector_platform_oauth_redirect`(`iss` 지원 시) — 정확한 값은 ChatGPT 관리 화면에서 복사하라고 문서가 안내 [C3] → U7 에서 사용자가 확인해 목록을 고정
   - Claude Code: `http://localhost:<포트>/callback`, `http://127.0.0.1:<포트>/callback` — **포트 무시 매칭** [A4]
   - Codex CLI: `http://127.0.0.1/callback`(포트 형식 미확인 [D1]) → 루프백 포트 무시 매칭에 포함
   - Gemini CLI: `http://localhost:<포트>/oauth/callback` [E1]
   - (Gemini 앱을 넣을 때만) `https://oauth-redirect.googleusercontent.com/r/*` 계열 [E5]
   - 규칙: `https` 는 정확 일치, 루프백은 호스트가 `localhost`·`127.0.0.1` 이고 경로가 목록과 같을 때 포트만 무시. 그 밖은 전부 거부.
5. **토큰 엔드포인트** `POST /oauth/token`: **`application/x-www-form-urlencoded`** 로 받는다(JSON 만 받으면 Claude 가 415 로 실패 [A4]). 
   - `grant_type=authorization_code`: `code_verifier` 의 S256 이 저장된 `code_challenge` 와 같은지, `client_id`·`redirect_uri` 가 코드 발급 때와 같은지, `resource` 가 `https://relmemo.com/mcp` 인지 본다. 클라이언트 인증은 `none`(공개 클라이언트).
   - `grant_type=refresh_token`: 아래 6. 무효한 갱신 토큰에는 **`invalid_grant`**(다른 코드 금지 [A4]).
   - `client_credentials` 는 만들지 않는다(Claude·ChatGPT 모두 미사용 [A4][C3]).
   - 응답: `access_token`, `token_type: "Bearer"`, `expires_in`, `refresh_token`, `scope`. `Cache-Control: no-store`.
6. **토큰 수명·저장(해시만) — 결정 N3**: 접근 토큰 **1시간**(짧게 SHOULD [F3]), 갱신 토큰 **30일**(또는 공개 서버 종료일까지 중 이른 쪽). 토큰 원문은 응답 1회에만 있고 DB 에는 `sha256` 해시만(`app/auth/sessions.py` 의 `hash_token()` 재사용). 접두(예: `rma_`·`rmr_`)를 붙여 실수로 붙여 넣은 토큰을 비밀 검사가 알아보게 할지는 결정 Q9.
7. **갱신 토큰 회전과 클라이언트별 충돌**: 규격은 공개 클라이언트에 회전을 MUST 로 하고 [F3] Claude 도 요구한다 [A4]. 반면 **Google(Gemini 앱)은 회전하지 말라고 권고**한다 [E5]. 권장: **기본은 회전**(새 갱신 토큰을 주고 옛 것을 같은 응답에서 무효화), 같은 "토큰 가족"에서 이미 쓴 갱신 토큰이 다시 오면 그 가족 전체를 폐기(도난 탐지). 클라이언트가 응답을 못 받고 재시도하는 경우 사용자가 다시 로그인해야 하는 부작용이 있다 → 짧은 유예(예: 직전 토큰을 30초간 1회 더 인정)를 둘지 결정 N8. Gemini 앱을 넣는다면 그 클라이언트만 회전하지 않는 예외 규칙이 필요하다(결정 N5 와 묶음).
8. **클라이언트 등록 — DCR 먼저, CIMD 는 다음 단계 (결정 N4)**:
   - **DCR** `POST /oauth/register`(RFC 7591, JSON): 다섯 곳이 모두 DCR 로 붙을 수 있다 — Claude 앱은 CIMD 값이 없으면 DCR 로 내려가고 [A4], Claude Code 는 DCR 기본 [B1], ChatGPT 는 DCR 도 지원 [C3], Codex 는 CIMD 가 없으면 DCR [D1], Gemini CLI 는 DCR 만 문서화 [E1]. 받는 것: `redirect_uris`(전부 허용 목록 안이어야 함), `client_name`, `token_endpoint_auth_method: "none"` 만. 돌려주는 것: `client_id`(무작위), 클라이언트 비밀은 **발급하지 않는다**(공개 클라이언트).
   - DCR 은 **로그인 없이 열린 쓰기 엔드포인트**다 → 남용 방지: 요청 크기 상한, 허용 목록 밖 리디렉트 거부, 전체 등록 수 상한(예: 1,000)과 일정 기간 미사용 등록 정리(결정 N4 세부). Claude 는 **새 연결마다 새로 등록**하므로 등록 수가 계속 는다 [A4].
   - 규격 2026-07-28 판은 DCR 을 **폐기 예정(하위 호환 MAY)** 으로 내리고 CIMD 를 SHOULD 로 올렸다 [F2][F4]. 지금 다섯 클라이언트 문서는 모두 DCR 로 동작하므로 DCR 로 시작하고, CIMD 는 단계 4(9장)에서 더한다.
   - **CIMD 를 열 때의 위험**: 인가 서버가 URL 형태 `client_id` 문서를 **우리 서버가 가져온다** → SSRF(우리 서버를 시켜 내부망을 찌르기) 대비가 필요하다(SHOULD [F3]). 권장: 알려진 호스트(`claude.ai`·`chatgpt.com`)의 `https` 주소만, 크기·시간 상한, 캐시. 알려진 값: ChatGPT `https://chatgpt.com/oauth/client.json`, Claude Code `https://claude.ai/oauth/claude-code-client-metadata` [C3][A4]. Claude 앱·Codex 의 CIMD URL 은 미확인.
9. **`iss` 응답 파라미터(RFC 9207)**: 인가 응답(성공·오류 모두)에 `iss=https://relmemo.com`. 메타데이터에 `authorization_response_iss_parameter_supported: true`. ChatGPT 가 요구하고 이 값에 따라 ChatGPT 리디렉트 주소가 달라진다 [C3]. 규격은 SHOULD, 다음 판 MUST 예고 [F2].
10. **연결 해제(폐기)**: 다섯 클라이언트 중 폐기 엔드포인트를 요구한다는 문서는 없다(Gemini 앱만 선택으로 기술 [E5]) → 폐기 엔드포인트는 만들지 않는다. 대신 사용자가 연결을 끊는 방법이 필요하다 — 결정 N6(① 웹에 "연결된 앱" 작은 목록·해제 버튼 ② 서버 명령 ③ 비밀번호 바꾸기·로그아웃과 묶기는 지금 기능이 없어 불가).

**(다) 저장 — 리비전 0005 (테이블 3개, `users` FK `ON DELETE CASCADE`, 원문 토큰 0)**
- `oauth_clients(id, client_id UNIQUE, client_name, redirect_uris, created_at, last_used_at)` — DCR 등록. 비밀 없음.
- `oauth_auth_codes(id, code_hash UNIQUE, client_id, user_id FK, redirect_uri, code_challenge, scope, resource, created_at, expires_at, used_at)`
- `oauth_tokens(id, user_id FK, client_id, family_id, access_hash UNIQUE, refresh_hash UNIQUE, scope, resource, access_expires_at, refresh_expires_at, created_at, last_used_at, revoked_at)`
- 컬럼 이름·인덱스는 U1 에서 고정. 1차안의 `api_tokens` 는 만들지 않는다.

**(라) 계정 격리 — D18 과의 관계**
- **사용자 = 토큰이 가리키는 계정**. 모든 조회는 토큰 행의 `user_id` 로만(D18 결정 3 "user_id 는 로그인 계정에서만 온다"의 확장 — 토큰은 로그인한 사용자가 동의해서만 생긴다). 남의 `person_id` 는 기존과 같이 "없음"(`PersonNotFound` — 존재 여부 비노출).
- **D18 결정 3 의 "로그인 없이 열린 예외는 네 경로뿐" 이 바뀐다** — 새 예외: `GET /.well-known/oauth-protected-resource[/mcp]`, `GET /.well-known/oauth-authorization-server`, `GET·POST /oauth/authorize`(로그인 없으면 로그인 칸을 보여 주는 화면이라 401 이 아님), `POST /oauth/token`, `POST /oauth/register`. 그리고 `/mcp` 는 쿠키가 아니라 Bearer 가 자격(없으면 401). → D18 보충(10장). 계약 테스트 `tests/test_auth_required_routes.py` 의 `_EXEMPT`(35행)에 이름으로 더하고, `/mcp` 는 면제가 아니라 "다른 자격" 단언을 따로 둔다.
- 기능 스위치 `MCP_ENABLED`(기본 0): 꺼져 있으면 `/mcp`·`/oauth/*`·`/.well-known/oauth-*` 가 **모두 없다**(404) — 공개 경로가 늘지 않는다. 켜진 앱에서만 위 예외가 생긴다(`PUSH_DEV_PAGE_ENABLED` 와 같은 패턴, 계약 테스트 153행).
- **시도 제한**: 로그인 칸이 하나 더 생기지만 검사 함수·정책은 기존 로그인과 같다(P9b 결정 H — 시도 제한 없음, 공개 기간 한정). 새로 생기는 공격면이 아니라 같은 비밀번호 검사의 두 번째 입구다. 토큰은 256비트 무작위라 추측 공격은 사실상 불가.
- **로그**: 토큰·코드·`code_verifier` 는 헤더·폼 본문으로만 받는다. 토큰 엔드포인트는 폼 본문이라 Caddy·uvicorn 접근 로그(요청 줄만)에 남지 않을 것으로 보지만 **실측 필요(미확인)**. **인가 코드는 리디렉트 주소의 쿼리 문자열에 실려 나간다**(규격상 정상) — 상대 클라이언트 쪽 로그에 남을 수 있으므로 한 번만·5분만 유효하게 하는 것이 방어다. 예외 메시지·422 본문에 폼 값이 실리지 않게(P9b U2 의 `/auth` 422 `input` 제거와 같은 방어).

### 4.4 Origin 검사 미들웨어(`app/auth/origin.py`)와의 관계
- 지금 미들웨어는 POST·PUT·PATCH·DELETE 에 `Origin` 이 **있으면** 호스트와 같을 때만 통과, **없으면 통과**(13행). 
  - 동의 제출(`POST /oauth/authorize`)은 우리 화면에서 보내는 같은 출처 POST → 통과, 그리고 위조 방어에 그대로 도움이 된다.
  - `POST /mcp`·`/oauth/token`·`/oauth/register` 를 CLI·클라우드 서버가 보내면 보통 `Origin` 이 없어 통과한다. **브라우저 안에서 도는 클라이언트(예: 점검용 MCP Inspector 웹 화면)가 `Origin` 을 붙이면 403** 이 난다. 다섯 클라이언트가 토큰·등록 요청을 브라우저에서 보내는지는 **미확인** → U7 에서 403 이 나면 그 두 경로만 예외로 둘지 판단한다(두 경로는 쿠키를 자격으로 쓰지 않아 교차 요청 위조의 대상이 아니므로 예외의 위험은 작다).
- 규격이 HTTP 전송 서버에 Origin 검증을 요구하는지는 이번 조사 범위에 없었다(미확인). SDK 쪽은 **허용 호스트(`allowed_hosts`) 검사**가 기본으로 켜져 있어 localhost 외 호스트는 421 이다 [G2][G3] — 6장.
- **`/mcp` 는 쿠키를 자격으로 받지 않는다(수용 기준)**. 쿠키를 받으면 브라우저의 교차 요청이 다시 위협이 된다. 반대로 기존 API 는 Bearer 를 받지 않는다(자격이 섞이지 않게).

## 6. 전송 · 배치

### 6.1 전송
- **Streamable HTTP, 같은 FastAPI 앱에 마운트(권장 유지)**. 현재 규격 판은 2026-07-28 이고 `initialize` 핸드셰이크와 `Mcp-Session-Id` 세션이 없어진 무상태 방식, 옛 HTTP+SSE 는 폐기 예정이다 [F1][F4]. 공식 SDK 는 옛 핸드셰이크(2025-11-25 이하) 클라이언트와 새 무상태 요청을 같은 엔드포인트에서 처리한다 [G3] — Gemini 앱은 2025-11-25 판까지만 지원 [E6], Claude·ChatGPT 가 새 판을 쓰는지는 미확인이라 **둘 다 받아야 한다**.
- compose 서비스 **3개 그대로**(D17 결정 1 무변경). 별도 MCP 컨테이너 안은 격리 로직이 중복되고 D17 결정 1 을 바꿔야 해서 채택하지 않는다(1차안과 같음).
- 로컬 stdio 프록시는 만들지 않는다(웹·앱형 클라이언트에 소용없음).

### 6.2 SDK 마운트 주의 (조사로 확인된 것)
- 마운트: `Mount("/mcp", app=mcp.streamable_http_app())` + 접두를 그대로 쓰려면 `streamable_http_path="/"` [G2].
- **lifespan**: 마운트된 앱의 lifespan 은 실행되지 않는다 → 호스트 lifespan(`app/main.py:158` `_lifespan`, 브리핑 주기 작업이 이미 있음)에서 `async with mcp.session_manager.run()` 을 같이 열어야 한다. 빠지면 `RuntimeError: Task group is not initialized.` [G2].
- **allowed_hosts**: SDK 기본은 localhost 만 허용 → 실제 호스트명 뒤에서는 `TransportSecuritySettings(allowed_hosts=["relmemo.com"])` 를 넘기지 않으면 전부 **421** [G2][G3]. 운영 `SITE_ADDRESS` 는 `relmemo.com` 과 옛 `*.sslip.io` 를 함께 받지만(HANDOFF 기록), MCP 의 `resource` 가 `https://relmemo.com/mcp` 하나이므로 **MCP 허용 호스트는 `relmemo.com` 만**(sslip 주소로 오면 421 — 의도). 로컬 시험용 값은 설정으로(`MCP_ALLOWED_HOSTS`, 가칭).
- `@mcp.custom_route()` 는 인증되지 않는다 [G4] — OAuth·메타데이터 라우트는 SDK 쪽이 아니라 FastAPI 라우트로 둔다(로그인 계약 테스트의 열거 대상이 되게).
- **끝 슬래시(작성자 추정 — 확인 필요)**: Starlette `Mount("/mcp")` 는 보통 `/mcp/` 를 받고 `/mcp` 를 307 로 돌리는 경우가 있다. 클라이언트가 POST 를 307 로 다시 보내는지는 클라이언트마다 다를 수 있어, **`POST https://relmemo.com/mcp` 가 리디렉트 없이 401 을 돌려주는지**를 U3 시험·U6 스모크의 수용 기준으로 둔다.
- 마운트된 하위 앱은 FastAPI 의존성·예외 처리기(공통 404 매핑, `app/main.py`)를 공유하지 않는다 → 어댑터가 `PersonNotFound` 를 스스로 "없음" 결과로 바꾸고, DB 세션 수명도 `get_session` 과 같은 규약(요청마다 열고 닫기)으로 맞춘다.
- JSON 응답 전용 모드(스트림 없이 요청-응답) 옵션이 SDK v2 에 있는지·클라이언트가 그것을 받는지는 **미확인**. 무상태 규격에서도 서버가 SSE 로 응답할 수 있으므로 Caddy 쪽 보정(아래)을 같이 본다.

### 6.3 Caddy 경로 (`Caddyfile` — 지금은 `/api/*` 만 백엔드로, 나머지는 프론트 정적 파일)
- **문제**: `/.well-known/*` 와 `/mcp` 는 `/api` 아래가 아니어서 지금은 **프론트 정적 서빙(`try_files … /index.html`)으로 떨어진다** → 메타데이터 요청에 HTML 이 돌아가 발견이 실패한다 [조사 4절 배포 주의].
- **추가할 블록(접두를 떼지 않는 `handle`, `handle_path` 아님)**:
  - `handle /mcp /mcp/*` → `reverse_proxy backend:8000` (백엔드도 `/mcp` 경로 그대로)
  - `handle /.well-known/oauth-protected-resource* /.well-known/oauth-authorization-server*` → `reverse_proxy backend:8000`
  - 인가·토큰·등록은 `/api/oauth/*` 로 두므로 **기존 `/api/*` 블록이 그대로 처리**한다(새 블록 불필요). 이 때문에 루트에 `/authorize`·`/token` 을 두지 않는다.
  - `/.well-known/` 의 다른 경로(예: 인증서 발급용 `acme-challenge`)는 Caddy 가 스스로 처리하므로 건드리지 않게 매처를 위 두 이름으로 좁힌다.
- **스트리밍**: `encode gzip` 과 `reverse_proxy` 가 `text/event-stream` 응답을 늦출 수 있다(미확인) → `/mcp` 블록에 `flush_interval -1` 을 두고 gzip 에서 이벤트 스트림을 빼는 보정을 U6 스모크에서 실측으로 정한다.
- `tests/test_deploy_files.py` 의 Caddyfile 단언(서비스 3개·`handle_path` 블록)에 새 블록 단언을 더한다.

### 6.4 도메인
- `relmemo.com` — Cloudflare DNS A 레코드 → EC2, **Cloudflare 프록시 끔**(HANDOFF 기록: Caddy 자동 HTTPS 가 직접 인증서를 받게). 이 상태를 유지한다 — 프록시를 켜면 TLS 를 Cloudflare 가 끊어 Caddy 인증서·`Host`·Origin 검사 가정이 달라진다.
- Claude 는 표준 포트(443)만 받는다 [A1][A2] — 지금 구성과 맞다.
- `issuer`·`resource`·허용 목록·메타데이터의 주소는 **설정값 하나(`PUBLIC_BASE_URL`, 가칭 = `https://relmemo.com`)에서 만든다** — 하드코딩 0, 로컬 시험은 `http://localhost:…`.

### 7.3 SDK·규격에서 새로 확인된 것
- 요청별 Bearer 식별: `TokenVerifier.verify_token` → `AccessToken | None`, `AuthSettings(issuer_url, resource_server_url, required_scopes, validate_token_resource)`, 핸들러에서 `get_access_token()`. SDK 가 PRM 과 401 `WWW-Authenticate` 를 자동 제공 [G4].
- SDK 는 리소스 서버 절반만 — 로그인·동의 화면·토큰 발급은 안 해 준다. 내장 인가 서버는 새 서버에 쓰지 말 것 [G4].
- 읽기 전용 표시: `@mcp.tool(title=…, annotations=ToolAnnotations(read_only_hint=True, open_world_hint=False))` [G5].
- 클라이언트 등록: CIMD SHOULD, **DCR 은 2026-07-28 판에서 deprecated(하위 호환 MAY)**, 사전 등록 가능. 2026-07-28 판은 DCR 때 클라이언트에 `application_type` 지정을 요구 [F2][F4].
- 인가 응답 `iss`(RFC 9207) SHOULD, 다음 판 MUST 예고 [F2]. 리디렉트 정확 일치 MUST, 동의 화면 리디렉트 호스트 표시 MUST, 루프백 경고 SHOULD, 인가 서버 엔드포인트 HTTPS MUST, 접근 토큰 짧은 수명 SHOULD [F3].
- 토큰 엔드포인트: 무효 갱신 토큰은 `invalid_grant`, form-urlencoded 필수(Claude), refresh 30초·코드 교환 10초 한도(Claude) [A4].

### 7.4 아직 미확인 (01-plan U0 또는 U7 에서 닫는다)
1. 공식 SDK 의 PyPI 이름·고정 버전·라이선스, 현재 의존 고정본과의 충돌(7.1 #5·#7).
2. `AccessToken` 에 사용자 id 를 실을 칸이 있는지(없으면 ASGI 래퍼 — 4.3 (가) 5).
3. SDK 를 `/mcp` 아래 마운트할 때 PRM 경로가 어디에 생기는지(루트 직접 서빙 안을 기본으로 둠).
4. `/mcp` 끝 슬래시 307 여부(작성자 추정, 6.2).
5. JSON 응답 전용 모드 존재·클라이언트 수용, Caddy gzip·flush 영향(6.2·6.3).
6. 접근 로그에 헤더·폼 값이 남지 않는지(실측).
7. 불투명 토큰이 다섯 곳 모두에서 문제없는지(ChatGPT 문서는 JWT 전제로 서술 [C3]).
8. 브라우저 안 클라이언트가 토큰·등록 요청에 `Origin` 을 붙여 403 이 나는지(4.4).
9. ChatGPT 커스텀 MCP 의 요금제 조건 — 사용자 계정에서 메뉴가 보이는지 사용자가 확인.
10. Claude 앱 Request headers 의 개인 요금제 공개 여부(OAuth 로 가므로 영향 작음).
11. Gemini 쪽: Gemini CLI 를 개인 계정으로 계속 쓸 수 있는지(2026-06-18 중단 [E2]), Antigravity CLI 의 OAuth 지원, Gemini CLI 의 CIMD·PKCE·`resource` 전송, `readOnlyHint` 처리, Gemini 앱의 무인증·요금제 조건.
12. Codex CLI 콜백의 실제 포트 형식과 서버 OAuth 요구 세부.
13. Claude·ChatGPT 가 2026-07-28 무상태 프로토콜을 이미 쓰는지(SDK 가 둘 다 받으므로 영향 작음).
14. `/.well-known/*` 를 루트가 아닌 곳에 둘 때 Claude 외 네 곳의 동작(루트에 두므로 회피).
15. ChatGPT 가 도구 안에서 인증이 필요할 때 쓰는 `_meta["mcp/www_authenticate"]` 가 필요한지 — 모든 도구가 로그인 필수라 401 만으로 충분한지 [C3].
16. 인가 서버 엔드포인트 HTTPS MUST [F3] 아래에서 **로컬(`http://localhost`) OAuth 시험을 클라이언트가 받아 주는지** — 안 받으면 클라이언트 연결 시험은 공개 주소에서만 가능(9장 위험).
17. 외부 IdP 들의 DCR·`resource`·`iss` 지원 여부(채택하지 않아 조사하지 않음).

### 9.1 단계 (조사 보고서 4절 (다) 순서를 사용자 방향 "로그인 방식"에 맞춰 바꿈)

조사 보고서는 "① 개인 토큰으로 CLI 먼저 → ② OAuth 추가 → ③ Gemini 앱" 순서를 제안했다. 사용자 방향이 로그인 방식이므로 **개인 토큰 단계를 건너뛰고**, 대신 시험 전용 토큰 주입(제품 경로가 아니라 시험 픽스처)으로 리소스 서버를 먼저 검증한다.

| 단계 | 내용 | 대략 규모 | 붙는 클라이언트 |
|------|------|-----------|-----------------|
| 1. 리소스 서버 + 읽기 도구 | U0 사실 고정 · `/mcp` 마운트 · 도구 4개(읽기 전용 표시) · 토큰 검증 틀(시험에서는 가짜 토큰 저장소 주입) · PRM · 401 `WWW-Authenticate` · `MCP_ENABLED` | 백엔드 2~3단위(작음~중간) | 아직 없음(로그인이 없어 실제 클라이언트는 못 붙음). 시험·MCP Inspector 로 확인 |

| 5. (보류 권장) Gemini 앱 | 리디렉트 추가 · 그 클라이언트만 회전 안 함 | 1단위 | Gemini 앱 — **미국 거주 등 자격 조건 때문에 사용자가 시험 자체를 못 할 가능성이 큼** [E4] |

합계: 필수(1~3) 약 8~10단위 + 계획·계획 검증·완료 검토. 규모 순위로 보면 2 > 1 > 3.

### 9.2 11-18 시연 전에 가능한 최소 범위가 있는가 — **판단: 사용자가 정한 방식(로그인 연결)으로는 불가**

이유(정직하게):
1. **선행 작업이 남아 있다.** FIX-037 커밋 → P9b 시연 리허설·04-review·완성 확인 → `/devlog done` 이 먼저다(활성 패키지 하나 규칙). 그 뒤에야 CR 이행(동결·D19·카드) → 01-plan → verifier 계획 검증 → 구현이 시작된다.
2. **로그인 연결은 단계 1~3 전부가 있어야 처음으로 동작한다.** 인가 서버(단계 2)가 가장 크고, 보안 경로(리디렉트·PKCE·코드 재사용·회전·격리)는 변이 시험까지 해야 "완료"라고 쓸 수 있다(원칙8·verifier 규칙). 이것을 하루 안에, 그것도 평가 전날 밤에 끝낼 수 있다고 쓰면 거짓이다.
3. **운영 위험**: 평가 하루 전에 새 리비전(0005)과 로그인 없이 열린 새 엔드포인트 5개를 운영본에 올린다. 0004 때처럼 옛 해시로 되돌리기 어려운 성질이 생기고, 문제가 나면 평가 시연(채팅·카드·브리핑) 자체가 흔들린다. `MCP_ENABLED=0` 으로 끄는 길은 있지만 리비전은 남는다.
4. **실제 연결 시험이 사용자 손을 요구한다**(비밀번호 입력·Claude/ChatGPT 계정에서 커넥터 추가·요금제 확인). 시연 전날 밤에 다섯 곳을 다 붙여 볼 시간이 없다.

**그래도 무언가를 11-18 에 보이고 싶다면 — 축소안(권장하지 않음, 사용자 선택 N1)**:
- 내용: 단계 1 만, **운영 서버에 올리지 않고 로컬에서** Claude Code 한 곳에 붙여 "내 기억을 다른 AI 에서 꺼내 쓰는 모습"만 보인다. 로그인 대신 **로컬 전용 시험 토큰 1개**(환경변수로 특정 계정에 묶음, 운영에서는 스위치로 꺼짐)를 `--header` 로 넣는다 — 이것은 사용자가 정한 로그인 방식이 아니고, D18 격리 원칙("계정은 로그인에서만")과도 어긋나는 임시 장치라 **시연 뒤 반드시 지운다**.
- 규모: 2단위 + 계획 검증. 위험: FIX-037·P9b 마무리와 같은 날 같은 작업 트리를 다툰다(우선순위상 시연 품질 FIX 가 먼저), 계획 검증을 서두르면 후하게 판정될 위험. 발표에서는 "OAuth 로그인 연결은 설계 완료·구현 예정"으로 말하는 편이 사실에 맞다.

### 9.3 권장 순서
① FIX-037 커밋(시연 품질 — 최우선) → ② P9b 시연 리허설 · 04-review · 완성 확인 · 승격(P9-infra 04-review 함께) → ③ 11-18 평가 → ④ 이 CR 수용 결정(12장 남은 결정) · 공개 기간 결정(N7) → ⑤ `/devlog change CR-008` 문서 이행 → ⑥ `/devlog start P12-mcp` → 01-plan(11장 뼈대 + U0) → verifier → 단계 1 → 2 → 3(공개 서버에서 실제 연결) → (선택) 4. 이 CR 문서 자체는 지금 커밋해 두어도 제품 코드에 영향이 없다(`frozen` 을 걸지 않는다 — 걸면 진행 중인 FIX·P9b 를 막는다).
