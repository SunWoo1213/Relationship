## 1. 무엇이 바뀌는가

- 기획서(`docs/proposal.md`)에는 외부 AI 클라이언트 연동·MCP 문장이 **없다**. 2장 범위 표의 포함 칸에 새 항목이 하나 생긴다.
  - **새 문장(권장안 A-읽기 기준)**: "사용자는 자신의 관계 메모리를 **MCP 클라이언트(예: Claude 계열 앱)** 에서 **읽기 전용으로** 조회할 수 있다 — 인물 목록·이름 찾기·인물 카드·저장된 브리핑. 접근은 사용자가 발급한 계정별 토큰으로만 하며, 기록(쓰기)·브리핑 생성·원문 조회는 MCP 로 열지 않는다."
  - 제외 칸 변동 없음. 다만 **경계 문장 하나를 더한다**(2.4 원칙7): "MCP 로 내보내는 것은 기록된 사실 그 자체다. 외부 클라이언트의 LLM 이 그 사실로 무엇을 말하는지는 이 제품의 범위가 아니며, 제품은 상담·평가·A–B 관계를 만들어 내보내지 않는다."
- **"제품 속 에이전트의 툴 7종"과 "MCP 툴"은 다른 것이다.** MCP 툴은 외부 클라이언트가 부르는 **어댑터**이고, 툴 7종 시그니처(S3.2)·`tools_check` 7/7 은 바뀌지 않는다. MCP 툴이 툴 7종 등록표에 섞여 들어가지 않게 한다(8장 수용 기준).

### 2.2 권장 근거
1. **A-읽기만이 불변 원칙을 하나도 건드리지 않는다.** 쓰기 0 → 원칙1·2·3·4 의 병합 경로가 없고, 툴 7종(S3.2)·ER·임계치가 그대로다. B 는 툴 7종과 게이트를 고치므로 사실상 기획서 핵심 변경이다.
2. **새 코드가 가장 적다.** 조회 함수가 이미 있다 — `app/api/read.py` 의 `list_persons`(149행)·`get_person_card`(183행)·`list_briefings`(268행). 어댑터는 이 함수들을 그대로 부르고, 응답 모델에 원문 필드가 없다(`PersonCardOut`·`PersonListItemOut`·`BriefingRecordOut` — `app/api/schemas.py` 39·196·222·329행 주석, 원문을 싣는 모델은 `EventRawOut`·`FactSourceEventOut` 둘뿐).
3. **LLM 비용 0.** 위 세 함수와 `get_briefing` 툴(`app/tools/briefing.py:6` "LLM 호출이 없다")은 LLM 을 부르지 않는다. 브리핑 **생성**(`run_briefings`)과 채팅 조회 턴(D16, 답 생성에 LLM)만 비용이 든다 → 둘 다 MCP 로 열지 않는다.
4. A-쓰기는 가치가 크지만(밖에서 "오늘 김 부장이랑 점심" 이라고 말하면 기록됨), **외부 LLM 이 발화를 고쳐 쓰는 문제**와 **`ask_user` 왕복 문제**를 풀어야 한다(2.3). 읽기를 먼저 열어 인증·전송을 검증한 뒤 별도 단계로 판단하는 편이 안전하다.

### 2.3 A-쓰기를 나중에 열 경우의 설계 방향 (이번 CR 에서는 결정하지 않음 — 기록만)
- **같은 파이프라인만 탄다**: `record_utterance(text)` 는 `POST /chat` 과 **같은 함수 경로**(`build_chat_ctx` → `run_turn`, `app/agent/loop.py:1086`)를 부른다. `create_person`·`update_person`·`add_event` 같은 툴 7종을 MCP 툴로 **직접 노출하지 않는다** — 노출하면 외부 LLM 이 4단계(후보검색→규칙필터→LLM판정→ask_user)를 건너뛰고 인물을 만들거나 병합할 수 있다(원칙4 위반).
- **`ask_user` 는 MCP 클라이언트에 "대기 질문"으로 돌려준다**: 루프가 `pending_questions` 에 저장하고 `{question_id, status:"pending"}` 으로 끝나는 지금 모델(S3.4) 그대로, MCP 툴 결과에 `question_id`·질문·선택지(`options`)를 싣는다. 사용자가 답하면 `answer_question(question_id, option)` 툴 → `POST /answers/{id}` 와 같은 함수. **외부 LLM 이 사용자 대신 선택지를 골라 답하는 것을 막을 수 없다** — 그래서 ① 툴 설명에 "사용자에게 그대로 물어 보라" 를 적고 ② 대기 질문은 웹 채팅방(`chat:<user_id>`)에도 같은 질문으로 보이게 해 사용자가 웹에서 답할 수 있게 하는 안을 권장한다. MCP 규격의 "사용자에게 묻기" 기능(이름·지원 여부는 7장 확인 목록)을 쓰는 안은 클라이언트 지원이 확인된 뒤에.
- **원 발화 보존**: 외부 LLM 이 요약·재작성한 문장이 `raw_utterance` 로 저장된다. 이 한계는 01-plan 에 고지로 남긴다(원칙8 — 평가 데이터에는 섞지 않는다).
- **비용 상한**: 토큰마다 하루 기록 호출 N회(5장).

## 4. 인증 · 격리 (D18 과의 관계)

### 4.1 왜 쿠키를 못 쓰나
D18 결정 2 의 로그인은 같은 출처 **HttpOnly 쿠키**다. MCP 클라이언트(데스크톱 앱·CLI·원격 커넥터)는 브라우저가 아니므로 그 쿠키를 갖지 않는다. 그래서 `/mcp` 에는 **다른 자격**이 필요하다.

### 4.2 방식 비교

| 방식 | 내용 | 비용 | 위험·한계 | 판단 |
|------|------|------|-----------|------|
| **개인 액세스 토큰(PAT) (권장)** | 로그인한 사용자가 토큰을 발급(한 번만 보여 줌) → MCP 클라이언트 설정에 `Authorization: Bearer <토큰>` 으로 넣음. 서버는 sha256 해시만 저장(`auth_sessions.token_hash` 와 같은 방식 — `app/auth/sessions.py` `hash_token()` 재사용) | 테이블 1개(0005) + 검사 함수 + 발급·폐기 경로 | 사용자가 토큰을 복사·붙여넣기 해야 함. **클라이언트가 고정 Bearer 헤더를 지원해야 함** — 일부 원격 커넥터(웹 앱형)는 OAuth 만 받을 수 있음(7장 확인 #4) | 범위·일정·코드량 모두 최소. 기존 세션 해시 코드를 재사용 |
| OAuth 2.1 (MCP 규격의 인가 절) | 서버가 인가 서버 메타데이터·동적 클라이언트 등록·PKCE·동의 화면·토큰 엔드포인트를 제공 | 큼 — 인가 흐름 4~6 엔드포인트, 동의 화면, 리프레시 토큰, 메타데이터 문서, 시험 다수 | 직접 구현하면 보안 실수 여지가 큼. 외부 IdP 위임은 D18 결정 1("소셜 로그인 없음")과 충돌 | 웹 앱형 커넥터를 꼭 써야 할 때만. 이번 권장에서 제외 |
| 인증 없음 + 네트워크 제한 | 로컬에서만 열고 IP 로 막음 | 0 | 공개 EC2 에서는 불가(계정 격리가 사라짐) | 로컬 전용 시연에서만 고려, 그래도 비권장(격리 시험이 무의미해짐) |

### 4.3 PAT 설계 초안 (권장안)
- 테이블 `api_tokens(id, user_id FK users ON DELETE CASCADE, name, token_hash UNIQUE, scope, created_at, expires_at, last_used_at, revoked_at)` — 리비전 **0005**. 토큰 원문은 DB·로그·응답(발급 응답 1회 제외)·trace·증거에 0.
- 토큰 형식: `secrets.token_urlsafe(32)` 에 식별 접두(예: `rmk_`) — 접두는 실수로 붙여 넣은 토큰을 비밀 검사(`secret-guard` 패턴)·사용자가 알아보게 하려는 것. 패턴 추가는 결정 Q9.
- **범위(scope)**: 이번에는 `read` 하나만 만든다. 쓰기 툴이 생기면 `write` 를 따로 — 읽기 토큰으로 쓰기 툴 호출은 403.
- **만료**: 기본 30일(후보 7/30/90일, 결정 Q4). 공개 서버 종료(11-19)와 함께 모두 무효(인스턴스 삭제).
- **폐기**: 사용자가 즉시 폐기(`revoked_at`). 계정당 활성 토큰 상한(후보 3개).
- **사용자 결정 = 토큰이 가리키는 계정**: MCP 툴 입력에 `user_id` 인자가 **없다**. 모든 조회는 토큰의 `user_id` 로만(D18 결정 3 "user_id 는 로그인 계정에서만 온다"의 확장). 남의 `person_id` 는 기존과 같이 404(`PersonNotFound` — 존재 여부 비노출).
- **시도 제한**: 토큰은 256비트 무작위라 추측 공격은 사실상 불가 → 실패 시도 제한은 두지 않는다(P9b 결정 H 와 같은 근거). 대신 **토큰별 호출 상한**(분당 N회)은 비용이 아니라 남용 방지로 둘지 결정 Q7. 읽기는 LLM 0 이라 비용 상한은 불필요.
- **로그**: 토큰은 `Authorization` 헤더로만 받는다 — **쿼리 문자열(`?token=`)로 받지 않는다**(접근 로그·Caddy 로그·브라우저 기록에 남는 경로 차단). uvicorn 접근 로그는 헤더를 찍지 않는다(7장 확인 #9 로 실측). 예외 메시지·422 본문에 헤더 값이 실리지 않게(P9b U2 의 `/auth` 422 `input` 제거와 같은 방어).
- **비교**: 해시 조회 방식(평문 비교 없음). `find_user_by_token` 과 같은 경로를 쓰거나 같은 모양의 `find_user_by_api_token` 을 새로 만든다(registry 에 없는 함수 — 새 행).

### 4.4 Origin 검사 미들웨어(`app/auth/origin.py`)와의 관계
- 지금 미들웨어는 POST 에 `Origin` 이 **있으면** 호스트와 같을 때만 통과, **없으면 통과**(13행). MCP 클라이언트(비브라우저)는 보통 `Origin` 을 보내지 않으므로 그대로 통과한다.
- MCP 규격은 HTTP 전송 서버에 **Origin 검증(DNS 리바인딩 방어)** 을 요구하는 것으로 기억한다(7장 확인 #3). 우리 미들웨어가 이미 "다른 Origin → 403" 을 하므로 요구와 같은 방향이다. 브라우저형 MCP 클라이언트가 `Origin` 을 붙여 오면 403 이 날 수 있다 → 그 클라이언트를 쓸지(결정 Q6)에 따라 허용 목록이 필요할 수 있다.
- **`/mcp` 는 쿠키를 자격으로 받지 않는다(수용 기준)**. 쿠키를 받으면 브라우저의 교차 요청이 다시 위협이 되고(CSRF), Bearer 만 받으면 브라우저가 자동으로 붙이는 자격이 없어 그 위협이 사라진다. 반대로 기존 API 는 Bearer 를 받지 않는다(자격이 섞이지 않게).
