## 1. 무엇이 바뀌는가

- 기획서에는 로그인·사용자 계정에 대한 문장이 없다(2장 범위 표 포함/제외 어느 칸에도 없음). 구현은 `APP_USER_ID` 환경변수 하나(기본 `"local"`)로 **단일 사용자를 고정**했고, CR-005 결정 D(d)는 "접근 코드·로그인은 없음(발표용)" 으로 정했다(D17 6). 이것을 바꾼다:
  - **새 문장**: 서비스 안에서 **아이디 + 비밀번호로 가입·로그인**한다(비밀번호는 해시로만 저장, 소셜 로그인 없음). 인물·사건·사실·일정·브리핑·대기 질문·푸시 구독·대화 기록은 **로그인한 계정의 것만** 보이고 다룬다. **계정마다 채팅방은 하나**이고, 로그인하면 내 대화 기록이 이어서 보인다(채팅방 목록 없음).
  - 범위(2장 표): **포함 칸에 "계정(아이디·비밀번호 로그인)과 계정별 기억 격리" 가 더해진다.** 제외 칸은 그대로(고민 상담·A–B 관계·태그 필터·페르소나·음성·네이티브). 인물 간 관계(A–B)는 여전히 저장하지 않는다 — 계정은 "사용자" 이지 인물이 아니다.
- **CLAUDE.md 원칙5 "프론트 화면은 3개로 고정" 을 폐지한다**(사용자 2026-11-15 저녁 "원칙 5의 화면은 그정도만 있어야한다는 깨줘"). 번호는 유지한다(다른 문서가 "원칙5" 를 참조) — 새 문장: "핵심 화면은 채팅 / 인물 카드 / 브리핑이다. 화면 수를 고정하지 않는다 — 필요한 화면(로그인·가입 등)은 계획에서 근거와 함께 더한다(CR-006, 사용자 2026-11-15). UI에 시간을 쓰지 않는다." "UI에 시간을 쓰지 않는다" 는 사용자가 말하지 않았으므로 그대로 둔다.
- 기존 데이터는 **모두 비운다**(로컬 개발 DB 인물 12명, 배포본 시험 데이터 포함) — 빈 상태에서 시작한다.
- **채팅방 목록은 의도적으로 제외한다**(사용자 2026-11-15 저녁 확인 원문: "맞아 이렇게 진행해줘 채팅방 목록은 일부러 넣지 않아 우리는 관계를 기억하는 것이 메인이니까"). 이 서비스의 기억 단위는 대화방이 아니라 **인물**이다 — 대화가 여러 방으로 갈라지면 같은 인물의 기억이 방마다 흩어진 것처럼 보이고, 인물 카드가 그 역할을 이미 한다. CLAUDE.md 원칙7 제외 목록에 한 줄로 더한다.

### 변경 항목 2 — 브리핑 달력 보기 (사용자 2026-11-15 저녁)
- 원문: "또 추가하고 싶은 기능은 브리핑 날짜를 달력형태로도 볼 수 있게 기능을 추가해줘"
- 해석(메인 세션이 사용자에게 알림): 브리핑 화면에 **달력 보기**를 더한다 — 월 달력에 일정(브리핑 예정일)과 이미 만들어진 브리핑이 날짜별로 표시되고, 날짜를 누르면 그날의 일정·브리핑이 보인다. **기존 목록 보기는 유지**("달력형태로**도**").
- 이것은 화면 요소·조회 API 추가라 원칙5 폐지와 같은 CR 에서 다룬다. 범위 표(2장): 포함 칸 "만남 전 브리핑 생성" 의 보기 방식 확장 — 제외 칸 변동 없음.
- 원칙 대조: **원칙7 경계 문장**(브리핑의 "제안" 은 기록된 사실에서 도출되는 한 줄로 한정) — 달력은 이미 만들어진 브리핑과 일정을 **날짜로 배치해 보여 줄 뿐** 새 생성·새 문장이 없다(LLM 호출 0) → 충돌 없음. **원칙9** — 읽기 전용 조회라 판정이 없고 `agent_traces` 를 쓰지 않는다(기존 `GET /briefings` 와 같은 규약) → 충돌 없음. **원칙1~4·툴 7종** 무관.
- API 판단: 지금 있는 `GET /briefings`(`app/api/read.py:267` `list_briefings`)는 **compose trace 가 있는 일정만**, `scheduled_at >= now - BRIEFINGS_LOOKBACK_DAYS` 창·상한 `BRIEFINGS_LIMIT` 으로 돌려준다 → 브리핑이 아직 없는 일정(예정일)과 임의의 달(과거·먼 미래)을 못 보인다. 일정 목록을 주는 엔드포인트는 없다(라우트 12개 중 0). 그래서 **월 범위 일정 조회 엔드포인트 1개가 새로 필요**하다(일정마다 브리핑 존재 여부·최신 브리핑 trace id 포함). 스키마 무변경(`schedules` 와 기존 trace 로 충분).
- 순서: **로그인 패키지(`P9b-auth`)가 먼저**(평가 전 필수). 달력 조회는 로그인 사용자 기준이어야 하므로 그 위에 올라간다 → 별도 패키지 **`P9c-briefing-calendar`**(backlog·INDEX 에 항목). 한 번에 활성 패키지는 하나라 P9b 완료(04-review) 뒤 활성화한다. **평가 전에 못 들어가면 배포본은 로그인만 반영된 상태**(브리핑 화면은 지금의 목록 보기 그대로)로 시연하고, 달력은 평가 뒤 이어간다.
