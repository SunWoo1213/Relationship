## 1. 무엇이 바뀌는가

- 기획서에는 계정 문장이 없고(CR-006 1절), CR-006 · D18 결정 1 이 "아이디 + 비밀번호로 가입" 을 정했다. 지금 가입은 아이디(`^[a-z0-9_]{3,20}$`, 소문자 정규화)와 비밀번호(8~128자)만 받고, 사이드바에 "<아이디> · 로그아웃" 을 보인다(`web/src/components/AppShell.tsx:29-53`). 아이디 중복은 **가입 제출 때** 409 `username_taken` 으로만 알린다(`app/auth/routes.py:108-114`). 이것을 바꾼다:
  - **새 문장 ①**: 가입할 때 **닉네임을 필수로** 입력받는다. 닉네임은 **사용자 자신의 화면 표시 이름**이다 — 가입·로그인·내 정보 응답과 사이드바에 보인다. 로그인은 여전히 아이디로 한다.
  - **새 문장 ②**: 아이디·닉네임은 **중복검사**를 한다 — (i) 가입 제출 때 서버가 409 로 거부(`username_taken` / `nickname_taken`)하고 (ii) 가입 화면에서 **제출 전에** 로그인 없이 중복 여부를 조회한다(조회 API 1개 + 칸마다 "중복 확인"). 최종 판정은 DB UNIQUE 와 가입 시 409 이고, 조회는 참고용이다(조회와 가입 사이에 다른 사람이 같은 값을 쓸 수 있다).
  - 해석 근거: "중복검사를 하도록" 을 (i) 만으로 읽으면 아이디는 이미 그렇게 하고 있어 바뀌는 것이 없다 → 사용자가 바라는 것은 (ii) 를 포함한다고 본다(메인 위임문과 같은 해석).
- 범위(2장 표): 포함 칸의 "계정(아이디·비밀번호 로그인)과 계정별 기억 격리"(CR-006) 안에서 **가입 입력 항목이 하나 늘 뿐**이다. 제외 칸 변동 없음 — 닉네임은 **사람(인물)이 아니라 계정의 표시 이름**이라 인물 간(A–B) 관계·고민 상담과 무관하다.
- 기존 계정(운영 DB 의 `test` 와 반영 전에 생길 계정)은 **지우지 않는다** — 리비전 0004 가 닉네임을 그 계정의 아이디 값으로 채운다(CR-006 의 0003 과 달리 데이터를 비우지 않는다).
