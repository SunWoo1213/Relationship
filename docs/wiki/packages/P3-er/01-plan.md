## 목표

`docs/resolution-plan.md` §5 구현 순서 표의 "P3 | ER 4단계 + 확신도 + trace | backend-agent | P2 | 승진 회귀 테스트 통과, trace에 breakdown 존재" 한 줄을 실현한다. 기획서 4장의 "같은 사람이 팀장 → 김팀장 → 그 사람 → 부장님(승진)으로 등장해도 하나로 묶는다"를, P2 가 만든 툴 위에 **엔티티 해석 4단계 파이프라인**(후보 검색 → 규칙 필터 → LLM 판정 → 확신도 분기)으로 얹는다. 이 패키지는 **CLAUDE.md 불변 원칙 1~4 의 뿌리를 코드로 만드는 자리**다 — 원칙1(오병합 ≫ 미검출, 확신도 미달이면 절대 자동 병합하지 않고 `ask_user`), 원칙2(임계치 두 개 `T_merge`/`T_new`, 구간별 `kind`), 원칙3(확신도 = `0.5·s_llm + 0.3·s_emb + 0.2·s_rule`, `s_llm` 은 **구조화 출력으로 자기보고한 점수이며 로그 확률이 아니다**), 원칙4(LLM 단일 호출 금지 — 4단계 전부 존재)를 각각 실행 가능한 코드와 회귀 테스트로 고정한다. 여기서 내리는 모든 설계 결정의 근거는 그 네 원칙이며, 원칙8(재현 가능)·원칙9(모든 판정에 근거)이 검증 방법을 규정한다. 닫는 검증은 **R4**("LLM 출력 확률"은 Claude API에 없음 → D3 의 3신호 자기보고 구조를 코드가 갖는다)와 **R9**(인물당 임베딩 1개 → 별칭 단위 top-K → 인물별 max 를 실제 임베딩 공급자로 돌린다, D5). 이 패키지가 끝나면 P4-pilot-eval 은 **`agent_traces` 만 읽어 confidence 를 재계산하고 보정표·트레이드오프 곡선을 만들 수 있어야** 한다(S3.7).

    - (a) **승진 "팀장 → 부장님" 연결**: 픽스처는 저장 인물 `{display_name:"김민수", aliases:["팀장","김팀장"], relation_tag:"직장", hierarchy:"동"}`, mention `"부장님"` — 호칭 사전이 `"부장님" → {group:"직장", hierarchy:"상"}` 을 유도하므로(결정 10) 유도 위계 `상` 과 저장 위계 `동` 이 **불일치 → 엄격 필터 탈락**, 두 값은 1칸 차이라 `hierarchy_adjacent` → **완화 재평가 1회로 통과**(테스트가 `decision.relaxed_retry is True` 를 단언한다) → `grouped_embedder` 가 `"팀장"`·`"김팀장"`·`"부장님"` 을 같은 군으로 묶어 `s_emb` 를 높게 주고 `FakeJudge` 가 그 인물을 `matched_person_id` 로 높은 `s_llm` 과 함께 고른다 → `confidence ≥ T_merge` → `apply_resolution` 이 `update_person(new_alias="부장님")` 로 별칭 누적, **`display_name` 은 바꾸지 않는다**(결정 3-b) → trace `relaxed_retry=true`, 해당 후보 `relaxed_pass=true`, `rule_passed` 는 위계 검사를 미통과로 센다(결정 2). 구체 수치는 결정 9.
    - (b) **"팀장" vs "이모" 배제**: 관계 태그 그룹 불일치로 규칙 필터 탈락(`excluded_by="relation_tag_conflict"`) → **규칙 통과 후보 0** → LLM 생략(`llm.skipped=true`) → `new_person` 구간(`forced_reason="no_candidates"`) → `ask_user(kind="new_person")` 페이로드 생성. 후보 목록은 trace 에 `passed_rules=false` 로 남는다(배제도 근거다 — 원칙9).
    - (c) **동명이인 분리**: 같은 별칭을 가진 인물 2명 → 둘 다 규칙 통과 → `FakeJudge` 가 **둘 중 하나를 `matched_person_id` 로 고르되 `s_llm` 을 중간값으로 자기보고**(단일 `Judgement` 모델 — 후보별 점수 배열이 아니다) → 그 후보 하나에 귀속한 `confidence` 가 `[T_new, T_merge)` → `ask_user(kind="identity")`, `options` 에 두 인물 표시 이름, `context.candidate_ids` 에 이름→id 매핑. 두 인물의 후보별 `s_emb`·`s_rule` 은 `candidates[]` 에 그대로 남는다.
  - **경계값·산식 테스트**: `confidence` 가 정확히 `T_merge`·`T_new` 일 때의 구간(`≥` 는 merge, `≥ T_new` 는 identity), **부동소수 오차 규약**(`0.5·0.2 + 0.2·1 = 0.30000000000000004` 처럼 산식이 경계를 아슬하게 넘거나 못 넘는 조합을 테스트에 명시하고, 비교는 `round(·, 6)`(또는 `math.isclose(abs_tol=1e-9)`)로 한다는 것을 단언), 가중치 합 1.0 검증, `s_rule` 분모 0 처리(결정 2), `s_emb` 가 `[0,1]` 밖이면 클램프, `T_new > T_merge` 설정 거부.

## 리스크 · 미결

- **결정 1 — 4단계를 모듈 4개로 쪼갠다(원칙4의 구조적 강제).** `app/er/{candidates,rules,judge,confidence}.py` 가 각각 1~4단계이고 `pipeline.py` 만 그것을 순서대로 부른다. 한 파일에 다 쓰면 "LLM 한 번 부르고 끝" 으로 되돌아가기 쉽고(원칙4 가 금지하는 것이 정확히 그것이다), 단계별 단위 테스트·단계별 trace 필드가 자연스럽게 나오지 않는다. **P3/P5 경계**: `resolve()` 는 "이 `mention` 이 누구인가"만 답한다. 발화에서 `mention` 을 뽑는 것(LLM 추출), `resolve` 를 언제 몇 번 부를지, 결과로 `add_event`·`add_schedule` 을 어떻게 잇는지, 답이 온 뒤 재개는 전부 P5-loop 이다. `hints` 는 호출자가 줄 수도 있고(P5 가 문맥에서 아는 경우) 비워 두면 P3 가 호칭 사전에서 유도한다.
- **결정 2 — `s_rule` 은 "평가 가능한 검사"만 분모에 넣고, 평가할 수 없으면 점수를 주지 않는다.** 검사 3종(호칭 사전 호환·위계 일치·관계 태그 일치) 중 정보가 없어 판단할 수 없는 검사는 분모에서 뺀다. 분모가 0이면 `s_rule = 0.0`(0.5 같은 중립값을 주지 않는다). 근거: 원칙1의 비대칭 비용과 P2 가 이미 채택한 규약("긍정인지 알 수 없음 = 긍정 아님", `_require_confirmation` 의 `not_affirmative` 기본 거부)의 연장이다 — 모르면 낮게 준다. 부작용으로 힌트가 전혀 없는 발화에서는 최대 confidence 가 `0.5+0.3 = 0.8` 이 되어 `T_merge` 를 겨우 만족한다. 이는 의도된 보수성이며, P4 곡선이 `T_merge` 를 조정할 때 이 상한을 함께 본다. trace `confidence_breakdown` 에 `rule_checked`·`rule_passed` 를 함께 남겨 P4 가 다른 분모 규칙으로 재계산해 볼 수 있게 한다.
  - **배제 규칙**: 규칙 필터는 **모순이 확인될 때만** 후보를 배제한다 — (i) 호칭 사전이 서로 다른 관계 그룹으로 단정하는 경우("팀장"=직장 vs 후보=가족 "이모"), (ii) **유도·힌트 위계와 저장 위계가 불일치하는 경우** — 여기서 **엄격 단계는 인접 여부와 무관하게 탈락**시키고, 인접(1칸) 불일치는 **완화 단계에서만** 통과로 본다(S3.3 "위계 제약을 인접 위계까지 허용으로 완화", 두 칸 상↔하 차이는 완화에서도 탈락). 정보가 없어서 확인되지 않는 것은 배제 사유가 아니며 `s_rule` 분모에서도 빠진다(미검출을 늘리지 않으면서 오병합만 막는다). 배제된 후보도 trace `candidates[]` 에 `passed_rules=false`·`excluded_by` 와 함께 남긴다(원칙9 — 배제도 판정이다).
  - **완화 통과의 계상(F-acc9b9)**: 완화 재평가로 통과한 위계 검사는 `rule_checked` 에는 세되 `rule_passed` 에는 **세지 않는다** — 즉 완화된 후보의 `s_rule` 은 위계 검사를 실패로 계산한 값이 되어 confidence 가 낮아진다. 완화가 임계치 통과를 도와주면 안 되기 때문이다(원칙1). 통과 사실 자체는 후보의 `relaxed_pass=true` 로 남겨 P4 가 "완화 통과를 통과로 세는 규칙"으로 재계산·비교할 수 있게 한다(원칙8).
- **결정 3 — LLM 판정은 Anthropic SDK + 강제 tool_use 구조화 출력, 실패는 안전 강등.**
  - (a) **왜 tool_use 인가**: Claude API 에는 임베딩도 로그 확률도 없고(D4·D3), 자유 텍스트 JSON 은 파싱 실패가 확률적으로 남는다. 도구 스키마를 강제(`tool_choice` 로 특정 도구 지정)하면 `{matched_person_id: integer|null, s_llm: number, reason: string}` 이 타입까지 강제된다. **`s_llm` 이 자기보고 점수라는 사실을 숨기지 않는다** — `Judgement.s_llm` 주석, `judge.py` docstring, trace `llm.self_reported=true` 세 곳에 명시한다(R4 를 코드로 닫는 방식). 파싱 후에도 `0 ≤ s_llm ≤ 1`·`matched_person_id ∈ 후보 id 집합 ∪ {null}` 을 다시 검증한다(모델이 존재하지 않는 id 를 지어내면 판정 무효).
  - (b) **모델 id**: env `ANTHROPIC_MODEL`(기본 `claude-sonnet-5`, `.env.example` 에 이미 있음). 실제 호출 가능한 모델 id 문자열과 SDK 의 tool_choice·usage 필드 이름은 **구현 시 `claude-api` 스킬로 확인**한다(계획 시점에 추정으로 못 박지 않는다). 확인 결과가 다르면 우회 구현하지 말고 03-log 에 적고 값을 고친다.
  - (c) **실패 시 분기**: 타임아웃(기본 20초)·5xx·429 는 **1회만** 재시도(비용·시간, 재시도 남발 금지). 그래도 실패하거나 스키마·범위 검증에 걸리면 `JudgeUnavailable` → `s_llm = 0.0` + **후보가 있으면 `band` 를 `identity` 로 강제 강등**(merge 도 new_person 도 아님), 후보가 없으면 `new_person`. 예외를 위로 던지는 대안은 택하지 않았다 — 그러면 P5 루프가 턴을 통째로 실패시키고 사용자는 아무 답도 못 받는데, 원칙1이 요구하는 안전한 실패는 "묻는 것"이지 "죽는 것"이 아니다. trace `llm.error` 에 예외 유형만 남긴다(응답 본문·키 금지).
  - (d) **키·비밀**: SDK 가 `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` 를 환경변수에서 읽게 두고 코드가 키 문자열을 변수로 옮기지 않는다. 프롬프트·trace·evidence 어디에도 키가 없어야 한다(security.md §1, 04-review 가 grep 으로 확인할 수 있게).
- **결정 3-b — 자동 연결(merge) 구간에서 `display_name` 을 바꾸지 않는다.** S3.3·스킬은 "확인되면 `update_person` 으로 별칭 누적 + `display_name` 갱신" 이라고 쓴다 — 전제가 **확인**이다. P2 는 D6 에 따라 `update_person(display_name=…)` 에 answered 질문을 요구하며(`_require_confirmation`), merge 구간에는 질문이 없다. 따라서 merge 는 **별칭 누적까지**만 하고, 표시 이름 갱신은 `identity` 질문에 사용자가 답한 뒤(P5 재개 경로)에만 일어난다. `Resolution.suggested_display_name` 에 후보 이름을 실어 P5 가 쓰게 한다. 근거: 인물 카드의 이름이 확인 없이 바뀌는 것은 사용자가 되돌리기 어려운 가시적 변화이고, 원칙1의 비대칭 비용은 "확신이 없으면 사람에게 묻는다" 쪽으로 기운다. **사용자 확인이 필요한 항목**(D6 문구와 이 해석이 어긋나 보일 수 있다).
- **결정 3-c — confidence 는 `matched_person_id` 후보 하나에 귀속하고, `null` 이면 병합하지 않는다(F-138665, 사용자 결정 2026-09-06 00:10).**
  - (a) **귀속**: 3단계 LLM 은 규칙 통과 후보 중 하나(`matched_person_id`)를 고르거나 `null` 을 준다(S3.3 의 단일 `Judgement` 모델 그대로 — 후보별 점수 배열로 바꾸지 않는다). 4단계의 `s_emb`·`s_rule` 은 **그 후보의 값**이다. "최고 유사도 후보의 `s_emb`" 로 계산하면 LLM 이 고른 B 를 A 의 유사도로 병합하는 셈이라 정확히 오병합 방향으로 값이 부풀고(원칙1), D3 의 "`s_emb`: 후보 검색 코사인 유사도"가 어느 후보 것인지도 불분명해진다. `confidence_breakdown.matched_person_id` 로 귀속을 드러내고, 후보별 `s_emb`·`s_rule` 은 `candidates[]` 에 남겨 P4 가 다른 귀속 규칙(예: 최고 유사도 기준)으로 **재계산**할 수 있게 한다(원칙8·S3.7).
  - (b) **`null` 분기**: `matched_person_id=null` 은 "아무도 아님" 이므로 병합 대상이 없다. `s_llm=0` 으로 취급하고 **merge 를 금지**한다 — 규칙 통과 후보가 하나라도 있으면 `identity`(사람에게 "이 사람 맞나요"를 묻는다), 없으면 `new_person`. 귀속 후보가 없으므로 `confidence_breakdown` 의 `s_emb`·`s_rule` 은 0, `confidence` 는 0 이고 `band_by_threshold` 는 그 값이 주는 구간(`new_person`), 최종 `band` 는 강제값이며 `forced_reason="no_matched"` 로 구분한다. 산식만 두면 `s_llm` 이 높을 때 `≥ T_merge` 가 나와도 병합할 대상이 없는 모순이 생긴다.
  - (c) **카드 영향 없음**: (a)(b) 는 D3·D10·S3.3 의 문장을 바꾸지 않는다(S3.3 의 `{matched_person_id | null, s_llm, reason}` 구조를 그대로 쓴다). 02-plan-verify 가 적은 대안 (B)(후보별 confidence 배열)는 S3.3 카드 갱신이 필요하므로 채택하지 않았다.
- **결정 4 — 판정과 실행을 분리한다(`resolve` 는 부수효과 없음, `apply_resolution` 이 실행).** 이유: (i) P4 가 `agent_traces` 만으로 판정을 재현·재계산해야 하는데(S3.7) 판정 함수가 DB 를 바꾸면 평가 실행 자체가 데이터를 오염시킨다(원칙8); (ii) trace 가 "무엇을 판정했는가"와 "무엇을 실행했는가"로 깨끗이 나뉜다(원칙9); (iii) 오병합 사고가 났을 때 실행 지점이 한 곳이라 막기 쉽다(원칙1). `ask_user` 페이로드(질문 문구·`options`·`context`·`AFFIRMATIVE_KEY`)도 **P3 가 만들되 저장은 `apply_resolution` 에서** 한다. `identity` 질문의 `options` 는 후보 표시 이름 최대 3개 + "아니요, 다른 사람이에요", `affirmative_options` 는 후보 이름들, `context` 에 `{mention, utterance, candidate_ids{이름→id}, confidence_breakdown}` 을 넣는다 — P2 04-review §7 이 남긴 **"질문이 특정 인물에 묶이지 않는다"** 는 구멍을 P5 가 이 `candidate_ids` 로 메울 수 있게 하는 것이 목적이다(S3.4 "context 에는 재개에 필요한 것만" — 전체 대화 이력·비밀 금지).
  - **trace 행의 갱신 주체(F-f43a9d, 사용자 결정 2026-09-06 00:10)**: `resolve()` 는 `er_resolve` 행을 쓰되 `decision.applied=false`·`decision.pending_question_id=null`·`decision.applied_at=null` 로 두고, **`apply_resolution()` 이 같은 행의 그 세 필드만 갱신**한다(`Resolution.trace_id` 로 행을 찾는다 — 그래서 `Resolution` 이 `trace_id` 를 들고 있어야 한다). 갱신은 `output` JSONB 의 **부분 갱신**이며 전체 재기록을 하지 않는다 — `candidates[]`·`confidence_breakdown`·`llm`·`band`·`band_by_threshold`·`forced_reason` 같은 **판정 필드는 불변**이고, 무엇이 언제 실행됐는지는 `applied_at` 이 드러낸다(원칙9 — 판정 근거는 남고 실행 사실만 덧붙는다). 이렇게 하면 결정 5 의 "판정 1회 = 행 1개" 계약이 유지된다. 대안 (B)(두 필드를 반환값으로만 두고 trace 에서 제거)는 `agent-observability` 체크리스트 "`ask_user` 호출에 `pending_question_id` 가 연결되는가"를 join 없이는 못 채우고, 대안 (C)(`step="er_apply"` 행 추가)는 행 1개 계약을 깨서 P4 의 단순 조회를 잃는다. 실행하지 않은 판정(P4 재계산·평가 실행)은 `applied=false`·`applied_at=null` 로 남아 구분된다.

P4 의 `ask_user_rate_by_kind` 와 완화 발동 비율로 관찰하고, 과도하면 P5 가 사용자 프로필(직급)을 `hints` 로 넘기는 방식을 검토한다 — 이 패키지는 `hints` 우선 규칙으로 인터페이스만 열어 둔다.
- **리스크 — 호칭 사전의 범위와 오탐.** 초기 표는 작게 간다(직장 직급 10여 개·가족 호칭 15개 내외·연인/친구/지인 소수·대명사 4개). "사장님"처럼 직장(대표)과 지인(가게 주인) 양쪽에 걸리는 항목은 **모호로 표시해 어느 쪽으로도 배제하지 않는다**(모호를 배제 근거로 쓰지 않는다 — 결정 2). 표 확장은 추측이 아니라 P4 실패 케이스에서만 한다(원칙8).
- **리스크 — 실 DB 테스트가 조용히 skip 된다.** P2 04-review 관찰 O4 와 같은 문제(`verify-impl.sh` 가 `POSTGRES_PORT`·`-rs` 없이 pytest 를 부른다). 대응: 판정 방법 표의 모든 pytest 를 `POSTGRES_PORT=5433 … -rs` 로 돌려 skip 0 을 evidence 에 남기고, 04-review 는 "회귀 3종이 실제로 실행됐다"는 줄을 요구한다. 수용 기준 후반부(trace)도 DB 가 필요하므로 이 항목이 곧 수용 기준의 조건이다.
- **리스크 — `openai`·`anthropic` 의존성 추가.** 지금까지 `requirements.txt` 는 런타임 호출자가 있는 것만 담았다(P2 결정 10). 이제 둘 다 호출자가 생기므로 설치본 버전으로 핀 고정하고 `pip freeze` 를 evidence 로 남긴다. 두 SDK 모두 **지연 import**(모듈 최상단이 아니라 함수 안)로 두어, 키·SDK 없이도 `app` 임포트와 DB 없는 테스트가 그대로 돌게 한다.
- **미결 1 — `agent_traces.tool_name = "er"` 규약(P1·P2 인계).** 이 계획이 정한 값이지만 P4(집계 쿼리)와 P5(툴 스키마 생성기)가 같은 상수를 쓰는 것이 조건이다. 두 패키지 계획에 인계한다. **사용자 확인 권장**(값 자체는 되돌리기 쉬우나 trace 데이터가 쌓인 뒤에는 마이그레이션이 필요하다).
- **미결 2 — 승진 시 `display_name`(결정 3-b).** merge 구간에서 이름을 안 바꾸면 데모의 "김부장 회의" 문구(D6)는 사용자가 `identity` 질문에 답한 경로에서만 나온다. 데모 시나리오상 그 편이 오히려 "에이전트가 확인하고 반영했다"를 보여 주지만, **D6 카드 문구와 다르게 읽힐 수 있어 사용자 확인이 필요하다.** 확인 결과가 "merge 에서도 갱신"이면 P2 의 `_require_confirmation` 을 건드려야 하므로 별도 FIX 가 필요하다(이 계획 범위 밖).
- **미결 3 — `pending_questions` 에 인물 바인딩·1회 소비가 없다**(P2 04-review §7). P3 는 `context.candidate_ids` 를 채우는 것까지 하고, "answered 질문 하나로 다른 인물을 만들 수 있다"는 구멍은 P5 가 막는다. P3 의 회귀 테스트는 이 구멍을 **가정하지 않는다**(질문을 만들기만 하고 답 처리는 하지 않는다).
- **미결 4 — 대명사("그 사람"/"걔") 처리 깊이.** 호칭 사전은 대명사를 "정보 없음"으로 분류할 뿐, 직전 발화의 지시 대상을 추적하지 않는다(대화 상태 추적은 P5 루프의 맥락 관리). 그 결과 대명사 발화는 `s_rule=0` 이 되기 쉽고 `identity` 질문 비율이 올라간다 — P4 의 `ask_user_rate_by_kind` 로 관찰하고, 과도하면 P5 에서 직전 turn 의 인물을 `hints` 로 넘기는 방식을 검토한다(이 패키지는 인터페이스만 열어 둔다).
- **미결 5 — `er_smoke.py` 실행은 키가 필요하다.** 에이전트는 `.env` 를 읽지 않으므로 스모크 실행 자체를 사용자가 하거나, 사용자가 셸에 키를 넣은 상태에서 명령을 실행해 달라고 요청한다(security.md §6). 키가 없으면 U8 의 스모크 증거는 "키 없음 종료(코드 2)" 출력으로 대체하고 04-review 에 그 사실을 적는다 — **없는 증거를 있는 것처럼 쓰지 않는다**(원칙8). **그 결과 R4 의 닫힘 표기를 둘로 나눈다(F-5aaf28)**: (i) *구조화 출력 스키마·파싱·범위 검증* 은 `FakeJudge`/스텁 클라이언트 테스트로 **검증 완료**, (ii) *실 API 호출* 은 `er_smoke` evidence 가 있을 때만 "실호출 검증"이며, 없으면 04-review 에 **"실호출 미검증"** 을 그대로 적는다. R4 자체(로그 확률을 쓰지 않고 자기보고 3신호 구조를 갖는다)는 (i) 만으로 닫히지만, "실제 API 가 그 스키마를 지킨다"는 (ii) 없이는 주장하지 않는다.
- **기계 검증에서 예상되는 WARN(FAIL 아님).** `verify-plan.sh` 7번(registry 중복)은 산출물 목록의 `requirements.txt`·`app/settings.py`·`app/embedding.py`·`app/tools/context.py`·`tests/conftest.py`·`tests/test_tools_context.py`·`scripts/embed_pilot.py`·`README.md` 에 대해 "다른 패키지로 이미 있음" WARN 을 낸다. 여덟 파일 모두 **새 행을 만들지 않고 기존 행의 비고만 갱신**하는 것이 계획이므로 의도된 결과다(P1·P2 와 같은 처리). `app/er/*`·`scripts/backfill_embeddings.py`·`scripts/er_smoke.py`·신규 테스트 7개는 registry 에 없으므로 신규 행이다.
- **보안.** 키는 `os.environ` 으로만, `.env` 는 읽지 않는다(§1). 프롬프트·`agent_traces.input/output`·`pending_questions.context`·evidence 에 키·헤더·전체 대화 이력을 넣지 않는다(§1·§5, S3.4). `utterance` 는 trace 에 들어가되 `TRACE_MAX_STRING` 으로 절단된다. 모든 인물 조회는 `user_id` 조건을 통과한 `search_person`/`update_person` 을 재사용하므로 격리가 유지된다(§5). 셸에서 `DROP`/`TRUNCATE` 를 쓰지 않고 테스트 정리는 rollback 으로만 한다(§4). 백필 스크립트는 삭제하지 않고 `NULL` 인 행만 채운다.
