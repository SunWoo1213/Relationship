  1. **한 턴에 이벤트가 여러 건이면 어디에 잇는가 -- 그 인물의 이번 턴 이벤트 전부에 잇는다.** 같은 턴 안의 이벤트는 모두 같은 발화에서 나왔을 가능성이 있어 어느 하나만 골라 근거로 삼을 객관적 기준이 없고(무작위로 하나만 고르면 "왜 이 이벤트가 근거인가"를 설명할 수 없다), R8 의 목적("이 사실이 어느 대화에서 나왔나")은 근거 후보가 여럿이어도 전부 원문으로 거슬러 갈 수 있으면 충족된다. 실무상 한 턴에 같은 인물의 이벤트가 2건 이상인 경우는 드물어(발화 하나가 보통 이벤트 하나로 이어진다) 카드가 시끄러워질 위험은 작다고 판단했다(근거는 `app/memory/direct_facts.py` 모듈 docstring "한 턴에 이벤트가 여러 건이면" 절).
  2. **`unlinked` 를 어느 trace 의 어디에 적는가 -- `memory_promote` step 을 재사용하고 `output.source="direct"` 로 LLM 승격 행과 구분한다.** 새 step 을 만들지 말라는 지시(01-plan 73행)에 따라 `memory_pattern`/`memory_promote`/`memory_error` 셋 중 골라야 했다. `memory_pattern` 은 `window`/`counts` 등 패턴 전용 스키마가 이미 고정돼 있고 원칙6 이 지키는 "패턴은 LLM/승격 이력을 모른다"는 모듈 경계(U5 가 이미 같은 이유로 `memory_pattern` 대신 `memory_promote` 를 선택한 전례, `app/memory/promote.py` 모듈 docstring "★ 세 판단")와 부딪힌다. `memory_promote` 는 "person_facts 의 upsert + fact_sources 근거"라는 목적이 정확히 같아 자연스럽게 맞고, `PromotedFact`/`RejectedFact` 와 병렬로 `DirectFactLink` 를 둘 수 있다. **가장 큰 위험은 `app/memory/promote.py::_considered_event_ids()` 가 `step='memory_promote'` 인 모든 행의 `considered_event_ids` 를 누적 조회해 "이미 본 이벤트" 로 삼는다는 것**이다 -- `DirectFactLinkResult.to_dict()` 는 이 키를 **절대 내지 않는다**(U5 ★3 이 막은 것과 같은 종류의 조용한 데이터 유실을 막기 위해, `.get("considered_event_ids") or []` 가 안전하게 빈 리스트로 처리한다는 것을 `app/memory/types.py::DirectFactLinkResult` docstring 에 근거로 남겼다). `test_direct_fact_link_does_not_disturb_promotion_links_in_same_turn` 이 이 두 경로가 같은 턴에 섞여도 서로의 링크를 건드리지 않음을 직접 검증한다.
  3. **`pattern:` 접두 방어 -- 한다.** U3 가 `update_person` 안에서 이미 거부해 실행 성공 호출에는 나타날 수 없는 불변식이지만, `_fact_keys_from_args()`(`app/agent/loop.py`)가 `app.settings.PATTERN_KEY_PREFIX` 로 한 번 더 casefold 비교해 거른다(그 불변식에 기대지 않는다, 원칙9). `link_direct_facts` 자신은 주어진 키를 그대로 믿지만, 애초에 `pattern:` 키가 그 함수까지 도달할 경로가 없다(호출자가 이미 걸렀다).
  4. **`after_record` 안인지 별도 함수인지 -- 실제 링크 로직은 별도 모듈(`app/memory/direct_facts.py::link_direct_facts`)에 두고, `after_record` 는 오케스트레이션만 한다.** `detect_patterns`/`promote_person` 을 각각 별도 모듈에 두고 `after_record` 가 순서만 정하는 기존 구조(U6)와 같은 모양을 지켰다 -- 세이브포인트·실패 격리·`memory_error` 기록은 여전히 `after_record` 한 곳에만 있다.
  5. **`RecordOutcome` 에 더한 필드 -- `event_ids_by_person: dict[int, list[int]]`, `fact_keys_by_person: dict[int, list[str]]`.** 01-plan 73행이 명시적으로 요구한 것은 `fact_keys_by_person` 뿐이지만, "그 턴의 이벤트에 잇는다"를 실행하려면 그 턴에 그 인물이 실제로 만든 이벤트 id 도 알아야 해서(U6 의 `event_person_ids` 는 인물 id 집합일 뿐 이벤트 id 자체가 없다) `event_ids_by_person` 도 함께 더했다. 둘 다 `to_dict()` 에는 담지 않는다(U1 스키마 규약 -- `loop_record.output` 은 여전히 `executed`/`failed` 두 키뿐, 판정 19행 "지킬 불변식"과 정합).
  - 부가: `_execute_call` 의 반환값을 `_record_impl` 이 이제 받는다(이전에는 버렸다) -- `add_event` 가 돌려주는 `EventOut.id` 가 U7 이 필요로 하는 유일한 새 정보였다. `update_person`/`add_schedule` 의 반환값은 여전히 쓰지 않는다(호출은 `result` 변수에 받지만 `add_event` 가 아닌 분기는 `result` 를 읽지 않는다).
