## 목표
`docs/resolution-plan.md` §5 구현 순서 표의 "P1 | 스키마 v2 마이그레이션 (Alembic) | backend-agent | 4장 | 9개 테이블 생성, `events.type` 제약 존재" 한 줄을 실현한다. S3.1(스키마 v2)이 정의한 9개 테이블을 Alembic 마이그레이션으로 실제 PostgreSQL(pgvector)에 만들고, 그 위에 세워질 P2-tools·P3-er 가 기대하는 컬럼·제약·인덱스를 확정한다. 이 패키지가 닫는 검증은 R8("시맨틱→원문 링크 없음" → `fact_sources` 테이블 실재)과 R9("인물당 임베딩 1개" → `person_embeddings` 없음, `person_aliases.embedding vector(1536)` 실재)이다. 기획서 9장의 개인정보 요구("인물 단위 완전 삭제")를 FK ON DELETE CASCADE 로, 기획서 7장 평가의 라벨 집합을 `events.type` CHECK 제약으로 스키마에 못 박는다.

## 범위
- 포함:
  - **백엔드 골격의 최소 부분(마이그레이션을 돌리는 데 필요한 만큼만)**
    - `requirements.txt`(런타임: SQLAlchemy, Alembic, `psycopg[binary]`, `pgvector`) / `requirements-dev.txt`(pytest). 지금까지 의존성 선언 파일이 없었다(P0-compose 04-review §7: "`psycopg[binary]` 3.3.5 가 첫 항목"). 설치된 버전을 `==` 로 고정하고 `pip freeze` 출력을 evidence 로 남긴다.
    - `app/` 파이썬 패키지 신설: `app/__init__.py`, `app/config.py`(DB 접속 설정 해석), `app/db/__init__.py`, `app/db/base.py`(SQLAlchemy 2.x `DeclarativeBase` + `MetaData(naming_convention=...)`), `app/db/models.py`(테이블 9개 모델).
    - `tests/conftest.py` — 저장소 루트를 `sys.path` 에 넣어 `app` 을 임포트할 수 있게 한다(기존 `tests/test_db_check.py` 8행의 `sys.path.insert` 줄은 건드리지 않는다).
  - **DB 접속 설정 모듈 `app/config.py`**: `DATABASE_URL` 이 있으면 그것을 쓰고, 없으면 `POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB / POSTGRES_PORT`(+ 호스트 기본값 `localhost`)로 조립한다 — `scripts/db_check.py` 의 `resolve_connection()` 과 **같은 우선순위·같은 변수 이름**. `.env` 는 읽지도 쓰지도 않는다(security.md §1). 값은 `os.environ` 에서만 읽고, 반환한 접속 문자열·비밀번호를 로그·예외 메시지에 찍지 않는다.
  - **SQLAlchemy 모델 9개**(S3.1 그대로): `persons`, `person_aliases`, `person_facts`, `fact_sources`, `events`, `schedules`, `pending_questions`, `push_subscriptions`, `agent_traces`. 컬럼 집합은 S3.1 5~15행과 글자 그대로 대응시키고, 임의의 컬럼을 추가하지 않는다.
    - CHECK 제약 4개: `events.type ∈ {conflict, praise, meal, meeting, personal_share, favor, other}`, `persons.relation_tag ∈ {가족, 연인, 친구, 직장, 지인}`, `persons.hierarchy ∈ {상, 동, 하}`, `pending_questions.kind ∈ {identity, new_person, schedule}`.
    - `person_aliases.embedding` = `vector(1536)` (D4 확정 차원, D5 별칭 단위). nullable — 별칭 행이 먼저 생기고 임베딩이 나중에 채워질 수 있다.
    - FK ON DELETE CASCADE: `person_aliases.person_id`, `person_facts.person_id`, `events.person_id`, `schedules.person_id` → `persons.id`; `fact_sources.fact_id` → `person_facts.id`, `fact_sources.event_id` → `events.id`.
    - `fact_sources` 는 대리키 없이 **복합 기본키 `(fact_id, event_id)`**.
    - 인덱스(최소): `persons(user_id)`, `person_aliases(person_id)`, `person_aliases(alias)`, `events(person_id, occurred_at)`, `schedules(scheduled_at)`, `pending_questions(session_id, created_at)` + 미답변 조회용 부분 인덱스 `WHERE answered_at IS NULL`, `person_facts(person_id, key)`, `fact_sources(event_id)`(역방향 조회), `agent_traces(session_id, created_at)`.
    - 타입 정책: 기본키는 `BIGINT GENERATED BY DEFAULT AS IDENTITY`; 모든 타임스탬프는 `TIMESTAMP WITH TIME ZONE`(생성 시각은 서버 기본값 `now()`); `pending_questions.options`·`pending_questions.context`·`push_subscriptions.keys`·`agent_traces.input`·`agent_traces.output` 은 **JSONB**; 그 밖의 문자열은 `TEXT`; `person_facts.confidence` 는 `DOUBLE PRECISION`; `agent_traces.tokens_in/tokens_out` 은 `INTEGER`.
  - **Alembic 도입과 초기 마이그레이션 1개**: `alembic.ini`(`sqlalchemy.url` 은 **비워 둔다** — 비밀이 ini 에 들어가면 안 된다), `alembic/env.py`(`app.config` 로 접속 정보 주입, `target_metadata = app.db.base.Base.metadata`, `compare_type=True`), `alembic/script.py.mako`, `alembic/versions/0001_schema_v2.py`(9테이블·제약·인덱스 전부). `upgrade()` 첫 줄은 `CREATE EXTENSION IF NOT EXISTS vector`(멱등, P0-compose 04-review §7 이 무해함을 확인), `downgrade()` 는 역순 `drop_table` — 확장은 지우지 않는다.
  - **스키마 검사 스크립트 `scripts/schema_check.py`**: 접속 → 서버 버전·`vector` extversion 출력 → 9개 테이블 존재 → `events.type` CHECK 존재와 값 7개 → 나머지 CHECK 3개 → `person_aliases.embedding` 의 `format_type` 이 `vector(1536)` → FK 6개의 `confdeltype='c'` → 인덱스 목록 → `person_embeddings` 테이블 **부재**(R9) 를 한 번에 찍고, 하나라도 어긋나면 0 이 아닌 종료 코드. 비밀번호·접속 문자열은 출력하지 않는다.
  - **검증 증거**: `docs/wiki/packages/P1-schema/evidence/` 에 `alembic upgrade head` → `schema_check` → `alembic downgrade base` → 테이블 부재 확인 → 재 `upgrade head` 왕복 출력, `pytest` 출력, `pip freeze` 출력을 `tee` 로 남긴다.
  - **문서 반영**: `docs/wiki/registry.md` 신규 행(app 패키지·모델·마이그레이션·requirements·schema_check·테스트) + 기존 행 비고 갱신(`README.md` 행, `scripts/db_check.py` 행 — **새 행 금지**), `README.md` 진행 상태 표 P1 행과 "로컬에서 해 보기" 절의 마이그레이션 실행 절.
  - **`scripts/db_check.py` 에 서버 버전 한 줄 추가**(P0-compose 04-review §6 관찰 O1 권고): `SELECT version()` 결과를 `[ok] server = …` 로 찍는다. 이유 — 이 패키지가 `vector(1536)` 컬럼과 제약을 **어느 서버 버전 위에서** 만들었는지가 P9-infra 의 RDS 메이저 버전 확인(미결 1)과 재현(원칙8)의 근거가 된다. `scripts/schema_check.py` 도 같은 줄을 찍는다.
- 이 패키지에서 하지 않는 것:
  - **데이터 삽입·시드**(테스트 픽스처 포함). 이 패키지의 검증은 빈 DB 의 DDL 만으로 한다. 시나리오 데이터는 P1-pilot-dataset(eval-agent).
  - **툴 7종**(S3.2)·FastAPI 앱·라우터·엔드포인트·ORM 세션 관리(`sessionmaker`/의존성 주입)·CRUD 함수 — 전부 **P2-tools**. 이 패키지의 `app/` 은 "모델 + 접속 설정"까지이며, `app/main.py` 를 만들지 않는다.
  - ER 로직·후보 검색 쿼리·거리 연산자 사용 — P3-er.
  - **벡터 인덱스(HNSW/IVFFlat) 생성·튜닝**. 근거: 행이 0건이라 인덱스가 성능을 보여줄 수 없고, `m`·`ef_construction`·거리 연산자(cosine `<=>` vs L2)는 P3-er 의 실제 후보 검색 쿼리가 정해야 한다. 별도 마이그레이션으로 P3-er 에서 추가한다(1536 은 pgvector HNSW 한도 2000 안 — D4 확정 근거).
  - **인물–인물(A–B) 관계 테이블**(원칙7, D8) 과 **`person_embeddings` 테이블**(D5, R9). 만들지 않는 것이 이 패키지의 산출물이며, 부재를 `scripts/schema_check.py` 가 검사한다.
  - `docker/initdb/01-vector.sql` 수정·SQL 추가(P0-compose 04-review §7: 테이블은 Alembic 으로), `docker-compose.yml` 변경.
  - 볼륨 삭제·`down -v`·`prune`·셸에서의 `DROP`/`TRUNCATE`(security.md §4). 스키마를 되돌릴 때는 `alembic downgrade` 만 쓴다. `DROP TABLE` 은 검토 가능한 마이그레이션 파일 안에만 존재한다.
  - RDS·Terraform·SSM·Dockerfile·CI — P9-infra.
  - `users` 테이블 신설, `pending_questions.status` 컬럼 신설 등 **S3.1 에 없는 컬럼·테이블 추가**.
  - `updated_at` 자동 갱신 트리거(DB 트리거). ORM `onupdate=func.now()` 까지만 둔다 — 트리거는 마이그레이션 검토 비용만 늘고 P2 의 쓰기 경로가 전부 ORM 이다.

## 리스크 · 미결
- **결정 1 — 모델 + autogenerate 보정(택일 결과).** SQLAlchemy 모델을 진실의 원천으로 두고, Alembic revision 은 `--autogenerate` 로 초안을 뽑아 **손으로 검토·보정**한다. 손으로만 쓴 마이그레이션을 택하지 않은 이유: P2-tools 가 어차피 ORM 모델을 쓰므로 모델을 나중에 또 쓰면 DDL 과 모델이 갈라지고, `alembic check` 같은 기계적 일치 검사를 쓸 수 없다. 대신 autogenerate 를 그대로 믿지 않고 아래 리스크대로 보정한다.
- **리스크 — Alembic autogenerate 가 `vector` 를 제대로 못 낸다.** 생성된 revision 에 `pgvector.sqlalchemy.Vector` import 가 빠지거나 타입이 `NullType` 으로 렌더될 수 있고, `compare_type` 이 매번 가짜 차이를 만들 수 있다. 대응: `env.py` 에 `render_item` 훅으로 Vector 렌더를 명시하고 revision 파일 상단 import 를 확인, U4 에서 `alembic check` 가 "변경 없음"인지 evidence 로 남긴다. 부분 인덱스(`WHERE answered_at IS NULL`)·CHECK 이름도 autogenerate 가 흘릴 수 있으므로 U2 의 DB 없는 테스트와 U4 의 `pg_constraint`/`pg_indexes` 조회로 이중 확인한다.
- **결정 2 — `pgvector` 파이썬 패키지를 쓴다.** `pgvector.sqlalchemy.Vector(1536)`. 직접 `UserDefinedType` 을 만들지 않는 이유: P3-er 이 곧 거리 연산자(`<=>` 등)를 써야 하는데 그때 또 만들게 되고 registry 중복이 된다. 리스크 — 설치·SQLAlchemy 버전 호환 실패. 그 경우에만 최소 `UserDefinedType` 자작으로 후퇴하고 그 결정을 03-log 에 적는다.
- **결정 3 — 의존성 선언은 `requirements.txt` + `requirements-dev.txt`.** 이유: 이 저장소는 라이브러리로 배포하지 않고 소스로 실행하며(빌드 백엔드·패키징 메타데이터가 필요 없다), P9-infra 의 Dockerfile 이 `pip install -r requirements.txt` 한 줄로 끝난다. **미결**: ruff·pytest 설정 등 도구 설정이 늘어나면 `pyproject.toml` 로 옮길지 P2-tools 착수 때 재검토한다(옮길 때 requirements 는 `pip-compile` 산출물로 남길 수 있다).
- **결정 4 — 골격 범위선.** `app/config.py` + `app/db/{base,models}.py` 까지. 엔진·`sessionmaker`·요청 단위 세션·FastAPI 앱·라우터는 **P2-tools**. Alembic `env.py` 는 자기 엔진을 직접 만들어 쓰므로 이 선 안에서 동작한다.
- **결정 5 — 벡터 인덱스는 만들지 않는다.** 데이터 0건 시점에서는 순차 스캔이 더 빠르고 인덱스 파라미터를 정당화할 측정치가 없다(원칙8 — 근거 없는 수치를 만들지 않는다). P3-er 에서 실제 쿼리와 함께 별도 마이그레이션으로 추가한다.
- **미결 — 로컬 pg16 vs RDS 메이저 버전.** 로컬은 `pgvector/pgvector:pg16`, vector 0.8.6(P0-compose 04-review §7). RDS 버전은 P9-infra 에서 정해진다. DDL 은 표준 범위 안에 두고, 검증 evidence 에 서버 버전을 남긴다(U5 의 `SELECT version()` 이 이 목적). RDS 의 pgvector 사용 가능 버전은 P9-infra 착수 시 재확인(README·registry 비고에 이미 메모).
- **미결 — 포트 5432/5433.** 로컬 5432 는 무관 컨테이너가 점유(04-review 관찰 O6). 에이전트는 `.env` 를 읽지 않으므로 모든 검증 명령에서 포트를 셸 변수로 명시한다. `DATABASE_URL` 과 `POSTGRES_PORT` 를 동시에 주면 `DATABASE_URL` 이 이긴다(db_check 규칙과 동일) — evidence 에는 두 경로 중 어느 것을 썼는지 `source=` 로 보이게 한다.
- **미결 — JSONB 채택 근거와 한계.** `options`·`context`·`keys`·`input`·`output` 은 구조가 호출마다 다르고(원칙9: `candidates[]`·`confidence_breakdown{}`·`decision`), 나중에 평가에서 키 단위로 뽑아 써야 하므로 TEXT 대신 **JSONB** 로 둔다(키 접근·GIN 인덱스 가능, 파싱 코드 불필요). 한계: JSONB 는 키 순서와 중복 키를 보존하지 않는다 — 원문 그대로의 재현이 필요한 값은 문자열 컬럼(`events.raw_utterance`)에 있으므로 문제되지 않는다. GIN 인덱스는 이 패키지에서 만들지 않는다(쿼리가 아직 없다).
- **미결 — `persons.user_id` 타입.** 단일 사용자 제품이지만 컬럼은 유지한다(S3.1, security.md §5 "모든 조회는 `user_id` 조건"). `users` 테이블이 S3.1 에 없으므로 **FK 없이 `TEXT NOT NULL`** 로 두고 인덱스만 건다. 기본 사용자 식별자를 어디서 얻을지(설정값)는 P2-tools 에서 정한다. `push_subscriptions.user_id` 도 같은 타입.
- **미결 — 타임스탬프 정책.** 전부 `TIMESTAMP WITH TIME ZONE`, 생성 시각은 서버 `now()` 기본값, 애플리케이션은 aware UTC 로 다룬다. "어제 저녁" 같은 상대 표현을 KST 기준 절대 시각으로 바꾸는 책임은 P2-tools/P5-loop 이며 스키마는 관여하지 않는다. `occurred_at`·`scheduled_at` 은 NOT NULL(툴 시그니처가 필수 인자), `briefed_at`·`confirmed_at`·`answer`·`answered_at`·`embedding` 은 nullable.
- **미결 — `person_facts` 의 `(person_id, key)` 유일성.** 승격이 같은 키를 갱신하는지 여러 행을 쌓는지는 P6-memory 가 정한다. 이 패키지에서는 UNIQUE 를 걸지 않고 인덱스만 둔다(나중에 거는 것이 나중에 푸는 것보다 쉽다).
- **미결 — `pending_questions` 에 `status` 컬럼이 없다.** S3.1 은 `answer`·`answered_at` 만 정의한다. S3.2 의 `{question_id, status:"pending"}` 의 `status` 는 `answered_at IS NULL` 에서 파생되는 값이며, 스키마에 컬럼을 추가하지 않는다. 미답변 조회를 위해 부분 인덱스만 둔다.
- **미결 — 인물 완전 삭제의 사각지대.** `pending_questions`·`agent_traces` 는 person FK 가 없으므로 `DELETE /persons/{id}` 의 CASCADE 로 지워지지 않는다(security.md §5). 스키마 결정이 아니라 애플리케이션 삭제 절차의 문제이므로 P2-tools 이후에서 다룬다 — 여기서는 기록만 한다.
- **기계 검증에서 예상되는 WARN(FAIL 아님).** `verify-plan.sh` 7번(registry 중복)은 산출물 목록의 `README.md` 와 `scripts/db_check.py` 에 대해 "다른 패키지로 이미 있음" WARN 을 낸다 — 둘 다 **새 행을 만들지 않고 기존 행의 비고만 갱신**하는 것이 계획이므로 의도된 결과다(P0-compose 04-review §5 와 같은 처리).
- **보안.** `alembic.ini` 에 `sqlalchemy.url` 값을 넣지 않는다(비밀 문자열 금지, security.md §1). 마이그레이션·스크립트 출력에 접속 문자열·비밀번호를 찍지 않는다. `DROP TABLE` 은 `downgrade()` 안에만 존재하고 셸에서 실행하지 않는다(§4). 볼륨 삭제가 필요해 보이면 `alembic downgrade base` 로 대신하고, 그래도 필요하면 명령을 사용자에게 보여 주고 멈춘다(§6).
