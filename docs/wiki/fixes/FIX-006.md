# FIX-006 · 테스트가 개발 DB 를 로컬 서버와 같이 써서, 서버를 한 번 쓰면 테스트 20건이 깨진다

발견: 2026-09-26 · FIX-005 전체 회귀(backend-agent 보고 → 메인 세션 원인 확인) | Refs: FIX-006 FIX-004 P1-schema 원칙8

## 증상

FIX-005 전체 회귀에서 시간대와 무관한 테스트 20건이 실패했다(`docs/wiki/fixes/evidence/FIX-005/20260925-2335-full-regression.txt`). 그중 하나는 다음과 같다.

```
tests/test_er_pipeline.py::test_resolve_skips_llm_when_no_candidates_pass_rules_no_candidates
>       assert result.forced_reason == "no_candidates"
E       AssertionError: assert 'no_matched' == 'no_candidates'
```

P5-loop 8행 실서버 확인이 `user_id=local` 에 남긴 인물 "서준"(id 23175)의 `user_id` 만 바꾸자 1481 passed 로 돌아왔다(`evidence/FIX-005/20260926-0005-row8-person-isolation.txt`·`20260926-0010-full-regression-after-isolation.txt`).

## 원인

- `tests/conftest.py::db_session` 은 바깥 트랜잭션 + SAVEPOINT 로 **테스트가 쓴 것**은 롤백한다. 하지만 **이미 커밋된 다른 데이터**는 그대로 보인다.
- 테스트는 개발 DB(`POSTGRES_DB=relationship`, 포트 5433)와 사용자 id `"local"` 을 쓴다. 테스트 파일 10여 개 헬퍼가 `user_id: str = "local"` 을 기본값으로 두고, `ToolContext.user_id` 기본값도 `app_user_id()`(기본 `"local"`)다.
- 로컬 서버(`uvicorn app.main:app`)도 기본으로 같은 DB·같은 `"local"` 을 쓰고, 요청마다 **커밋**한다.
- 그래서 로컬 서버를 한 번 쓰면 "`local` 에는 테스트가 넣은 사람만 있다"는 테스트의 가정이 깨진다. FIX-004(전역 개수 단언)와 같은 계열이지만, 이번에는 테스트 코드 한 곳이 아니라 **테스트 환경 전체**의 격리 문제다.

## 수정안 (파일 · 방식 · 회귀 테스트)

**방식: 테스트 전용 DB(사용자 결정 2026-09-26, "테스트 전용 DB").** 같은 PostgreSQL 서버 안에 `relationship_test`(이름은 설정으로 덮어씀) DB 를 따로 두고, pytest 는 항상 거기에만 붙는다. 개발 DB·로컬 서버 데이터는 테스트에 보이지 않는다.

| # | 파일 | 방식 |
|---|------|------|
| 1 | `tests/conftest.py` | 앱·엔진을 import 하기 **전에** 테스트용 DB 이름을 확정한다. 기본 `relationship_test`, 환경변수 `TEST_POSTGRES_DB` 로 덮어쓴다. `DATABASE_URL` 이 설정돼 있으면 그 DB 이름만 테스트 DB 로 바꾼다(호스트·포트·계정은 유지). 그런 다음 세션 시작 시 한 번 확인한다. 테스트 DB 가 없으면 만들고(`CREATE DATABASE`, 기존 DB 는 건드리지 않음), `vector` 확장과 `alembic upgrade head` 를 적용한다. **개발 DB 이름과 같아지면 즉시 실패**시켜 실수로 개발 DB 를 쓰지 못하게 한다. |
| 2 | 테스트 헬퍼 | 원칙적으로 무변경(`"local"` 그대로). 테스트 DB 안에서는 서버 데이터가 없으므로 가정이 다시 성립한다. |
| 3 | `.github/workflows/tests.yml` | CI 서비스 DB 에서도 같은 경로가 돌게 한다. conftest 가 테스트 DB 를 만들고 마이그레이션한다. 기존 `alembic upgrade head` 단계는 개발 DB 용으로 남기거나 정리한다(구현 시 판단, 이유 기록). skip 0 규칙은 유지한다. |
| 4 | `docs/RUNNING.md`·`README.md` 실행 절 | "테스트는 `relationship_test` 를 쓴다, 로컬 서버 데이터와 분리된다" 한 줄. |
| 5 | 회귀 테스트 | 새 테스트 1건 이상. ① 테스트 세션의 `current_database()` 가 개발 DB 이름이 아니다. ② 개발 DB 에 커밋된 행이 테스트 세션에 보이지 않는다. 가능하면 **개발 DB 에 임시 인물을 커밋하지 않고** 확인한다. 예: 이름 비교와 엔진 URL 검사. 개발 DB 에 쓰는 테스트는 만들지 않는다. ③ 테스트 DB 이름이 개발 DB 와 같게 설정되면 conftest 가 거부한다. |

회귀: `POSTGRES_PORT=5433 python -m pytest -q tests/` 전체 skip 0. 그다음 **격리 증명**을 한다. 개발 DB 의 `row8-check-23175`(서준)를 `local` 로 되돌려 테스트 20건이 깨지던 조건을 재현한 뒤, 전체 회귀가 여전히 통과하는지 본다. 끝나면 `row8-check-23175` 로 복구한다(두 UPDATE 모두 evidence). 재현·복구는 메인 세션이 사용자 승인 범위(FIX-005 에서 승인한 같은 행의 `user_id` 변경) 안에서 한다.

**설계 판단**
1. **import 순서**: `tests/conftest.py` 는 `sys.path` 등록 직후, `app.db.session`/`app.embedding` 을 import 하기 **전에** `apply_test_database_env()` 를 호출한다. `get_engine()` 은 최초 호출 시점의 `os.environ` 을 읽어 엔진을 모듈 전역에 캐시하므로(리스크 A, 기존 설계), 이 순서를 지키지 않으면 개발 DB 이름으로 캐시된 엔진을 이후 되돌릴 방법이 없다.
2. **엔진 캐시**: `app/db/session.py::get_engine()` 은 무변경이다. "앱·엔진 import 전에 확정"이라는 요구를 `app` 코드 수정 없이 `os.environ` 조작만으로 만족시켰다 — `DATABASE_URL` 이 있으면 DB 이름만 바꿔 재조립하고, 없으면 `POSTGRES_DB` 를 바꾼다(`app.config.resolve_connection()` 의 기존 우선순위를 그대로 이용).
3. **DB 생성·마이그레이션 시점**: `CREATE DATABASE`/`CREATE EXTENSION`/`alembic upgrade head` 는 세션 스코프 `db_engine` 픽스처 최초 호출 시 1회 수행한다(`ensure_test_database_ready()`). 접속 정보 확정(순수 문자열 조립, 회귀 ③ 대상)은 DB 접속 여부와 무관하게 모듈 로드 시 즉시 실행해 개발 DB 이름 충돌을 항상 잡지만, 실제 DB 생성·마이그레이션은 `dbtest` 를 쓰는 테스트가 실제로 `db_engine` 을 요청할 때까지 미뤄 기존 "PostgreSQL 미접속 → skip" 경로(사유가 `-rs` 로 보임)를 그대로 유지했다.
4. **alembic 이 테스트 DB 를 보게 한 방법**: `alembic/env.py` 는 무변경이다 — `app.config.resolve_connection()` 으로 `os.environ` 을 읽는 기존 로직을 그대로 쓰고, 이미 `apply_test_database_env()` 가 환경을 테스트 DB 로 바꿔 둔 뒤에 `alembic.command.upgrade(cfg, "head")` 를 파이썬 API 로 호출한다(`Config.script_location` 은 cwd 의존을 없애려 절대경로로 명시). CLI `alembic upgrade head` 를 셸에서 따로 부르지 않는다.
5. **CI 처리**: `.github/workflows/tests.yml` 의 `alembic upgrade head` 단계(개발 DB `relationship` 에 직접 적용하던 것)를 제거했다 — pytest 가 스스로 `relationship_test` 를 만들고 마이그레이션하므로 그 단계는 더 이상 어떤 테스트도 거치지 않는 중복 작업이었다(로컬 실행과 CI 가 같은 경로를 타게 하려는 목적, 수정안 4행). `DATABASE_URL`(포트 5432, DB `relationship`)은 그대로 두었다 — `apply_test_database_env()` 가 그 URL 의 DB 이름만 `relationship_test` 로 바꾸므로 서비스 컨테이너의 기본 DB 이름과 무관하게 동작한다(로컬에서 `DATABASE_URL=...5433/relationship` 로 같은 경로를 직접 확인, evidence `20260925-2352-database-url-path-check.txt`).
