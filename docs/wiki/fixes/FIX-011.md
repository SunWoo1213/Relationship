# FIX-011 · 구현 검증이 테스트 없이 통과하던 것을 막는다

발견: 2026-09-29 · 사용자 요청으로 "계획 → 계획검증 → 구현 → 구현검증" 네 단계 훅을 점검하다 발견 | Refs: FIX-011 FIX-008 L-002 원칙8 verification

## 증상

`verify-impl.sh`(구현 검증, `/devlog done` 의 1단계)를 이 기기에서 돌리자 이렇게 나왔다.

```
== verify-impl P6-memory ==
WARN  pytest 미설치 — 테스트 증거 없음
FAIL  문법 오류 → evidence/…-lint.txt
```

두 줄 다 사실과 달랐다.

- **pytest 는 설치돼 있다.** 스크립트가 `python -m pytest` 로 불렀는데 이 기기에 `python` 이라는 이름이 없었을 뿐이다(FIX-008 과 같은 뿌리). 그런데 이 경우가 `WARN` 이라서, **테스트를 한 건도 돌리지 않고 구현 검증이 지나간다.** 검증 실패가 경고로 내려앉은 것이 문제의 핵심이다.
- **문법 오류가 아니었다.** `FAIL` 이라고 가리킨 파일의 내용은 `verify-impl.sh: line 50: python: command not found` 한 줄이었다. 진짜 문법 오류와 구분되지 않는다.

고쳐서 pytest 가 돌게 하자 **세 번째 문제**가 드러났다. 이 기기의 DB 컨테이너는 5433 인데 기본값 5432 로 붙으려다 실패해 **255건이 건너뛰어졌고, 그런데도 `PASS pytest 통과` 가 찍혔다**(1215 passed / 309 skipped). 스크립트 주석이 `-rs: … DB 미연결로 조용히 skip된 초록불 방지` 라고 적어 두고도 실제로는 막지 못하고 있었다.

부수로, `devlog` 스킬과 `verification.md` 가 소견 생성을 `python .claude/scripts/findings.py …` 로 안내한다. 이 기기에서는 실행되지 않아 **FAIL/WARN → 소견 루프가 시작조차 되지 않는다.**

## 원인

하나의 뿌리에서 세 갈래로 벌어졌다. 도구를 부르는 이름과 경로가 OS 마다 다른데 한쪽만 가정했고(`python`, 시스템 인터프리터), 그 가정이 깨졌을 때 **실패 방향이 통과 쪽**이었다. 가드는 못 하면 막아야 하는데 못 하면 넘어가고 있었다.

같은 점검에서 나머지 세 단계는 정상임을 확인했다. `delegate-guard`(계획 위임 승인), `verify-plan.sh`(계획 검증 + `검증자: verifier` 강제), `stage-gate`(`frozen` → `active` → `02-plan-verify` 의 `결과: 통과`·`승인:` 순서 검사)는 모두 제 일을 한다.

## 수정안 (파일 · 방식 · 회귀 테스트)

**공용 탐지를 `_py.sh` 에 추가한다** — `hook_python_with <모듈> [루트]`. 후보를 `.venv/bin/python`(Unix) → `.venv/Scripts/python.exe`(Windows) → `python` → `python3` 순으로 보며, 각 후보로 **그 모듈을 실제 import 해 본다.** 훅은 표준 라이브러리만 쓰므로 기존 `HOOK_PY` 로 충분하지만, 검증 스크립트는 pytest·ruff·yaml 처럼 가상환경 안에만 있는 의존성이 필요해 탐지가 따로 필요하다.

**`verify-impl.sh` 의 실패 방향을 뒤집는다.**

| 상황 | 그때 | 지금 |
|------|------|------|
| pytest 를 돌릴 인터프리터가 없다 | `WARN 미설치` | **`FAIL`** — 테스트 증거 없이 통과시키지 않는다 |
| 린트·문법 검사를 못 돌린다 | `FAIL 문법 오류`(사실과 다름) | **`FAIL 인터프리터가 없다`**(사실대로) |
| DB 에 못 붙어 건너뛴 테스트가 있다 | `WARN skip 있음` | **`FAIL`** — 건수와 함께, 포트를 맞춰 다시 돌리라고 알린다 |

DB 미연결 skip 만 골라내는 근거는 `tests/conftest.py` 가 남기는 사유 문구다(`not reachable` · `Connection refused` · `OperationalError`). 그 밖의 정상 skip 은 그대로 `WARN` 이다.

**`findings.sh` 래퍼를 만든다.** 문서는 OS 에 상관없이 `bash .claude/scripts/findings.sh …` 한 가지로 안내한다. `devlog` 스킬 2곳과 `verification.md` 1곳을 고쳤다.

**`test-guards.sh` 의 PyYAML 탐지를 공용 함수로 통일한다**(FIX-010 에서 임시로 넣었던 중복 제거).

### DB 포트를 어떻게 전달하나 (사용자 결정 2026-09-29 — A안)

검증 3에서 드러난 "DB 에 못 붙어 건너뜀" 은 값을 전달하는 방법의 문제이기도 하다. 사용자가 포트를 환경 파일에 적어 두었는데, 이 저장소의 코드는 **환경 파일을 스스로 읽지 않는다**(`python-dotenv` 미사용 — security §1 이 비밀 파일 접근을 좁히기 위해 그렇게 두었다). `app/config.py` 의 기본값은 `5432` 인데 개발용 컨테이너는 `5433` 이라 그대로 두면 계속 건너뛴다.

선택지는 셋이었다. (A) 실행할 때 환경 파일을 셸에 올린다 / (B) 검증 스크립트가 환경 파일을 직접 읽게 한다 / (C) 기본 포트를 5433 으로 바꾼다. **사용자가 A 를 골랐다.** B 는 스크립트가 비밀 파일을 읽게 되어 security §1 과 충돌하고, C 는 다른 기기가 5432 면 그쪽이 깨진다. A 는 코드를 바꾸지 않고 양쪽 OS 에서 같게 동작한다.

```
set -a; . ./.env; set +a
bash .claude/scripts/verify-impl.sh <id>
```

값을 출력하지 않고 셸에 올리기만 한다(`cat`·`echo` 는 훅이 막는다). 환경 파일이 없는 기기에서는 `POSTGRES_PORT=5433 bash …` 처럼 필요한 값만 앞에 붙여도 된다. 이 방법을 `verification.md` 의 루프 절 머리말과 `verify-impl.sh` 헤더 주석에 적었다.

확인: 환경 파일을 올린 셸에서 `verify-impl.sh P6-memory` → `PASS pytest 통과`, 증거 `evidence/20260929-0134-pytest.txt` 에 `1524 passed, skip 0`. DB skip FAIL 없음.

곁들여 `tests/conftest.py` 의 주석 오기를 고쳤다 — "기본 포트 5433" 이라고 적혀 있었으나 실제 기본값은 `app/config.py` 의 `5432` 다. 이 잘못된 주석이 "포트를 안 줘도 되겠지" 라는 오해를 만들 수 있었다.

### 남은 것 — Windows 기기 확인 (사용자 몫, 2026-09-29 기록)

FIX-008·FIX-010·FIX-011 은 **전부 Mac 에서만 확인했다.** 양쪽 OS 에서 돌아가게 짜기는 했지만(`python` → `python3` 순서, `.venv/Scripts/python.exe` 후보), Windows 에서 실제로 돌려 본 적이 없다. 그 기기에서 아래 다섯 가지를 한 번 확인해야 이 FIX 가 닫힌다.

| # | 확인할 것 | 명령 | 기대 |
|---|----------|------|------|
| 1 | 훅 자가 점검 | `bash .claude/scripts/test-guards.sh` | `== 결과: 실패 0 ==` |
| 2 | 구현 검증이 테스트를 실제로 돈다 | `set -a; . ./.env; set +a` 뒤 `bash .claude/scripts/verify-impl.sh P6-memory` | `PASS pytest 통과`, 증거에 `passed`·skip 0 |
| 3 | 인터프리터를 `python` 으로 고르는가 | `bash -c '. .claude/hooks/_py.sh; echo $HOOK_PY'` | `python`(Windows 표준 이름. `python3` 스텁을 건드리지 않았다는 뜻) |
| 4 | venv 경로를 찾는가 | `bash -c '. .claude/hooks/_py.sh; hook_python_with pytest "$PWD"'` | `.venv/Scripts/python.exe` |
| 5 | 커밋 후처리가 도는가 | 아무 커밋이나 한 번 | 승인 마커 자동 삭제 + `journal.md` 에 `COMMIT` 줄 자동 생성 |

특히 3번이 중요하다. Windows 의 `python3` 는 Microsoft Store 를 여는 스텁인 경우가 많아, 순서가 뒤바뀌면 훅이 멈추거나 스토어 창이 뜰 수 있다. `_py.sh` 가 `python` 을 먼저 보고 **실제로 실행해 확인**하도록 짠 이유가 이것이다.

하나라도 어긋나면 그 출력을 근거로 새 FIX 를 연다. `HANDOFF.md` "사용자 몫" 절에도 같은 내용을 적어 두었다.

점검 대상으로 남기는 것: 이 결함이 있는 동안 `verify-impl.sh` 로 "통과" 처리된 과거 패키지들은 **테스트 증거 없이 닫혔을 수 있다.** 다만 그 패키지들의 04-review 에는 메인 세션·verifier 가 따로 돌린 pytest 출력이 증거로 붙어 있어 실제 위험은 낮다. 되돌리지 않고 기록만 남긴다.
