# FIX-015 · 루프가 제안하는 사실 키를 고정 어휘로 유도한다

발견: 2026-09-29 · P6-memory U7 실 LLM 확인(journal 19:50) / 04-review §7-1·§7-2 가 "범위 밖 별건" 으로 분류 | Refs: FIX-015 P6-memory S3.2 D-5

## 증상

같은 뜻의 사실이 **키 3개로 중복 저장된다.** 실 LLM 왕복에서 한 인물에 아래 세 행이 동시에 있었다(journal 2026-09-29 19:50, 확인용 행 `u7-check`):

| key | value | 만든 곳 |
|---|---|---|
| `소속` | 네이버 | 루프의 `update_person` (P5) |
| `직장` | 네이버 | 루프의 `update_person` (P5) |
| `workplace` | 네이버 | 승격 (P6-memory U5) |

앞선 확인(journal 17:30)에서는 같은 자리에 `이직 = 카카오` 가 생겼다. 즉 **관측된 것만 `이직`·`소속`·`직장` 세 가지**이고, 발화마다 다른 한국어 키가 만들어진다.

결과로 `person_facts` 에 두 어휘가 섞인다 — 승격이 만든 통제된 9키(`job`·`workplace`·…)와 루프가 만든 자유 키. **브리핑(P6-briefing)과 인물 카드(P8)는 이 둘을 함께 읽으므로 중복을 그대로 보여준다.** 그래서 그 두 패키지보다 먼저 닫는다.

부차 관측(같은 확인): 사실 제안 자체가 드물다 — 발화 7건 중 `update_person(facts=…)` 제안은 2건이고 나머지는 이벤트만이었다. 시맨틱 사실의 주 공급원은 승격이고 루프 경로는 보조다. 그래도 루프가 만든 키가 카드 맨 위에 섞여 보이는 것은 같다.

## 원인

`app/agent/propose.py::PROPOSAL_ARG_SCHEMA` 의 `facts.key` 가 **enum 없는 자유 문자열**이다(145~155행):

```python
"facts": {
    "type": "array",
    "items": {
        "type": "object",
        "properties": {
            "key": {"type": "string"},      # ← enum 없음
            "value": {"type": "string"},
        },
        "required": ["key", "value"],
    },
},
```

같은 스키마의 다른 고정 집합 필드는 이미 enum 으로 LLM 을 유도하고 있다 — `type`(`EVENT_TYPES`) · `relation_tag`(`RELATION_TAGS`) · `hierarchy`(`HIERARCHIES`). `facts.key` 만 빠져 있다. 그 모듈의 docstring(125~131행)이 설계 의도를 이미 적어 뒀다:

> `type`/`relation_tag`/`hierarchy` 만 CLAUDE.md 고정 집합 enum 으로 LLM 을 **유도**한다 (…PROPOSAL_SCHEMA 의 enum 으로 유도할 뿐, 7종 밖 값의 거부는 게이트가 한다).

즉 **유도할 어휘가 생긴 뒤에도 그 자리에 연결하지 않은 것**이 원인이다. 어휘 `FACT_KEYS` 9종은 P6-memory U1 에서 `app/memory/types.py` 356~366행에 이미 만들어져 있다(`job`·`workplace`·`family`·`hobby`·`likes`·`dislikes`·`health`·`life_event`·`contact_note`).

곁들여 `_PROPOSAL_TOOL_DESCRIPTION`(120행)에도 사실 키에 대한 지시가 없다.

### 이 수정이 하지 않는 것 (한계를 미리 박아 둔다)
- **enum 은 유도이지 거부가 아니다.** 게이트(`app/agent/gate.py`)는 어휘를 검사하지 않으므로, LLM 이 그래도 어휘 밖 키를 내면 여전히 저장된다. 거부까지 하는 안(사용자에게 제시한 (나)·(다))은 고르지 않았다 — 거부는 그 사실을 **잃는다**(`failed[]` 로만 남는다). 유도 후에도 자유 키가 관측되면 그때 거부를 별건으로 올린다.
- **이미 저장된 중복 행(`소속`·`직장`)은 지우지 않는다.** 개발 DB 의 확인용 행은 보존이 원칙이다(HANDOFF "지우지 않는다").
- **승격(U5)은 손대지 않는다.** 승격은 이미 `FACT_KEYS` 로 검증한다(U4 `validate_extraction`).
- **추출 품질**(회사명이 `workplace` 가 아니라 `job` 에 들어간 것)은 별개다 — P10-final-eval 몫.

### 이 확인에서 새로 드러난 것 2건 (FIX-015 범위 밖, 별건 후보)

1. **[추출 품질] `likes = 매운 음식` 은 틀렸다.** 발화는 "지현이는 매운 음식을 **못 먹어**" 였는데 LLM 이 `likes` 에 넣었다(같은 호출에서 `dislikes = 고수` 는 맞게 넣었다). 어휘는 지켜졌지만 **값의 의미가 뒤집혔다** — 즉 FIX-015 는 "어느 서랍에 넣는가" 를 고쳤을 뿐 "무엇을 넣는가" 는 고치지 않는다. 앞서 관측된 "회사명이 `workplace` 가 아니라 `job` 에" 와 같은 범주이며 **P10-final-eval 몫**이다. 이제 지표가 붙을 자리가 분명해졌다 — `dislikes` 와 `likes` 의 혼동은 브리핑이 정반대 제안을 내게 만든다(예: 매운 음식점 추천).
2. **[응답 문구] 사실만 저장된 턴이 "새로 기억한 것이 없어요" 라고 답한다.** trace 161·171·181 세 턴 모두 `person_facts` 를 실제로 썼는데(fact_id 13~16) 응답은 `_NOTHING_STORED` 였다. 원인은 `app/agent/respond.py::build_reply` 가 `stored_events`·`stored_schedules` 두 숫자만 보고 사실 건수를 받지 않기 때문이다(P5-loop 결정 B(i), FIX-015 가 만든 것이 아니다). 사용자에게는 "기억 안 했다" 고 해 놓고 카드에는 사실이 쌓이는 상태라 **신뢰를 깎는다.** FIX 후보.
