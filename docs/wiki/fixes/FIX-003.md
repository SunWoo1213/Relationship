# FIX-003 · verifier 에이전트가 frontmatter YAML 오류로 조용히 로드되지 않았다

발견: 2026-09-24 · P5-loop 02-plan-verify 3차 위임(메인 세션) | Refs: FIX-003 P5-loop L-002 L-004

## 증상

P5-loop 계획 검증 3차를 verifier 에 위임하자 Agent 호출이 실패했다(이 세션에서 3회, 다른 세션에서 1회).

```
Agent type 'verifier' not found. Available agents: architect, backend-agent, claude, claude-code-guide, eval-agent, Explore, general-purpose, Plan, statusline-setup
```

- `.claude/agents/verifier.md` 파일은 있고, 사람 눈으로 보면 frontmatter 형식(`---` 사이 name·description·tools·model)도 정상이다.
- 오류 메시지 없이 **목록에서만 빠진다.** L-002(검증은 verifier 만)·L-004(단계 승인 마커)가 걸려 있어 계획 검증이 통째로 멈춘다.
- 부작용: 실패한 Agent 호출도 `delegate-guard.sh` 의 1회용 단계 승인 마커를 소모한다 → 사용자 재승인이 두 번 필요했다.

## 원인

description 의 끝 문장 `… 요청에 쓴다. L-002: 계획·구현·검증은 서로 다른 모델이 맡는다.` 에서 **`: `(콜론+공백)을 YAML 이 키-값 구분자로 읽는다.** 따옴표 없는 plain scalar 안에서는 허용되지 않는 형식이라 frontmatter 전체가 파싱에 실패하고, Claude Code 는 그 에이전트를 조용히 버린다.

확인 명령과 출력(메인 세션, 2026-09-24):

```
python -c "yaml.safe_load(<verifier.md frontmatter>)"
YAML ERROR mapping values are not allowed here
  in "<unicode string>", line 3, column 199:
     ... "수용 기준 대조", "리뷰해줘" 요청에 쓴다. L-002: 계획·구현·검증은 서로 다른 모델이 맡는다.
```

같은 검사에서 architect·backend-agent·eval-agent 는 정상 파싱됐다. 결함은 verifier 를 만든 커밋 `64f92e4`(harness(L-002)) 부터 있었다. 그 뒤 verifier 위임이 성공했던 세션이 있었다면, 그 세션의 Claude Code 버전이 이 오류를 너그럽게 처리했을 가능성이 있다(확인 불가 — 추정).

`model: fable` 은 원인이 아니다(파싱 결과 `verifier fable` 정상).
