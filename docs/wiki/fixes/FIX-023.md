# FIX-023 · 요청이 끝났을 때 DB 에 무엇이 남는지 실제 커밋으로 확인한다

발견: 2026-10-05 · 테스트 방식 점검 ⑦·⑧ | Refs: FIX-023 FIX-006 FIX-019 FIX-020 P5-loop P6-briefing 원칙8 원칙9

## 증상

- 테스트 1809개의 대부분은 `db_session`(세이브포인트 안에서 돌고 끝나면 롤백, FIX-006)으로 돈다. **실제 커밋 경계**(요청 하나가 끝났을 때 무엇이 남고 무엇이 사라지나)는 검증되지 않는다. 실제 커밋으로 도는 테스트는 동시성 6건(`test_briefing_select` 1 · `test_answer_concurrency` 2 · `test_upsert_concurrency` 3)뿐이다.
- 예: "DB 오류로 롤백된 요청은 trace 도 남지 않는다"(P5-loop 결정 H, 13-트러블슈팅 REL-02)는 코드를 읽어 안 사실이지 테스트로 고정된 사실이 아니다.
- 마이그레이션 down→up 왕복은 FIX-020 때 손으로 한 번 했을 뿐 CI 에 없다(점검 ⑧).

## 원인

FIX-006 이 테스트 격리를 위해 세이브포인트 픽스처를 표준으로 삼았고, 커밋 경계 자체를 보는 테스트 층이 따로 없었다.

## 결과 (커밋 해시 · 테스트)

커밋 해시: pending(커밋 전 — backend-agent 가 테스트·워크플로만 작성, 커밋·푸시는 메인 세션 몫).

- `tests/test_commit_boundaries.py`(신규, `pytestmark = pytest.mark.dbtest`) 1a~1d 전부 구현·통과.
  - 1a `test_chat_real_commit_persists_event_and_trace` — `get_session` 오버라이드 없이 `POST /chat` 1건을 보낸 뒤, **요청과 다른 새 `Session`** 으로 `events` 행(원문·타입)과 `agent_traces`(`loop_record` 포함) 행이 남았는지 확인.
  - 1b `test_chat_db_error_during_record_commits_nothing_and_leaves_no_trace` — 기록 단계(`add_event`)를 실제 시그니처를 유지한 채(게이트의 `inspect.signature` 대조를 깨지 않도록) `SQLAlchemyError` 를 내도록 monkeypatch. 응답은 500 `{"detail":{"code":"internal_error"}}`(예외 원문 미노출), 새 커넥션으로 조회하면 `events` 0행·`agent_traces` 0행(그 `session_id` 기준) — **알려진 한계**(P5-loop 01-plan 결정 H: `SQLAlchemyError` 는 라우트가 삼키지 않고 `get_session()` 전체 rollback 을 타므로 `loop_error` trace 조차 못 남긴다)로 docstring 에 명시. 결정 H 가 바뀌면 이 테스트를 의도적으로 고친다.
  - 1c `test_answers_resume_real_commit_persists_answer_and_resume_result` — `POST /chat`(→ `new_person` 되묻기) → `POST /answers/{id}` 왕복을 `get_session` 오버라이드 없이 돌린 뒤, 새 `Session` 으로 `pending_questions.answered_at`/`answer` 와 재개로 만들어진 인물·이벤트가 함께 커밋됐는지 확인.
  - 1d `test_run_briefings_real_session_scope_isolates_failed_schedule` — `app.db.session.session_scope()`(주기 작업·`default_run_once` 와 같은 경계)로 `run_briefings()` 를 실제로 돌려, 일정 2건 중 생성기가 실패한 1건만 `briefed_at IS NULL`·`briefing_compose` trace 없음으로 격리되고, 성공한 1건만 커밋(`briefed_at` 값·`briefing_compose` trace 1행·`briefing_error` trace 1행)되는지 확인.
  - 발견한 결함: 없음(제품 코드 무변경 — 네 테스트 모두 현재 동작을 그대로 고정/확인했다). 1b 는 "결함"이 아니라 이미 01-plan 결정 H 가 받아들인 트레이드오프를 테스트로 고정한 것.
- `.github/workflows/tests.yml` 리눅스 `pytest` job(매트릭스 3.13·3.14 둘 다 — 아직 공통 스텝으로 추가했으므로 두 버전 모두 적용됨) — pytest 단계 뒤에 `DATABASE_URL` 을 그 스텝의 `env:` 로만 `relationship_test` 로 겹쳐 써서 `alembic downgrade base` → `upgrade head` → `alembic check` 왕복을 테스트 DB 에서 실행. 개발 DB(`relationship`, job 수준 `env.DATABASE_URL`)는 건드리지 않는다. 로컬에서 같은 3단계를 테스트 DB(`POSTGRES_PORT=5433 POSTGRES_DB=relationship_test`)로 먼저 실행해 확인(`downgrade base` → `upgrade head` → `alembic check` → `No new upgrade operations detected.`).
- CI 결과(커밋 `125976a`, run 37400595262, 메인 세션 확인): `pytest (3.13)` · `pytest (3.14)` · `windows` 모두 success. 로그: `1813 passed` · 두 버전 모두 `Running downgrade 0001 -> ` 뒤 `No new upgrade operations detected.`(테스트 DB 왕복). 상태: 완료.
