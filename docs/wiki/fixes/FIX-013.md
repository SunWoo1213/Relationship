# FIX-013 · 커밋과 푸시가 한 명령에 있으면 커밋 후처리가 건너뛰어진다

발견: 2026-09-29 · FIX-012 커밋(`0c46913`) 직후, 사용자가 "승인 창이 안 떴다" 고 물어 확인하다 | Refs: FIX-013 FIX-011 FIX-009 L-003 verification 원칙8

## 증상

`git commit -F .claude/commit-draft.txt && git push origin dev2` 처럼 커밋과 푸시를 **한 Bash 명령에 묶어** 실행하자, 커밋 후처리가 전혀 일어나지 않았다.

커밋 `0c46913` 직후 관측:

| 항목 | 결과 |
|------|------|
| 커밋 자체 | 정상 (`0c46913`, 푸시도 반영됨) |
| `journal.md` 의 `COMMIT` 줄 | **생성 안 됨** (메인 세션이 수기로 넣었다) |
| `.claude/.commit-approved` 마커 | **지워지지 않고 남음** |
| `.claude/gitlog.md` 스냅샷 | 갱신 안 됨 |
| `PUSH-dev2` 줄 | 정상 생성 |

남은 승인 마커는 1회용인데 소비되지 않았다. 마커에는 그때 초안의 sha256 이 들어 있어 **다른** 초안으로는 `commit-guard` 가 막지만, **같은 초안이면 사용자 승인 없이 한 번 더 커밋될 수 있다.** 이번에는 사용자가 직접 지워 정리했다.

## 원인

`.claude/hooks/commit-cleanup.sh` 는 명령 문자열에 푸시가 보이면 푸시 갈래로 들어가 처리한 뒤 `exit 0` 한다. 커밋 처리 구간은 그 아래에 있어 도달하지 못한다.

```
if (명령에 git push 가 있나) {            # 26행
    if (dev:main)  … exit 0   fi          # 28~35행  ← exit 34행
    if (dev2:dev)  … exit 0   fi          # 38~46행  ← exit 45행
    if (dev2)      … exit 0   fi          # 49~54행  ← exit 53행
    exit 0                                # 55행
}                                         # 56행
... git commit 처리 (마커 삭제·COMMIT 기록·gitlog 갱신) ...   # 58~73행
```

갈래가 `if … fi` 세 개로 **나란히** 놓여 있고 `elif` 로 이어져 있지 않다는 점이 중요하다. 지금 배타를 만드는 것은 각 갈래 끝의 `exit 0` 이다.

훅은 "이 명령이 무엇인가" 를 **하나만** 고르는 구조였다. 한 명령이 두 가지 일을 할 수 있다는 것을 전제하지 않았다.

곁들여, 이 상황은 절차 위반이기도 하다. `HANDOFF.md` 주의 절에 "푸시·승격은 단독 Bash 호출" 이라고 적혀 있는데 메인 세션이 두 명령을 묶었다. 규칙을 지켰다면 나지 않았을 문제다. 다만 규칙에만 기대면 같은 일이 또 나므로 훅도 고친다.

FIX-011 에서 `commit-cleanup` 시험 10건을 새로 넣었는데도 못 잡았다. 시험이 모두 **단일 명령**만 넣었기 때문이다.

## 수정안 (파일 · 방식 · 회귀 테스트)

### ① 훅 구조: "먼저 걸리는 것 하나" → "해당되는 것 전부"

**`exit` 를 지우는 것이 아니라 갈래를 `if/elif` 로 바꾼다.** 2차본은 "`exit 0` 네 곳(34·45·53·55행)을 지운다" 고 썼는데, **지금 갈래의 배타를 만드는 것이 바로 그 `exit` 들이다.** 푸시 블록 안은 `if … fi` 가 **세 번 나란히** 놓인 구조이고(28~35 · 38~46 · 49~54행), 서로 `elif` 로 이어져 있지 않다. 그러니 `exit` 를 지우면 한 명령이 여러 갈래를 동시에 타고, 2차본이 같은 절에서 요구한 "배타 유지" 와 정면으로 어긋난다. verifier 가 격리 실험으로 확인했다 — `push origin dev2 && push origin dev2:dev` 에서 `PUSH` 와 `PUSH-dev2` 가 **둘 다** 기록되고 `.awaiting-decision` 까지 생겼다. 계획대로 구현하면 고치려던 결함 대신 **새 결함**이 생긴다. (verifier 2차 [필수] 1)

바꾸는 모양:

```
지금                          바꾼 뒤
if   (dev:main) … exit 0 fi   if   (dev:main) … 
if   (dev2:dev) … exit 0 fi   elif (dev2:dev) … 
if   (dev2)     … exit 0 fi   elif (dev2)     … 
exit 0                        fi
fi                            fi
                              (이어서 커밋 처리)
```

즉 **세 `if` 를 하나의 `if/elif/elif` 사슬로 합치고, 갈래 안의 `exit 0` 세 개(34·45·53행)와 블록 끝의 `exit 0`(55행)을 없앤다.** 배타는 `elif` 라는 구조가 보장하고, 흐름은 커밋 처리로 이어진다. 각 갈래 **안쪽**의 성공 판정(30·39·50행의 ref 비교)은 그대로 둔다.

**순서는 커밋 처리 → 푸시 처리** 로 둔다. 1차본은 "푸시 → 커밋으로 두면 시점 해석이 유지된다" 고 썼는데 **그 근거는 틀렸다.** 이 훅은 PostToolUse(`settings.json` 85~93행)라 Bash 명령 **전체가 끝난 뒤 한 번** 실행된다. 훅 안에서 어느 블록을 먼저 돌리든 `rev-parse HEAD`·`rev-parse origin/dev2` 는 같은 시점(명령 종료 후)을 본다. 즉 순서는 판정의 정확성에 영향이 없고 **journal 줄 순서만** 바꾼다. 실제로 일어난 순서(커밋 → 푸시)대로 남기는 것이 읽기에 맞으므로 커밋을 먼저 처리한다. (verifier [권고])

**순서 변경은 필수가 아니라 가독성 선택이다.** verifier 실험에서 순서를 바꾸지 않은 변이(푸시 → 커밋)도 정상 동작했다. 커밋을 먼저 처리하는 것은 journal 줄이 실제 순서대로 남게 하려는 것뿐이다. 순서를 바꾸면 **58~60행의 `|| exit 0` 세 줄을 블록으로 바꿔야 한다.** 지금은 "커밋 명령이 아니면 / 마커가 없으면 / 초안이 없으면" 각각 스크립트를 끝내는데, 그대로 두면 커밋 조건이 안 맞는 명령에서 푸시 처리까지 끊긴다. (verifier [권고] — 놓치기 쉬운 자리)

**푸시 하위 갈래(`dev:main` · `dev2:dev` · `dev2`)는 배타로 유지한다.** 한 명령에 푸시가 둘 있으면 더 구체적인 갈래 하나만 탄다. 2차본은 그 근거를 "판정이 서로 얽힌다" 고 적었는데 **틀렸다** — 39행은 `origin/dev` 를, 50행은 `origin/dev2` 를 각각 보므로 서로 다른 ref 이고 독립 판정이 가능하다. 배타를 택하는 진짜 이유는 **단순성과 절차상 미사용**이다. `SKILL.md` §6 은 푸시 명령을 각각 단독으로 제시하므로 두 푸시를 한 명령에 묶을 일이 없다. (verifier 2차 [권고])

배타의 대가: `push origin dev2 && push origin dev2:dev` 에서 **dev2 는 성공하고 dev2:dev 는 실패**하면(non-fast-forward 등) `dev2:dev` 갈래만 타므로 성공한 dev2 푸시가 journal 에 남지 않는다. `safety-guard.sh` 가 이 복합 명령을 허용하므로 도달 가능한 경로다. journal 정보 손실일 뿐 마커·게이트에는 영향이 없어 받아들인다. 리스크 절에 적었다.

각 처리는 지금의 성공 판정을 그대로 거친다 — 푸시는 원격 추적 ref 가 HEAD 와 같은지, 커밋은 HEAD 제목이 초안 첫 줄과 같은지. 명령에 글자만 있고 실제로 일어나지 않은 일은 여전히 기록하지 않는다.

### ② `test-guards.sh` 에 복합 명령 시험 6건

기존 12건은 전부 **단일 명령**이라 이 결함을 못 잡았다. 격리 임시 저장소를 쓰는 기존 틀(`cc_run`/`cc_count`/`cc_check`, `test-guards.sh` 203~224행)에 붙인다. `cc_count` 는 **누적** 건수를 세므로 케이스마다 기대값을 누적으로 잡거나 journal 을 비운다(verifier [권고]).

| # | 케이스 | 전제 | 기대 |
|---|-------|------|------|
| 1 | `commit && push origin dev2` | 초안 제목 = HEAD 제목, 커밋 마커 있음, `origin/dev2` = HEAD | `COMMIT` + `PUSH-dev2` **둘 다**, 커밋 마커 소비 |
| 2 | `commit && push origin dev2:dev` | 위 + 푸시 마커 있음, `origin/dev` = HEAD, **`.awaiting-decision` 없음(선행 `rm -f`)** | `COMMIT` + `PUSH` 둘 다(`\| PUSH \|` 누적 **2**), **커밋 마커·푸시 마커 모두 소비**, `.awaiting-decision` 생성 |
| 3 | `commit && push origin dev2`, 푸시만 실패 | 새 커밋을 하나 더 만들어 `origin/dev2` ≠ HEAD 로 두고 초안 제목을 새 HEAD 에 맞춤 | `COMMIT` 만, `PUSH-dev2` 증가 없음, 커밋 마커 소비 |
| 4 | 푸시 단독 (`push origin dev2`) | **초안 제목 = HEAD 제목 + 커밋 마커 있음**, **`origin/dev2` = HEAD 로 재동기화**(시험 3 이 HEAD 를 옮겼다) | `PUSH-dev2` 만, **커밋 마커는 그대로 남는다** |
| 5 | `commit; push origin dev2`, 커밋 실패 | 초안 제목 ≠ HEAD 제목, 커밋 마커 있음, `origin/dev2` = HEAD | `PUSH-dev2` 만, `COMMIT` 증가 없음, 마커 유지 |
| 6 | 푸시 두 개 (`push origin dev2 && push origin dev2:dev`) | **`origin/dev2` = HEAD 이고 `origin/dev` = HEAD**, 푸시 마커 있음, `.awaiting-decision` 없음 | 배타 유지 — `\| PUSH \|` +1 **이면서 `PUSH-dev2` 는 불변** |

**2번 전제의 `.awaiting-decision` 없음이 중요하다.** 기존 시험 6(`test-guards.sh` 274~282행)이 그 마커를 만들고 지우지 않는다. 새 케이스가 그 뒤에 붙으면 "생성됐다" 판정이 **훅이 아무 일도 안 해도 통과**한다. (verifier 2차 [필수] 2)

**4·6번의 ref 재동기화가 없으면 거짓 실패가 난다.** 시험 3 이 새 커밋을 만들어 HEAD 를 옮기므로 `origin/dev2`·`origin/dev` 는 옛 커밋을 가리킨 채 남는다. (verifier 2차 [필수] 3)

**6번은 `| PUSH |` 건수만으로는 배타 여부를 못 잡는다.** 배타가 깨진 상태에서도 `| PUSH |` 는 1건만 늘기 때문이다. `PUSH-dev2` 가 **늘지 않았다**는 것을 함께 봐야 한다. (verifier 2차 [필수] 1 의 일부)

**34행(`dev:main`) 갈래는 시험하지 않는다.** `commit && push origin dev:main` 은 `/commit release` 절차상 쓰지 않는 조합이고(승격은 단독 명령), 시험하려면 `dev` 브랜치와 승격 마커를 갖춘 별도 준비가 필요하다. `elif` 사슬로 바꾸면 세 갈래가 같은 구조를 공유하므로 1·2 가 통과하면 34행도 같은 이유로 고쳐진 것으로 본다. **미검증임을 여기 적어 둔다.** (verifier 2차 [권고])

**2번이 45행 `exit` 잔존을 잡는 유일한 시험이다**(verifier [필수] 2). 1차본은 이 케이스를 리스크 절에 약속해 놓고 시험 표에 넣지 않았다.

**4번의 전제가 핵심이다**(verifier [필수] 3). 전제를 적지 않으면 마커가 남은 이유가 "명령에 commit 이 없어서"(58행)인지 "초안 제목이 달라서"(65행)인지 구분되지 않아 **항상 통과하는 시험**이 된다. 초안 제목을 HEAD 와 같게 두고 마커를 둔 상태에서만, fallthrough 가 커밋 마커를 과잉 소비하지 않는다는 것을 검사할 수 있다.

### ③ 절차 문구 — 새로 적는 것이 아니라 **이유를 붙여 강화**한다

`docs/wiki/HANDOFF.md` 주의 절에는 "푸시·승격은 단독 Bash 호출" 이 **이미 있었다.** 그런데도 메인 세션이 어겼다 — 규칙만 있고 **왜** 그래야 하는지가 없어서다. 그래서 이유를 붙인다(이미 반영: "한 명령에 묶으면 `commit-cleanup` 이 푸시만 처리하고 끝나 마커가 남고 journal 줄이 빠진다").

`.claude/skills/commit/SKILL.md` 는 더 직접적인 원인을 품고 있다. §3 의 선택지 이름이 "커밋 + 실험 푸시" · "커밋 + 검증 승격" 이라 **한 명령으로 묶도록 유도한다.** §5(커밋)와 §6(푸시) 사이에 "푸시는 커밋과 **다른 Bash 호출로** 실행한다" 를 명시한다. (verifier [권고])

2차본은 "고치기 전 훅에서 시험 1·2·4 가 각각 실패해야 한다" 고 적었는데 **4 에 대해서는 거짓이다** — verifier 실험에서 시험 4 는 고치기 전 훅에서 통과했다. 글자 그대로 따르면 구현자가 "시험 4 가 안 실패한다" 는 거짓 소견을 내거나 통과를 실패로 보고하게 된다. 그래서 검출력 확인을 대상별로 A·B·C 로 나눴다. (verifier 2차 [필수] 4)

**변이 훅 실험 절차**(3~5 공통): 원본을 scratchpad 에 `cp` 로 백업 → 작업 트리의 훅을 편집 → `bash .claude/scripts/test-guards.sh 2>&1 | tee docs/wiki/fixes/evidence/FIX-013/<ts>-<변이이름>.txt` → **백업을 `cp` 로 되돌린다**. 되돌릴 때 `git checkout -- <경로>` 는 쓰지 않는다 — `safety-guard.sh` 가 막는다(`security.md` §2). 복원 뒤 원본과 `diff` 가 0 인지 확인한다. (verifier 2차 [권고])

## 기획서 정합성

수정이 원칙·D·S 를 바꾸는가? **바꾸지 않는다.** `.claude/hooks/` 와 `.claude/scripts/`, 그리고 절차 문서만 바뀐다. 제품 코드·데이터 모델·툴 시그니처는 무변경이다. L-003(dev 로 올린 뒤 멈춘다)의 동작도 그대로이며, 복합 명령에서도 `dev2:dev` 갈래가 대기 마커를 만드는지 시험으로 확인한다.

## 커밋 단위

훅(`commit-cleanup.sh`) + 시험(`test-guards.sh`) + 문서(FIX-013·SKILL.md·HANDOFF)를 **한 커밋**으로 낸다. 셋이 서로를 전제하므로 나누면 중간 상태가 깨진다. `SKILL.md` 는 §3 선택지 **이름은 그대로 두고** §5~§6 사이에 "푸시는 커밋과 다른 Bash 호출로" 문장만 넣는다(이름을 바꾸면 절차 설명 여러 곳을 함께 고쳐야 한다).

## 리스크

- **`exit` 를 지우기만 하고 `elif` 로 합치지 않는 것.** 그러면 배타가 깨져 한 명령에 두 줄이 기록된다(verifier 실험으로 확인). 회귀 표 5번이 이것을 잡는다.
- **배타 유지의 정보 손실**: `dev2` 성공 + `dev2:dev` 실패인 복합 명령에서 성공한 dev2 푸시가 기록되지 않는다(위 ① 절).
- **시험 간 잔존 상태**: `.awaiting-decision` 은 기존 시험 6 이 남기고, HEAD 를 옮기는 시험은 원격 추적 ref 를 낡게 만든다. 각 케이스 전제에 적었다.
- **변이 훅 복원**: `git checkout -- <경로>` 는 `safety-guard.sh` 가 막는다. scratchpad 백업 후 `cp` 로 되돌리고 `diff` 0 을 확인한다.
- **순서를 커밋 → 푸시로 바꾸면 58~60행의 `|| exit 0` 가 푸시 처리까지 끊는다.** 블록으로 바꿔야 한다.
- 커밋이 실패하고 푸시만 성공하는 경우(`;` 로 이은 명령)에도 각자의 성공 판정이 독립적으로 동작해야 한다 — 시험 5.
- 푸시가 둘 있는 명령에서 하위 갈래를 배타로 두기로 했으므로, `dev2` 와 `dev2:dev` 를 함께 민 명령은 한 줄만 남는다. 절차상 쓰지 않는 조합이지만 시험 6 으로 현재 동작을 고정한다.
- 1차 검증(verifier)에서 확인된 것: 사전 훅은 복합 명령을 이미 통과시킨다(`safety-guard.sh` 68~85행은 `[^;|&]*` 로 푸시 구간만, `commit-guard.sh` 46·56행은 `git commit` 만 본다). 실제로 `0c46913` 이 그렇게 통과했다. **사후 훅만 고치면 된다.**
- 과거에 후처리가 건너뛴 커밋: `git log` 160건 중 journal 에 해시가 없는 것이 **10건**이다(메인 세션 확인). verifier 는 12건으로 셌다(세는 기준 차이). 대부분 README·CI·병합 커밋이라 이 결함보다는 다른 기기나 GitHub 웹에서 만든 것으로 보이나 원인 분류는 하지 않았다. **이번 FIX 범위 밖**으로 두고 목록만 결과 절에 남긴다.
