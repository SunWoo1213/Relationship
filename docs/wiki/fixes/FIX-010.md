# FIX-010 · 브랜치를 세 단계로 바꾼다 — dev2 실험 → dev 검증 → main 배포

발견: 2026-09-29 · 사용자가 원하는 브랜치 구조를 다시 설명함 | Refs: FIX-010 FIX-009 FIX-008 L-001 L-003 security

## 증상

사용자가 원한 구조는 이렇다.

> dev2는 아무때나 막 푸시해서 실험하는 곳, dev는 실험을 통해서 어느 정도 검증된 애들을 두는 곳, main은 dev에서 끝난 애들을 올리는 곳.

그런데 FIX-009 로 구현해 둔 것은 **방향이 반대**였다. `dev` 가 작업 브랜치이고 `dev2` 는 `dev` 를 그대로 복사해 두는 백업(`git push origin dev:dev2`)이었다. 즉 dev2 가 dev 의 **하류**였는데, 사용자는 dev2 를 **상류**(실험이 먼저 쌓이는 곳)로 쓰려 했다.

어긋난 지점:

| | 그때 | 원하는 것 |
|---|------|----------|
| 허용 방향 | `dev → dev2` 한 방향 | `dev2 → dev` 로 올려보내는 길이 필요 |
| 커밋이 쌓이는 곳 | `dev` | `dev2` |
| 승인 마커·L-003 대기 | `dev` 푸시에 걸림 | **`dev2 → dev` 승격**에 걸려야 맞음 |
| 마커 없는 자유 푸시 | `dev2` | 그대로 맞음 |

## 원인

첫 지시("커밋마다 dev2 에도 푸시")의 표면만 보고 dev2 를 백업 사본으로 해석했다. 브랜치를 셋으로 나누려는 **목적**(단계별 신뢰도 구분)을 확인하지 않은 것이 원인이다. 자세한 것은 `lessons/L-001-dev-branch.md` 개정 절에 남겼다.

## 수정안 (파일 · 방식 · 회귀 테스트)

### 새 규칙

| 푸시 | 마커 | 뒤이어 |
|------|------|--------|
| `git push origin dev2` | 없음 | 아무 일 없음 (실험) |
| `git push origin dev2:dev` | `.push-approved` | L-003 대기 마커 생성 |
| `git push origin dev:main` | `.release-approved` | 대기 마커 해제, `RELEASE` 기록 |
| 그 밖 전부 (`origin dev` 직접 포함) | — | 거부 |

`origin dev` 직접 푸시를 막는 이유: dev 는 검증을 통과한 것만 들어오는 곳인데 직접 밀 수 있으면 검증 단계가 무의미해진다.

승격은 **통째로(fast-forward)** 한다. 버릴 실험은 dev2 에 `git revert` 커밋을 남긴 뒤 승격한다. cherry-pick 선별은 dev2 와 dev 를 항상 갈라지게 만들고, 정리하려면 강제 푸시 금지를 풀어야 해서 택하지 않았다(사용자 결정 A, 2026-09-29).

### 곁들여 고친 것 — 자가 점검 스크립트가 이 기기에서 깨져 있었다

`test-guards.sh` 를 돌리자 **실패 50건**이 나왔다. 두 가지 원인이 겹쳐 있었고 둘 다 Windows→Mac 이전에서 온 것이다.

1. 스크립트가 `python` 이름으로 인터프리터를 부른다(FIX-008 과 같은 뿌리). → 훅과 같은 `_py.sh` 탐지를 쓰게 했다. 못 찾으면 그냥 넘어가지 않고 실패로 끝낸다.
2. 시험 입력의 파일 경로가 `C:\Capstone2\...` 로 박혀 있다. Mac 에서는 "프로젝트 밖" 으로 취급돼 stage-gate 검사가 **조용히 통과**했다 — 즉 그 케이스들이 아무것도 검증하지 못하고 있었다. → 경로를 `$ROOT` 기준으로 바꿨다. 옛 기기 경로가 프로젝트 밖으로 취급되는지 확인하는 줄은 따로 하나 남겼다.
3. frontmatter 검사만 PyYAML 이 필요한데 맨 셸의 인터프리터에는 없다. → 그 검사에 한해 `.venv` 의 인터프리터를 먼저 찾아 쓰고, 없으면 skip 으로 알린다.

새 브랜치 규칙 케이스 5건(`dev2` 허용 2, `dev2:dev`·`dev2:main`·강제 푸시 거부 3)도 목록에 넣었다.

### 회귀 테스트(완료 판정 명령)

| # | 확인 | 기대 |
|---|------|------|
| 1 | `push origin dev2` | 허용 |
| 2 | `push origin dev2:dev`, 마커 없음 | 거부 |
| 3 | `push origin dev2:dev`, 마커 있음(격리 사본) | 허용 |
| 4 | `push origin dev` 직접 | 거부 |
| 5 | `push origin dev:main`, 마커 없음 | 거부 |
| 6 | 강제 푸시 · origin 아닌 원격 · 목록 밖 브랜치 | 거부 |
| 7 | `push origin dev:main`, 승격 마커 있음(격리 사본) | 허용 |

| 9 | `POSTGRES_PORT=5433 pytest -q -rs` | 1511 passed |

마커가 있어야 하는 3·7 번은 **격리된 사본을 ROOT 로 주어** 시험한다. 진짜 `.claude/.push-approved` 를 만드는 것은 스스로 승인을 위조하는 셈이라 금지돼 있다.

## 기획서 정합성

수정이 원칙·D·S 를 바꾸는가? **바꾸지 않는다.** `.claude/` 와 위키 문서만 바뀌고 제품 코드·데이터 모델·툴 시그니처는 무변경이다. L-003(dev 로 올린 뒤 멈춘다)의 뜻도 그대로이며, 그 시점이 "dev 푸시" 에서 "dev2→dev 승격" 으로 옮겨졌을 뿐이다.
