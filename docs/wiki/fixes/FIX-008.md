# FIX-008 · 훅이 파이썬 인터프리터를 못 찾으면 조용히 통과한다

발견: 2026-09-29 · P6-memory U1 커밋(`7564c5d`) 직후, 커밋 후처리가 돌지 않아 발견 | Refs: FIX-008 security L-001 L-003 L-004 원칙8

## 증상

`.claude/hooks/` 의 훅 9개(호출 지점 10곳)가 stdin JSON 을 `python -c` 로 파싱한다. 이 기기(macOS)에는 `python` 이라는 이름의 실행 파일이 없어 그 호출이 `command not found`(종료코드 127)로 끝나고, 파싱 결과가 **빈 문자열**이 된다. 각 훅은 값이 비면 검사를 건너뛰고 통과하도록 쓰여 있으므로, 결과적으로 **가드가 조용히 열린 상태**가 된다.

관측된 증상 세 가지:

- 세션 시작 로그 첫 줄이 `(source: unknown)` 으로 찍혔다 — `session-start.sh` 가 stdin 을 못 읽었다는 뜻이다.
- 커밋 `7564c5d` 뒤 1회용 승인 마커 `.claude/.commit-approved` 가 지워지지 않고 남았다. 마커가 남으면 다음 커밋이 사용자 승인 없이 통과할 수 있다.
- 같은 커밋 뒤 `docs/wiki/journal.md` 의 `COMMIT` 줄이 자동으로 생성되지 않아 메인 세션이 수기로 넣었다.

재현(증거 `fixes/evidence/FIX-008/20260929-0010-before-python-detect.txt`):

```
$ command -v python
(없음 — 종료코드 1)
$ printf '{"tool_input":{"command":"git add -A"}}' | python -c '...'
command not found: python
$ 같은 입력을 python3 로
git add -A
```

값이 비면 통과하는 자리(발췌):

```
safety-guard.sh:32    [ -n "$cmd" ] || exit 0
stage-gate.sh:25      [ -n "$fp" ]  || exit 0
delegate-guard.sh:23  [ -n "$sub" ] || exit 0
```

## 원인

훅이 Windows 환경에서 작성됐다. Windows 에서는 python.org 설치본이 `python.exe` 를 만들고 `python` 이 표준 이름이며 `python3` 는 없거나 Microsoft Store 를 여는 스텁인 경우가 많다. 반대로 최근 macOS 에는 `python` 이 아예 없고(Apple 이 macOS 12.3 에서 Python 2 를 제거했다) `python3` 만 있으며, `python` 이라는 이름은 가상환경(venv)을 활성화했을 때만 생긴다. 훅은 venv 밖의 맨 셸에서 실행되므로 macOS 에서는 항상 실패한다.

즉 이름 하나에 의존한 것이 원인이며, 어느 한쪽 이름으로 바꾸는 것은 해결이 아니다 — `python3` 로 바꾸면 Windows 가 같은 방식으로 깨진다. 더 근본적인 문제는 인터프리터를 찾지 못했을 때 **가드가 닫히지 않고 열리는** 실패 방향이다.

## 수정안 (파일 · 방식 · 회귀 테스트)

**신설** `.claude/hooks/_py.sh` — 훅 공용 인터프리터 탐지. 후보를 `python` → `python3` 순으로 보되, 존재 여부(`command -v`)만이 아니라 **실제로 한 번 실행해 본다**(`"$c" -c 'pass'`). 순서를 이렇게 두는 이유는 Windows 에서 `python` 이 먼저 성공하므로 Microsoft Store 스텁인 `python3` 를 아예 건드리지 않기 때문이다. macOS 에서는 `python` 이 없어 `python3` 로 내려간다.

**수정** 훅 9개 — `_py.sh` 를 불러오는 한 줄을 넣고, `| python -c` 를 `| "$HOOK_PY" -c` 로 바꾼다(10곳). 파싱에 쓰는 파이썬 코드 자체와 각 훅의 판정 규칙은 바꾸지 않는다.

**실패 방향은 훅 성격별로 다르게 둔다.**

| 성격 | 해당 훅 | 인터프리터를 못 찾았을 때 |
|------|---------|--------------------------|
| 차단형 가드 | `safety-guard` · `secret-guard` · `stage-gate` · `commit-guard` · `delegate-guard` | **deny** — 조용히 여는 현재 동작이 결함이므로 닫는 쪽으로 실패한다 |
| 종료 가드 | `handoff-check` | 경고만 하고 통과 — Stop 훅이 계속 막으면 턴을 끝낼 수 없어 갇힌다 |
| 보조 | `commit-cleanup` · `session-start` · `precompact` | 경고만 하고 통과 — 차단 권한 자체가 없다 |

**건드리지 않는 것**: `.claude/settings.json`(훅 등록), 각 훅의 판정 규칙, 제품 코드 전부.

**회귀 테스트(완료 판정 명령)**

| # | 확인할 것 | 명령 | 기대 |
|---|----------|------|------|
| 1 | 탐지 동작 | `bash -c '. .claude/hooks/_py.sh; echo "$HOOK_PY"'` | 이 기기에서 `python3` |
| 2 | 파싱 복구 | `_py.sh` 로 고른 인터프리터에 훅과 같은 입력을 넣는다 | `git add -A` 가 그대로 출력 |
| 3 | 커밋 후처리 | 이 FIX 의 커밋 직후 `ls .claude/.commit-approved` · `tail -1 docs/wiki/journal.md` | 마커 없음 · `COMMIT` 줄 자동 생성 |
| 4 | 세션 훅 | 다음 세션 시작 로그 | `(source: unknown)` 이 아닌 실제 값 |
| 5 | 제품 회귀 | `POSTGRES_PORT=5433 pytest -q -rs` | 1511 passed, skip 0 (훅은 제품 코드와 무관함을 확인) |

3·4 는 이 커밋 이후에만 관측할 수 있으므로 `## 결과` 에 적는다.

## 기획서 정합성

수정이 원칙·D·S 를 바꾸는가? **바꾸지 않는다.** 이 수정은 `.claude/hooks/` 안에서만 일어나며 제품 코드(`app/`·`tests/`·`alembic/`)와 데이터 모델·툴 시그니처·임계치에 손대지 않는다. 기획서 결정 카드(D)와 명세 카드(S)는 제품의 동작을 정하는 문서이고, 훅은 그 문서를 지키게 만드는 개발 하네스다. 따라서 CR 이 아니라 FIX 가 맞다.

다만 이 수정은 `docs/wiki/security.md` 가 전제하는 집행력을 되살리는 것이므로, 그 카드에 "훅은 파이썬 인터프리터를 찾지 못하면 통과시키지 않고 차단한다" 한 줄을 더한다.

## 결과 (커밋 해시 · 테스트)

구현: `.claude/hooks/_py.sh` 신설(탐지 순서 `python` → `python3`, 각 후보를 `-c 'pass'` 로 실제 실행해 확인) + 훅 9개에서 호출 지점 10곳 교체. 차단형 5개는 `$HOOK_PY` 가 비면 deny, 통과형 4개는 `${HOOK_PY:-false}` 로 기존 동작을 유지하며 stderr 에 경고. `docs/wiki/security.md` 에 §7 신설.

검증(증거 `fixes/evidence/FIX-008/20260929-0040-after-python-detect.txt` — 대조군은 `git show HEAD:<훅>` 으로 수정 전 스크립트를 같은 입력으로 실행):

| 훅 | 입력 | 수정 전 | 수정 후 |
|----|------|--------|--------|
| `safety-guard` | 전체 스테이징 명령(규칙 D) | 출력 없음 = 통과 | deny |
| `commit-guard` | 초안 파일을 쓰지 않는 커밋 | 출력 없음 = 통과 | deny |
| `secret-guard` | `.env` 쓰기 | 출력 없음 = 통과 | deny |

부수 발견: `delegate-guard` 를 처음 시험했을 때 남아 있던 1회용 마커 `.claude/.stage-approved` 가 소비됐다. P6-memory U1 위임 당시 훅이 고장나 있어 마커가 지워지지 않고 남아 있던 것으로, 그 상태에서는 승인 없는 위임이 한 번 더 통과할 수 있었다. 같은 이유로 `.claude/.commit-approved` 도 U1 커밋 뒤 남아 있었고, 이 FIX 의 커밋 절차에서 새 초안과 해시가 달라 `commit-guard` 가 거부하게 되므로 재승인으로 정상화된다.
