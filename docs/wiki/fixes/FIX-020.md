# FIX-020 · "한 인물·한 키에 한 행" 같은 규칙을 DB 가 지키게 한다(UNIQUE 제약)

발견: 2026-10-05 · 복기 자료 작성 중 코드 관찰 → 테스트 방식 점검 2번 항목 | Refs: FIX-020 P1-schema P2-tools P6-memory P7-push S3.1 D6 원칙1

## 증상

코드는 세 곳에서 "같은 것이 이미 있으면 새 행을 만들지 않는다" 를 **애플리케이션이 조회 후 삽입**으로 지킨다. DB 에는 기본키 외 UNIQUE 제약이 0개다(`app/db/models.py` grep `UniqueConstraint|unique=True` → 0).

| 자리 | 코드 | 의도된 규칙 |
|---|---|---|
| 사실 | `app/memory/promote.py::_upsert_fact`(130행), 툴 `update_person` | 인물당 키 하나(결정 D-6) |
| 별칭 | `app/tools/persons.py` 별칭 upsert(334행~) | 인물당 같은 문자열 하나(D6 "격상만") |
| 구독 | `app/push/subscriptions.py::save_subscription`(P7 U2) | 사용자당 같은 endpoint 하나(P7 결정 F) |

두 요청이 동시에 오면 둘 다 "없음" 을 읽고 둘 다 삽입해 **중복 행**이 생긴다. 그 뒤 `_upsert_fact` 의 `.one_or_none()` 은 `MultipleResultsFound` 예외를 내 승격이 실패하고(`memory_error`), 구독은 같은 알림이 두 번 간다. 재현 테스트 없음.

개발 DB 확인(2026-10-05, 읽기 전용): 세 조합 모두 중복 행 0 — 제약을 걸 수 있는 상태.

## 원인

P1-schema 가 스키마 v2 의 열·FK·CHECK 만 만들고 upsert 키의 유일성은 코드 규약으로 남겼다. 동시성이 낮은 1인 개발 환경이라 드러나지 않았다.

  - `app/db/models.py` -- `UniqueConstraint("person_id","key")`(PersonFact)
    · `("person_id","alias")`(PersonAlias) · `("user_id","endpoint")`(PushSubscription).
    `name=` 은 일부러 지정하지 않는다 -- `app/db/base.py` 의 `uq` naming_convention
    템플릿(`"uq_%(table_name)s_%(column_0_N_name)s"`)은 `%(constraint_name)s` 토큰이
    없어, `name` 을 지정하면 그 값이 최종 이름이 되어 버리고 convention 이 적용되지
    않는다(실측 확인, `ck`/`fk` 템플릿과 다른 점 -- 코드 주석에 남겼다). 최종 이름:
    `uq_person_facts_person_id_key` · `uq_person_aliases_person_id_alias` ·
    `uq_push_subscriptions_user_id_endpoint`.
  - `alembic/versions/0002_unique_upsert_keys.py`(신규) -- upgrade 전 세 조합
    각각 `GROUP BY ... HAVING count(*) > 1` 로 중복을 검사해 있으면 `RuntimeError`
    로 멈춘다(자동 삭제 금지, 메시지에 테이블 이름과 중복 그룹 수만). 이어서
    제약 3개 생성. downgrade 는 제약 3개 제거.
  - `app/memory/promote.py::_upsert_fact` -- "조회 후 분기"를 `INSERT ... ON
    CONFLICT (person_id, key) DO UPDATE` 한 문장으로 교체. `confidence` 는
    `CASE WHEN person_facts.value = EXCLUDED.value THEN person_facts.confidence
    ELSE EXCLUDED.confidence END` 로 "값이 같으면 유지, 다르면 갱신"이라는 기존
    3분기(created/same/updated) 의미를 그대로 보존했다. `action`/`previous_value`
    는 upsert 문 **이전에** 읽은 "이전 값 추정치"로 판정한다(트레이스 표시용 --
    아주 좁은 동시성 창에서는 실제 직전 값과 어긋날 수 있지만, 저장되는 값·행
    개수는 원자적 SQL 문이 전적으로 결정하므로 항상 정확하다). `xmax = 0` 트릭
    (`RETURNING id, (xmax = 0) AS inserted`)으로 신규/충돌 분기.
  - `app/tools/persons.py::_add_alias` -- 먼저 평범한 SELECT 로 존재를 확인해
