# FIX-031 · Windows CI 의 훅 자가 시험이 session-start 시험에서 멈춘다

발견: 2026-10-11 · P8-frontend U0 커밋 `440a0e5` 의 CI run 38111227562 windows job | Refs: P8-frontend FIX-022 L-001

## 증상

- run 38111227562: pytest(3.13)·(3.14) success, **windows job 이 `Run bash .claude/scripts/test-guards.sh` 단계에서 33분 넘게 끝나지 않음**(직전 run 38065630404 `2341f9e` 는 같은 job 이 2분 49초). 워크플로에 `timeout-minutes` 가 없어 기본 6시간까지 돈다 → 사용자 승인 뒤 `gh run cancel`(결론 cancelled).

  ```
  04:22:05.0585730Z ok   allow  marker=frontend-agent, frontend-agent allowed (consumed)   ← U0 새 시험은 전부 ok
  04:22:05.3617845Z ok   handoff-check passes when stop_hook_active
  04:22:05.3618549Z == session-start 출력 존재 ==
  (이후 출력 없음 — 취소까지 약 33분)
  ```

- U0 에서 넣은 새 시험(케이스 6·7, `web/x.ts` 거부, frontend-agent 위임 3줄)은 Windows 에서도 전부 ok — **멈춤은 U0 새 시험이 아니라 그 뒤 기존 `session-start` 시험(test-guards.sh 488~490행)**.

## 원인 (근본 원인 미확정 — 가설)

488~490행:
```bash
out="$(echo '{"source":"resume"}' | bash "$H/session-start.sh" | head -n 1)"
```
`head -n 1` 은 첫 줄을 읽고 파이프를 닫는다. 리눅스·Mac 에서는 남은 출력을 쓰려던 쪽이 SIGPIPE 로 곧바로 끝나지만, Windows Git Bash(MSYS)에서는 파이프 닫힘이 쓰는 쪽(`session-start.sh` 안의 `git`·파이썬·`gitlog.sh --write` 하위 프로세스)에 SIGPIPE 로 전달되지 않거나 늦게 전달되어 쓰기에서 막힐 수 있다. 출력이 파이프 버퍼보다 작으면 드러나지 않는데, session-start 출력은 HANDOFF·journal 꼬리를 그대로 싣기 때문에 커밋마다 길이가 바뀐다(로컬 Mac 기준 지금 12,417바이트). U0 커밋에서 HANDOFF 가 길어진 것이 계기일 수 있다 — **확인 안 됨**. 같은 커밋 재실행으로 재현되는지도 보지 않았다(간헐일 수 있음).

## 수정안 (파일 · 방식 · 회귀 테스트)

1. `.claude/scripts/test-guards.sh` 488~490행 — 파이프 중간에서 읽기를 끊지 않는다. session-start 출력을 **끝까지 받아** 변수에 담은 뒤 첫 줄을 고른다:
   `full="$(echo '{"source":"resume"}' | bash "$H/session-start.sh")"; out="$(printf '%s\n' "$full" | head -n 1)"` (판정 문자열 `세션 재개` 는 그대로).
   같은 `… | bash 훅 | head` 형태가 test-guards 안에 더 있는지 grep 해 같은 방식으로 맞춘다(있으면 목록을 03-log·결과에 남김).
2. `.github/workflows/*.yml` windows job(및 리눅스 job)에 `timeout-minutes: 20` — 다시 멈추면 6시간이 아니라 20분 안에 **실패**로 드러나게 한다(직전 정상 소요 약 3분).
3. 회귀 판정: 로컬 `bash .claude/scripts/test-guards.sh` 실패 0 · 푸시 뒤 CI run 의 **windows job success**(`gh run view <id>`) — 이 run 이 U0 의 Windows 확인(R-U0-4)도 겸한다. 근본 원인 판정: 수정 뒤 windows job 이 정상 시간(수 분)에 끝나면 가설과 일치, 또 멈추면(20분 실패) 가설이 틀린 것 → 다시 사용자에게 보고.
