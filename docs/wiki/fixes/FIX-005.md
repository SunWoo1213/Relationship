# FIX-005 · 에이전트가 시각을 UTC 로 계산해 "어제 저녁"이 한국 시간 새벽 3시로 저장된다

발견: 2026-09-25 · P5-loop 판정 표 8행 실서버 확인(메인 세션, 실 OpenAI) | Refs: FIX-005 P5-loop S3.4 원칙8 원칙9

## 증상

실서버에서 "어제 대학 동기 서준이랑 저녁 먹었어"를 보내고 새 인물 질문에 답하자 사건이 저장됐다. 그런데 사건 시각이 한국 시간 저녁이 아니라 **다음 날 새벽 3시**다(`docs/wiki/packages/P5-loop/evidence/20260925-2325-row8-db-check.txt`):

```
 type |   content   |            raw_utterance            |      occurred_at
------+-------------+-------------------------------------+------------------------
 meal | 저녁 먹었어 | 어제 대학 동기 서준이랑 저녁 먹었어 | 2026-09-24 18:00:00+00
```

`2026-09-24 18:00+00` 은 한국 시간(KST, UTC+9)으로 **9월 25일 03:00** 이다. 사용자가 말한 "어제 저녁"은 9월 24일 18시 무렵(KST), 곧 `2026-09-24 09:00+00` 이어야 한다.

## 원인

코드 어디에도 **사용자 시간대**라는 개념이 없다. 모든 시각이 UTC 로 계산된다.

1. `app/tools/context.py:104` — `ctx.now()` 기본값이 `datetime.now(timezone.utc)` 다.
2. `app/agent/loop.py:786` — 인식 단계가 이 UTC 시각을 그대로 프롬프트에 넣는다(`app/agent/propose.py:222` `현재 시각(now): "{now.isoformat()}"` → `...+00:00`).
3. LLM 은 받은 기준 시각대로 "어제 저녁"을 **UTC 기준 18시**로 바꾼다. 결과는 `2026-09-24T18:00:00`(오프셋 없음) 또는 `...+00:00` 이다.
4. `app/agent/propose.py:241` `_parse_iso_datetime` 은 `datetime.fromisoformat` 만 한다. 오프셋이 없는 값은 시간대 없는 datetime 이 된다. PostgreSQL `timestamptz` 는 이를 세션 시간대(UTC)로 해석해 `18:00+00` 이 된다.

**같은 원인의 두 번째 증상(코드로 확인, 실측 전)**: `app/agent/loop.py:686` `_schedule_candidates(now)` 는 "`now` 와 같은 tzinfo 로 내일·모레 저녁 7시"를 만든다. `now` 가 UTC 라서 칩에는 "저녁 7시"라고 보이지만 저장값은 `19:00+00`, 곧 **KST 새벽 4시**다. 날짜도 어긋날 수 있다. KST 오전 0~9시에는 UTC 날짜가 하루 전이므로, 이때 말한 "내일"과 "어제"가 하루씩 밀린다.

**영향**: P6 의 반복 패턴 규칙("90일 내 3회")과 브리핑("만남 직전")은 날짜·시각에 기대므로, P6 착수 전에 고쳐야 한다. 이미 저장된 확인용 행(개발 DB)은 되돌리지 않는다(원칙8, 개발 데이터).

## 수정안 (파일 · 방식 · 회귀 테스트)

**원칙: DB 에는 계속 UTC(`timestamptz`)로 저장한다. "사람이 말한 시각"을 해석하는 자리에서만 사용자 시간대를 쓴다.**

| # | 파일 | 방식 |
|---|------|------|
| 1 | `app/settings.py` | `APP_TIMEZONE` 설정 추가(기본 `Asia/Seoul`, 환경변수로 덮어씀) + `user_timezone() -> ZoneInfo`. 잘못된 이름이면 기동 시 명확한 오류를 낸다. `.env.example` 에 키 이름만 추가한다. |
| 2 | `app/agent/loop.py` | 인식 단계 프롬프트에 넘기는 `now` 와 `_schedule_candidates` 의 기준 시각을 `ctx.now().astimezone(user_timezone())` 로 바꾼다. 칩 문구와 저장값이 같은 "현지 저녁 7시"를 가리키게 한다. `ctx.now()` 자체(UTC)는 바꾸지 않는다. `occurred_at` 이 없을 때 쓰는 대체값 `now` 는 절대 시각이라 그대로 둔다. |
| 3 | `app/agent/propose.py` | `_parse_iso_datetime` 이 **오프셋 없는** 값을 받으면 사용자 시간대를 붙인다(`replace(tzinfo=…)`). 오프셋이 있는 값은 그대로 둔다. 시간대는 인자로 받는다(모듈 전역 상태 금지). 프롬프트에 "now 와 같은 오프셋을 붙인 ISO 8601"을 요구하는 문장을 더한다. 프롬프트는 안내일 뿐이고, 실제 보정의 단일 출처는 파서다(원칙1 "프롬프트 의존 금지"와 같은 태도). |
| 4 | `requirements.txt` | `tzdata` 를 고정 버전으로 추가한다. Windows와 슬림 컨테이너에도 IANA 시간대 DB 가 있게 하기 위해서다. |
| 5 | 테스트 | 새 `tests/test_agent_timezone.py`(파일명은 구현 시 registry grep 후 확정). ① 가짜 제안기가 오프셋 없는 `"2026-09-24T18:00:00"` 을 주면 저장된 `events.occurred_at` 이 `2026-09-24 09:00+00` 이다. ② `+09:00` 이 붙은 값은 그대로 저장된다. ③ `+00:00` 이 붙은 값은 바꾸지 않는다(오프셋이 있으면 존중). ④ 고정 `now = 2026-09-24T23:30+00`(KST 25일 08:30)일 때 일정 후보가 KST 26·27일 19:00 이고, 칩 문구의 날짜와 일치한다. ⑤ 인식 프롬프트의 now 문자열이 `+09:00` 이다. ⑥ `APP_TIMEZONE` 을 바꾸면 결과도 따라 바뀐다. ⑦ 잘못된 시간대 이름은 오류를 낸다. |

회귀: `POSTGRES_PORT=5433 python -m pytest -q tests/`(전체, skip 0) + 기존 `tests/test_agent_loop.py`·`tests/test_api_answers_resume.py` 의 일정 후보 단언이 UTC 를 가정했다면 **기대값을 KST 기준으로 고친다**(단언을 지우지 않는다). 실서버 재확인: 같은 발화로 `occurred_at` 이 `2026-09-24 09:00+00`(= KST 18:00) 부근인지 psql 로 확인한다. 실제 AI 호출이라 서버 기동은 사용자가 한다.

**설계 판단(기존 테스트 기대값을 고친 곳과 이유)**
`test_run_turn_add_event_naive_datetime_is_caught_as_failed`(R-24 "기록
단계 실패가 다음 제안을 막지 않는다") 는 원래 오프셋 없는 ISO
**문자열**을 트리거로 썼다 -- 그 문자열이 `datetime` 으로는 바뀌지만
naive 라서 `add_event` 가 거절했다. FIX-005 이후 오프셋 없는 문자열은
`_convert_datetime_args` 가 사용자 시간대를 붙이므로 더 이상 naive 가
아니게 되어, 같은 입력으로는 이 테스트가 의도한 실패 경로(ToolError →
`failed[]`)를 더는 재현하지 못한다. 그렇다고 이 테스트가 지키던 회귀
(제안 하나의 실패가 턴 전체를 막지 않는다)를 지울 이유는 없다 -- 트리거를
raw naive `datetime` **객체**(문자열이 아니므로 `_convert_datetime_args`
의 `isinstance(value, str)` 분기를 타지 않아 시간대 보정 대상이 아니다)
로 바꿔 같은 방어(naive 가 어떤 경로로든 `add_event` 까지 닿으면 여전히
거절된다)를 그대로 확인했다. 단언(`assert`)은 하나도 지우지 않았다.
