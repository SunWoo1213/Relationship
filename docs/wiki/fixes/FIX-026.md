# FIX-026 · 사실 값을 바꾸면 updated_at 도 갱신한다(FIX-020 회귀) · 패턴 사실 저장도 ON CONFLICT 로

발견: 2026-10-06 · verifier 사후 검토 `docs/wiki/fixes/review-FIX-018-025.md` [필수] F-20-1 · [권고] R-20-1 | Refs: FIX-026 FIX-020 FIX-023 S3.1 S3.5 D14 P6-memory P6-briefing 원칙9

## 증상

- **F-20-1**: FIX-020(`7459925`)이 사실 저장을 `INSERT … ON CONFLICT DO UPDATE` 로 바꾸면서, SQLAlchemy 가 `Column.onupdate`(`app/db/models.py` 157~161행 `updated_at … onupdate=func.now()`)를 `set_` 에 적용하지 않아 SET 절에서 `updated_at` 이 빠졌다(컴파일 SQL: `… DO UPDATE SET value = …, confidence = CASE … END RETURNING …`). 재현(테스트 DB, 커밋 2회, `evidence/20261006-1429-review-fix020-updated-at.txt`): 값 '등산'→'클라이밍' 뒤 `updated_at advanced after value change?: False`, ORM 경로는 `True`. 자리: `app/memory/promote.py::_upsert_fact`(174행 `set_`) · `app/tools/persons.py::update_person`(610행 `set_`).
- 영향: `updated_at` 은 브리핑 입력에 노출(`app/briefing/inputs.py:134`, `app/tools/briefing.py:93`)되고 정렬 기준(`inputs.py:101`, `memory/patterns.py:133`, `memory/direct_facts.py:95`) — "가장 최근 사실" 판단이 틀어진다.
- 테스트가 놓친 이유: `updated_at` 전진을 단언한 테스트가 없었고, `now()` 는 트랜잭션 시작 시각이라 세이브포인트 롤백 테스트로는 재현 불가(FIX-023 의 커밋 경계 층이 필요했던 이유와 같다).
- **R-20-1**: `app/memory/patterns.py`(128~170행)의 패턴 사실(`pattern:{type}`) 저장은 여전히 "조회 후 삽입". FIX-020 의 UNIQUE 제약 이후 동시 실행 시 조용한 중복 대신 `IntegrityError` → 500 이 된다.

## 원인

FIX-020 이 ORM 단위 작업을 Core 문으로 바꾸며 ORM 의 `onupdate` 훅을 잃었고, 같은 테이블의 네 번째 저장 자리를 놓쳤다. 검증자 리뷰 없이 커밋됐다(review R-공통-1).

### 같은 값 재저장 시 동작 — 무엇으로 정했고 근거는

재현 전에 직접 실험(2건, 테스트 DB `relationship_test`)으로 FIX-020
이전 ORM 코드의 실제 동작을 확인했다:

1. **`existing.value = 같은값`(update_person 의 "분기 없이 항상 대입"
   패턴 재현)** -- `f in session.dirty` 는 `True` 이지만, 커밋 후
   `updated_at` 은 **전진하지 않았다**. SQLAlchemy 유닛오브워크가 대입
   전후 값을 비교해 **모든 컬럼이 실제로 같으면 UPDATE 문 자체를 내지
   않기** 때문이다(`onupdate` 는 UPDATE 문이 나갈 때만 호출된다).
2. **`value` 는 같고 `confidence` 만 다른 값으로 대입** -- 이번엔
   `updated_at` 이 **전진했다**. 즉 "대입하는 모든 컬럼이 기존 값과
   같을 때만" UPDATE 가 생략된다 -- 컬럼 하나라도 실제로 다르면 그 행은
   UPDATE 되고, `onupdate` 가 걸린 `updated_at` 도 함께 전진한다.

`app.memory.promote._upsert_fact`(FIX-020 이전)는 "값이 같으면 분기
자체를 타지 않고 `.value`/`.confidence` 를 건드리지 않는다"는 명시적
조건이 있었으므로 1번 실험과 그대로 일치한다 -- CASE 조건은 `value`
비교 하나로 충분하다(`confidence` 는 그 분기 안에서 아예 안 바뀌므로).

`app.tools.persons.update_person` 의 facts 경로(FIX-020 이전)는 값이
같아도 `.value`/`.confidence` 를 **항상** 대입했지만(분기 없음), 실험
1·2가 보여주듯 그 무조건 대입이 실제 UPDATE 로 이어지는지는 SQLAlchemy
가 대입 전후 값을 비교해서 결정한다 -- 그래서 이 경로를 ON CONFLICT 로
옮긴 CASE 조건은 `value`·`confidence` **둘 다** 이전과 같을 때만
`updated_at` 을 유지한다(`and_(...)`). 이번 호출의 `confidence` 는 항상
`DEFAULT_FACT_CONFIDENCE` 상수이므로, 실무에서는 "값이 같으면 사실상
유지"가 되지만(기존에 저장된 confidence 가 이미 같은 상수이므로),
과거에 어떤 이유로 confidence 가 다른 값으로 저장돼 있었던 경우까지
정확히 옛 ORM 과 같은 동작을 재현한다.

### 4) mypy 기준선 변경 — 이유

`app/memory/patterns.py` 의 새 `INSERT ... ON CONFLICT ... RETURNING`
문의 `stmt` 변수가 `app/memory/promote.py`·`app/push/subscriptions.py`
가 이미 기준선에 올려 둔 것과 **같은 종류**(`[var-annotated] Need type
annotation for "stmt"`)의 mypy 제약을 똑같이 만났다 -- 세 파일 모두
`pg_insert(...).values(...).on_conflict_do_update(...).returning(...)`
체인이고, 같은 패턴을 쓰는 두 선례가 이미 기준선에 주석 없이 올라가
있다(진짜 결함이 아니라 체이닝된 SQLAlchemy Core 제네릭 타입을 mypy 가
추론하지 못하는 것으로 이미 판단된 사례). `scripts/mypy_check.py --run
--update-baseline` 으로 재생성해 **그 항목 한 줄만** 추가됐음을
`git diff scripts/mypy_baseline.txt` 로 확인했다(그 밖의 내용은 바뀌지
않았다).

(최초 `--update-baseline` 실행을 `--run` 없이 호출하는 실수로 기준선
전체가 0건으로 잘못 덮어써졌다 -- `git show HEAD:scripts/mypy_baseline.txt`
로 원문을 Write 툴로 그대로 복구한 뒤 `--run --update-baseline` 으로
다시 생성했다. 복구 직후 `git diff` 가 빈 출력임을 확인해 원상태 일치를
검증했다.)
