# FIX-017 · 사실 키의 뜻을 LLM 에게 알려 "못 먹어" 가 likes 로 가지 않게 한다

발견: 2026-09-30 · FIX-015 실 LLM 확인(journal 2026-09-30 01:00, trace 181) — P6-briefing 01-plan 결정 G 에서 "별개 FIX 후보" 로 넘김 | Refs: FIX-017 P5-loop P6-memory P6-briefing S3.2 S3.5

## 증상

"지현이는 매운 음식을 **못 먹어**" 가 `likes = 매운 음식` 으로 저장됐다(trace 181, 같은 호출의 `dislikes = 고수` 는 맞음). 2026-09-29 에는 회사명(카카오)이 `workplace` 가 아니라 `job` 에 들어갔다. **어휘(9키)는 지켰는데 값이 엉뚱한 키로 간다.**

피해: 브리핑(P6-briefing)이 이 사실을 근거로 쓰면 "매운 음식점을 예약하세요" 같은 **정반대 제안**이 나온다. P6-briefing 은 원문을 함께 보여 줘서(결정 G) 실 확인 5회 동안 정반대 제안은 없었지만, **근거 라벨은 여전히 `likes`** 였고 인물 카드(P8)는 원문 없이 키·값을 그대로 보여 준다.

## 원인

LLM 이 받는 것은 **키 이름뿐**이다.

| 경로 | 키를 알려 주는 자리 | 뜻 설명 |
|---|---|---|
| 루프 제안기 `app/agent/propose.py` | `PROPOSAL_ARG_SCHEMA.facts.key` 의 `enum`(FIX-015) | **없음** — 프롬프트(`build_propose_prompt`)에 사실·키 이야기가 한 줄도 없다 |
| 승격 추출기 `app/memory/extract.py` | `build_extract_prompt` system "뽑을 수 있는 키는 다음 9종뿐이다: job, workplace, …" | **없음** — 이름만 나열 |

키의 한국어 뜻은 `app/memory/types.py` 346~353행 **코드 주석**에만 있다(`likes`(좋아하는 것)·`dislikes`(싫어하는 것·피할 것)·…) — LLM 은 이것을 보지 못한다. "못 먹어" 처럼 대상 명사(매운 음식)만 눈에 띄고 부정이 동사에 붙는 한국어 문장에서, 뜻 설명 없는 영어 키 `likes`/`dislikes` 는 쉽게 헷갈린다.

### 이 수정이 하지 않는 것
- **거부는 하지 않는다** — 프롬프트 유도일 뿐, 게이트·`update_person` 은 키와 값의 의미를 검사하지 않는다(그건 LLM 판단이 필요해 원칙1 구조와 맞지 않음).
- **이미 저장된 잘못된 행(`likes=매운 음식` 등)은 고치지 않는다**(확인용 행 보존 관례). 브리핑은 원문 동봉(결정 G)으로 계속 방어한다.
- 스키마·툴 시그니처·`FACT_KEYS` 어휘 자체는 그대로다.
- 정밀도 지표는 P10-final-eval 몫 — 6번은 소표본 전후 비교이지 성능 수치가 아니다.
