# 신뢰성 보고서 (초안) — 위험 → 테스트 → 통과 · 실패 · 미검증

> **상태: 초안 (P8-frontend U9b, backend-agent, 2026-10-15). verifier 대조 완료(`review-u9b-backend.md` §6).**
> 교수 피드백(2026-10-15 캡스톤 발표): "어떤 테스트로 신뢰성을 올리고, 어떤 테스트를 통과하고 실패한 건지 분명하게 드러내야 고객들이 이 제품을 사용할 것." — 이 문서는 그 요구에 답한다. 구성은 **위험 → 그 위험을 막는 테스트 → 통과한 것 · 실패한 것 · 아직 확인하지 못한 것(미검증)** 이다.
>
> 규칙 (원칙8):
> - **새 수치를 만들지 않았다.** 모든 수치는 아래 파일에서 그대로 옮겼고 각 수치 옆에 출처 경로를 적었다. 이 문서가 직접 계산한 수치는 없다(합계 203 = 135 + 4 + 64 는 `tests.md` 가 이미 적은 값).
> - 성능이 기준에 못 미친 것도, 아직 사람이 확인하지 않은 것도 **있는 그대로** 적는다. "미검증" 은 실패가 아니라 "확인하지 않았다" 는 뜻이다.
> - 표본이 작은 평가는 방향까지만 말한다. 비율 뒤에는 항상 분자/분모를 함께 쓴다.
>
> 경로 약칭: `P8/` = `docs/wiki/packages/P8-frontend/` · `P4b/` = `docs/wiki/packages/P4b-er-redesign/` · `R/` = `reports/`.

## A. 오병합 — 다른 사람을 같은 사람으로 묶는다

**왜 중요한가.** 오병합은 사용자의 신뢰를 한 번에 무너뜨린다(CLAUDE.md 불변 원칙 1: 오병합 ≫ 미검출). 그래서 확신도가 `T_merge`(0.8) 미만이면 자동 병합하지 않고 `ask_user` 를 부른다.

**막는 테스트·평가.**
- 단위 테스트: `tests/test_er_candidates.py` · `test_er_rules.py` · `test_er_confidence.py` · `test_er_judge.py` · `test_er_pipeline.py` · `test_er_dictionary.py` · `test_er_types.py` · `test_er_smoke.py` (파일 이름만 적었다 — 건수는 이 초안에서 세지 않았다).
- 파일럿 평가: 시나리오 40건 · 채점 mention 132(골드 135 − ambiguous 3), 제안 방식과 베이스라인 4종 비교 — `R/eval.md` "실행 메타"·"방식 × 지표".

**통과한 것 (현재 `R/eval.md`, `T_merge` = 0.8, 분모 132).**

- 원인(`R/failure_cases.md` §8): ① **2단계 규칙 필터가 정답 후보를 지웠다**(오병합 `sc-015` "부장님", 미검출 `sc-007` "문실장님" 둘 다 여기서 시작) ② **4단계가 재지 못한 규칙 신호(`rule_checked`=0, 141 중 100)를 0 점으로 합산**해 확신도 상한이 0.80 에 묶여 79건 중 52건이 임계치 바로 아래에 몰렸다.

**남은 위험 (아직 위험이다).**
- 오병합 0 은 **"40건에서 안 났다" 이지 안전의 증명이 아니다.** D13 이 후보를 늘려 오병합 기회도 늘었다 — `R/failure_cases.md` §13.7.
- 감점 후보가 자동 연결된 경우 14건(전부 인접 위계 완화 예외 경로, 오병합 0/14), 보수 강등으로 되묻기가 된 경우 5건(전부 정답을 되묻게 한 것) — `R/failure_cases.md` §13.4. "예외 경로가 곧 위험 경로" 구조는 그대로다.
- `sc-015`·`sc-007` 은 "고쳐졌다" 가 아니라 "안전한 쪽(되묻기)으로 옮겨졌다" — 정답 병합이 된 것이 아니다(`R/failure_cases.md` §13.7).
- 두 실행의 차이가 전부 D12·D13 때문은 아니다: 양쪽에서 LLM 을 부른 136 mention 중 60건에서 `s_llm` 이 달랐다 — 같은 모델·프롬프트로도 자기보고 점수는 흔들린다(`R/failure_cases.md` §13.7).

**미검증.** 150건 데이터셋 최종 평가·신뢰구간·운영 `T_merge` 확정(P10, 아직 안 함) · 공급자 1벌(`openai` / `gpt-4o-mini-2024-07-18`)만 실호출 — Gemini·Anthropic 경로는 실호출 0(`R/failure_cases.md` §10) · LLM `reason` 원문이 제안 방식 trace 에 없어 "왜 그렇게 판정했나" 의 문장은 재현 불가(`R/failure_cases.md` §1).

## B. 확신도 — 에이전트가 자기 확신을 부풀린다

**막는 장치.** `s_llm` 은 LLM 의 자기보고 점수(0~1)일 뿐이고 로그 확률이 아니다(Claude API 가 주지 않는다). 그래서 임베딩 유사도·규칙 통과율과 결합한 3신호(`0.5·s_llm + 0.3·s_emb + 0.2·s_rule`, 미측정 신호는 분모에서 제외)로만 판정하고, 보정표(`R/calibration.json`)를 둔다.

**통과 / 한계.** 임계치와 무관하게 "LLM 이 고른 인물이 골드였는가" 만 보면(`matched_person_id` 가 있는 107건): `s_llm` 0.9–1.0 에서 98/101 (97.0%), 0.8–0.9 에서 2/5 (40.0%), 0.7–0.8 에서 1/1, 합계 101/107 (94.4%) — `R/failure_cases.md` §4g. **0.8–0.9 구간은 표본이 5건뿐이라 40.0% 를 비율로 읽으면 안 된다.**

**주의할 오독.** 보정표의 `proposed` 0.9–1.0 칸이 46.5% (47/101) 로 낮게 보이는 것은 `deferred`(되묻기)를 전부 오답으로 세는 정의 때문이다. LLM 과신의 증거가 아니다 — `R/failure_cases.md` §4g.

**미검증.** 다른 모델·다른 도메인에서의 보정 · 150건에서의 구간별 정답률(P10).

## C. 원문·근거 — 요약하다가 원문을 잃는다

**막는 장치.** 요약해도 `events.raw_utterance` 를 버리지 않고, 시맨틱 사실은 `fact_sources(fact_id, event_id)` 로 근거 이벤트에 연결한다. 화면은 펼칠 때만 원문 조회 API 를 부른다.

**테스트 (P8 백엔드 U2, 18건 — `P8/tests.md` "tests/test_api_read_raw.py").**
- 원문이 **한 글자도 가공되지 않는다**: 특수문자·줄바꿈·탭·이모지·앞뒤 공백이 든 문자열이 응답에서 `==` 로 일치(`test_이벤트_원문_응답_전체_값`), 5000자도 자르지 않음. 원문에 `strip()` 을 거는 변이(U2-M6)는 2건이 잡았다.
- 근거 목록은 최신순·동률은 id 내림차순·상한 20, 다른 사실·다른 인물의 원문이 섞이지 않는다(U2-M1·M3·M4·M5·M7·M8 검출).
- 프론트: 원문은 목록·카드 응답에 없고 펼칠 때 1회만 요청, 다시 펼쳐도 재요청 없음(`P8/tests.md` "card.test.tsx" 원문 행들, E2E `card.spec.ts` — 원문을 `textContent` 완전 일치로 단언).
- 메모리 승격·패턴 쪽 근거 링크: `tests/test_memory_promote.py` · `test_memory_patterns.py` · `test_memory_extract.py` (P6-memory 는 수용 기준 전부 통과, 전체 회귀 1622 passed skip 0 — `docs/wiki/CURRENT.md` P6-memory 항목).

**실패 이력.** E2E 에서 원문 줄바꿈이 공백으로 바뀌는 변이(U9a V2)를 1차 E2E 가 잡지 못했다(Playwright `toHaveText` 의 공백 정규화). 커밋 전에 `textContent` 완전 일치로 고쳐 1 failed 로 검출 — `P8/tests.md` E2E 카드 행, `P8/review-u9a-e2e.md`.

**미검증.** 실서버에서 사람이 카드의 타임라인 항목·사실을 펼쳐 DB 의 `raw_utterance` 와 같은지 보는 것(U10 판정표 30행 ⑥~⑧, 아직 안 함).

## D. 사용자 격리 — 남의 데이터가 보인다

**테스트.** 모든 조회에 `persons.user_id = app_user_id()` 조건. 없는 것과 남의 것은 같은 404 본문(`{"detail":{"code":"not_found"}}`)이라 존재 여부가 새지 않는다.
- 목록(`test_목록은_다른_사용자_인물을_뺀다`, U1-V1), 카드(`test_없는_인물과_타사용자_인물은_같은_404`, U1-V2), 이벤트 원문(U2-M2), 사실 근거 4가지 넘겨짚기(U2-M1·M3 — 남의 인물, 내 다른 인물의 사실 id, 남의 인물 경로에 내 사실, 세 404 본문 동일), 브리핑 목록(U3-M5/V2) — `P8/tests.md` 백엔드 절.
- **이번 단위(U9b)에 더한 방어:** 손으로 조작한 trace(남의 일정 id + 내 인물 id)가 남의 일정 제목·시각을 내 브리핑 목록에 섞지 못하게 하는 조인 조건 + 테스트(`test_조작된_trace_…`, 이 조건을 지우는 변이 U9b-M2 가 검출).

**한계 (솔직히).** 이 프로젝트에는 **인증이 없다.** 서버 환경변수 `APP_USER_ID` 한 사람을 전제로 하며(01-plan 41행 — 단일 사용자 전제는 P5-loop 결정 I, 격리 부채는 결정 D 로 P9 전 과제), `pending_questions`·`agent_traces` 에는 `user_id` 컬럼이 없어 대기 질문의 격리는 세션 id 에 의존한다(`P8/review-u3-read-questions-briefings.md` 8절). 여러 사용자가 한 서버를 쓰는 상황의 보안은 **검증하지 않았고 지원하지 않는다**(인증·로그인은 P9 전 과제).

## E. 조회가 데이터를 바꾼다 — 읽기 API 의 쓰기 0

**테스트.** 읽기 전용 6개 조회(`GET /persons`·`/persons/{id}`·`/events/{id}/raw`·`/persons/{pid}/facts/{fid}/sources`·`/questions/pending`·`/briefings`)는 호출 전후로 **스키마 v2 의 9테이블 행 수**와 `schedules.briefed_at`·`persons.updated_at` **값**이 같아야 한다 — 공통 헬퍼 `tests/helpers_read_api.py`, 쓰기 0 테스트 5건(`P8/tests.md` 의 `쓰기_0` 행들)과 헬퍼 자체 시험 2건.

**실패 이력 (숨기지 않는다).** 처음 만든 U1·U2 의 "쓰기 0" 테스트는 **7개 테이블의 행 수만** 비교했다. 이번 단위에서 조회 함수가 `Person`·`Schedule.briefed_at` 을 몰래 UPDATE 하거나 `push_subscriptions` 에 INSERT 하는 변이 5종(M4a~M4e)을 옛 테스트에 걸어 보니 **5종 전부 살아남았다**(`P8/evidence/20261015-1523-u9-be-mutation-old-tests.txt` — `12 passed`/`18 passed`). 값까지 보는 헬퍼로 바꾼 뒤에는 5종 전부 검출됐다(`P8/evidence/20261015-1523-u9-be-mutation.txt`). 즉 "쓰기 0 이 통과했다" 는 말은 옛 판에서는 증거가 되지 못했다.
